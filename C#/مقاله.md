# بهترین روش‌های پیاده‌سازی Background Jobs با Hangfire در ASP.NET Core

در معماری‌های مدرن وب، نیاز به پردازش کارهای پس‌زمینه (Background Jobs) برای دستیابی به مقیاس‌پذیری (Scalability)، جلوگیری از مسدود شدن رابط کاربری (Non-blocking UI)، استفاده بهینه از منابع سیستم و مدیریت فرآیندهای پیچیده (Workflows) امری ضروری است. در اکوسیستم .NET، Hangfire یکی از محبوب‌ترین و قدرتمندترین کتابخانه‌های پردازش کارهای پس‌زمینه محسوب می‌شود.

این مقاله بر روی **Best Practices** و **الگوهای تولیدی** (Production Patterns) تمرکز دارد، نه صرفاً تنظیمات اولیه یا معرفی قابلیت‌ها. هدف ما ارائه راهنمایی‌های عملی و مبتنی بر تجربه است که در مصاحبه‌های فنی و محیط‌های واقعی کاربرد داشته باشد.

بیایید از اصول پایه شروع کنیم و به تدریج به مفاهیم پیشرفته‌تر برسیم.

## 1. استفاده از Persistent Storage در محیط Production

### چرا این موضوع مهم است؟

ذخیره‌سازی در حافظه (In-Memory Storage) در Hangfire به معنای از دست رفتن تمام Job‌های در صف و در حال اجرا در صورت Restart شدن برنامه است. در محیط Production، این موضوع می‌تواند منجر به از دست رفتن تراکنش‌های مالی، اعلان‌های مهم یا پردازش‌های حیاتی شود.

### راه‌حل

**همیشه** از یک Persistent Storage استفاده کنید:

```csharp
services.AddHangfire(configuration => configuration
    .UseSqlServerStorage(connectionString, new SqlServerStorageOptions
    {
        SchemaName = "HangFire", // برای جداسازی منطقی
        PrepareSchemaIfNecessary = true
    }));
```

### گزینه‌های Storage

- **SQL Server**: مناسب برای اکثر سناریوها، پشتیبانی کامل از Transaction
- **PostgreSQL**: گزینه‌ای قدرتمند و Open Source
- **Redis**: برای سیستم‌های با Throughput بسیار بالا (نیاز به Hangfire.Pro)
- **MongoDB**: برای تیم‌هایی که از NoSQL استفاده می‌کنند

### نکته مهم در مصاحبه

در مصاحبه، اگر از In-Memory Storage در Production استفاده کنید، این یک **Red Flag** محسوب می‌شود. مصاحبه‌کننده انتظار دارد شما درک کنید که چرا Persistence برای Background Jobs حیاتی است.

## 2. طراحی Idempotent و Stateless Jobs

### Idempotency (قابلیت تکرارپذیری)

**Idempotency** به این معناست که اجرای چندباره یک Job با همان ورودی باید نتیجه یکسانی داشته باشد و هیچ Side Effect مضاعفی ایجاد نکند. این ویژگی برای Background Jobs **حیاتی** است چون:

1. Hangfire به صورت پیش‌فرض Job‌های Fail شده را Retry می‌کند
2. در صورت Crash برنامه، Job ممکن است دوباره اجرا شود
3. در محیط‌های Distributed، ممکن است یک Job به صورت همزمان در چند سرور اجرا شود

### مثال: پردازش سفارش (Non-Idempotent)

```csharp
// ❌ پیاده‌سازی خطرناک
public void ProcessOrder(int orderId)
{
    var order = _orderService.GetOrderById(orderId);

    // شارژ کارت اعتباری
    _paymentService.Charge(order.CreditCardInfo, order.Amount);

    // تغییر وضعیت سفارش
    order.Status = OrderStatus.Processed;
    _orderService.UpdateOrder(order);
}
```

**مشکل**: اگر بعد از `Charge` و قبل از `UpdateOrder` خطای شبکه رخ دهد، Hangfire این Job را Retry می‌کند و مشتری **دوباره** شارژ می‌شود!

### راه‌حل: Idempotent Implementation

```csharp
// ✅ پیاده‌سازی امن
public void ProcessOrder(int orderId)
{
     var order = _orderService.GetOrderById(orderId);

    // بررسی Idempotency: اگر قبلاً پردازش شده، خروج
    if (order.Status == OrderStatus.Processed)
    {
        _logger.LogInformation($"Order {orderId} already processed. Skipping.");
       return;
    }
    
    // استفاده از Transaction برای Atomicity
    using var transaction = _dbContext.Database.BeginTransaction();
    try
    {
        // بررسی مجدد در Transaction (Double-Check Pattern)
        order = _orderService.GetOrderById(orderId);
        if (order.Status == OrderStatus.Processed)
        {
            transaction.Rollback();
            return;
        }
        
        // شارژ کارت
        var chargeResult = _paymentService.Charge(order.CreditCardInfo, order.Amount);
        
        // ذخیره نتیجه شارژ در دیتابیس (Idempotency Key)
        order.PaymentTransactionId = chargeResult.TransactionId;
    order.Status = OrderStatus.Processed;
     _orderService.UpdateOrder(order);

        transaction.Commit();
    }
    catch (Exception ex)
    {
        transaction.Rollback();
        _logger.LogError(ex, $"Failed to process order {orderId}");
        throw; // برای Retry توسط Hangfire
    }
}
```

### الگوهای پیشرفته‌تر برای Idempotency

1. **Idempotency Key**: استفاده از کلید یکتا برای هر عملیات (مثل Transaction ID)
2. **Optimistic Concurrency**: استفاده از Row Version یا Timestamp
3. **Distributed Lock**: برای محیط‌های Multi-Server (مثل Redis Lock)

### نکته مهم در مصاحبه

در مصاحبه، اگر مثال Idempotency بزنید، مصاحبه‌کننده ممکن است بپرسد: "اگر Payment Gateway خودش Idempotent باشد، آیا هنوز نیاز به چک داریم؟" پاسخ: **بله**، چون Idempotency باید در **تمام لایه‌ها** رعایت شود و نمی‌توان به سرویس‌های خارجی اعتماد کرد.

### Stateless Jobs (کارهای بدون حالت)

یک Job **Stateless** است اگر:
- به هیچ State در حافظه (In-Memory) وابسته نباشد
- به Shared State که ممکن است توسط سیستم‌های دیگر تغییر کند وابسته نباشد
- تمام اطلاعات مورد نیاز را از ورودی‌ها یا دیتابیس قابل اعتماد دریافت کند

### چرا Stateless بودن مهم است؟

1. **مقیاس‌پذیری**: می‌توانید Job را روی هر سروری اجرا کنید
2. **قابلیت Retry**: در صورت Fail، می‌توان Job را بدون نگرانی از State از دست رفته Retry کرد
3. **Debugging**: راحت‌تر می‌توان مشکل را پیدا و تکرار کرد

### مثال: استفاده نادرست از HttpContext

```csharp
// ❌ وابستگی به HttpContext
public void SendUserNotification()
{
    // HttpContext در Background Thread موجود نیست!
    int userId = (int)HttpContext.Current.Session["UserId"];
    var user = _userService.GetUserById(userId);
    // Logic
}
```

**مشکلات**:
- `HttpContext.Current` در Background Thread `null` است
- Session State در Background Jobs در دسترس نیست
- این Job قابل Test کردن نیست

### راه‌حل: Stateless Design

```csharp
// ✅ Stateless و Testable
public void SendUserNotification(int userId)
{
    // تمام اطلاعات از Parameter یا Database می‌آید
    var user = _userService.GetUserById(userId);
    if (user == null)
    {
        _logger.LogWarning($"User {userId} not found");
        return;
}

    _notificationService.Send(user.Email, "Your notification");
}
```

### نکات مهم

1. **از Cache با احتیاط استفاده کنید**: اگر داده‌ای در Cache است، همیشه یک Fallback به Database داشته باشید
2. **از Static Variables پرهیز کنید**: در محیط‌های Multi-Server مشکل ایجاد می‌کند
3. **State را در Database ذخیره کنید**: اگر نیاز به State دارید، آن را در دیتابیس Persist کنید

### Reentrancy (قابلیت ورود مجدد)

با رعایت Idempotency و Stateless بودن، Job شما **Reentrant** می‌شود، یعنی می‌تواند در هر زمان و روی هر سروری بدون مشکل اجرا شود.

  

## 3. نگه داشتن Job‌ها کوچک و متمرکز

### Single Responsibility Principle (SRP)

هر Job باید **فقط یک دلیل برای تغییر** داشته باشد. این اصل باعث می‌شود:

- **Maintainability**: راحت‌تر می‌توان کد را تغییر داد
- **Testability**: تست کردن یک مسئولیت ساده‌تر است
- **Debugging**: پیدا کردن مشکل سریع‌تر است
- **Reusability**: Job‌های کوچک قابل استفاده مجدد هستند

### مثال: Job بزرگ و پیچیده

```csharp
// ❌ Job با مسئولیت‌های متعدد
public void ProcessOrderComplete(int orderId)
{
    // 1. پردازش پرداخت
    ProcessPayment(orderId);
    
    // 2. به‌روزرسانی موجودی
    UpdateInventory(orderId);
    
    // 3. ارسال ایمیل
    SendConfirmationEmail(orderId);
    
    // 4. به‌روزرسانی Analytics
    UpdateAnalytics(orderId);
    
    // 5. ارسال به سیستم‌های خارجی
    SyncWithExternalSystems(orderId);
}
```

**مشکلات**:
- اگر یک بخش Fail شود، کل Job Fail می‌شود
- Retry کردن کل Job ممکن است Side Effect داشته باشد
- نمی‌توان بخش‌ها را به صورت مستقل Scale کرد

### راه‌حل: تقسیم به Job‌های کوچک

```csharp
// ✅ Job‌های کوچک و متمرکز
public void ProcessPayment(int orderId)
{
    // فقط پردازش پرداخت
}

public void UpdateInventory(int orderId)
{
    // فقط به‌روزرسانی موجودی
}

public void SendConfirmationEmail(int orderId)
{
    // فقط ارسال ایمیل
}

// زنجیره کردن Job‌ها
var paymentJobId = BackgroundJob.Enqueue(() => ProcessPayment(orderId));
var inventoryJobId = BackgroundJob.ContinueJobWith(paymentJobId, 
    () => UpdateInventory(orderId));
var emailJobId = BackgroundJob.ContinueJobWith(inventoryJobId, 
    () => SendConfirmationEmail(orderId));
```

### مزایای این رویکرد

1. **Fault Isolation**: اگر یک Job Fail شود، بقیه اجرا می‌شوند
2. **Independent Scaling**: می‌توانید Worker‌های بیشتری برای Job‌های مهم اختصاص دهید
3. **Better Monitoring**: می‌توانید دقیقاً ببینید کدام بخش مشکل دارد
4. **Selective Retry**: فقط بخش Fail شده را Retry می‌کنید

### نکته در مصاحبه

اگر مصاحبه‌کننده بپرسد: "آیا همیشه باید Job‌ها را کوچک کنیم؟" پاسخ: **نه همیشه**. اگر عملیات‌ها باید به صورت Atomic انجام شوند (مثل Transaction)، بهتر است در یک Job باشند. Trade-off بین Atomicity و Fault Isolation را توضیح دهید.

## 4. مدیریت Exception و Retry Strategy

### Automatic Retries در Hangfire

Hangfire به صورت پیش‌فرض Job‌های Fail شده را Retry می‌کند. اما **مدیریت صحیح Retry Policy** برای Performance و Reliability حیاتی است.

### تنظیم Retry Policy

```csharp
// تنظیم Retry برای تمام Job‌ها
GlobalJobFilters.Filters.Add(new AutomaticRetryAttribute 
{ 
    Attempts = 3, // تعداد تلاش‌ها
    DelaysInSeconds = new[] { 10, 30, 60 } // فاصله بین Retry‌ها (Exponential Backoff)
});

// یا برای Job خاص
[AutomaticRetry(Attempts = 5, DelaysInSeconds = new[] { 5, 15, 30, 60, 120 })]
public void ProcessCriticalOrder(int orderId)
{
    // Logic
}
```

### انواع خطاها و استراتژی Retry

1. **Transient Errors** (خطاهای موقت):
   - خطای شبکه، Timeout، Deadlock
   - **باید Retry شود** با Exponential Backoff

2. **Permanent Errors** (خطاهای دائمی):
   - Validation Error، Business Logic Error
   - **نباید Retry شود** (هدر دادن منابع)

### پیاده‌سازی Retry هوشمند

```csharp
public void ProcessOrder(int orderId)
{
    try
    {
        var order = _orderService.GetOrderById(orderId);
        _paymentService.Charge(order);
    }
    catch (PaymentGatewayTimeoutException ex)
    {
        // Transient Error - Retry منطقی است
        _logger.LogWarning(ex, $"Payment gateway timeout for order {orderId}");
        throw; // برای Retry توسط Hangfire
    }
    catch (InvalidCreditCardException ex)
    {
        // Permanent Error - Retry بی‌فایده است
        _logger.LogError(ex, $"Invalid credit card for order {orderId}");
        // Job را به Failed State ببرید بدون Retry
        throw new JobAbortedException("Cannot retry invalid credit card", ex);
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, $"Unexpected error processing order {orderId}");
        throw;
    }
}
```

### Error Handling در Job

```csharp
// ✅ Error Handling صحیح
public void SendEmailNotification(int userId)
{
    try
    {
        var user = _userService.GetUserById(userId);
        if (user == null)
        {
            _logger.LogWarning($"User {userId} not found. Job will not retry.");
            return; // Silent failure - نیازی به Retry نیست
        }
        
        _emailService.Send(user.Email, "Notification");
    }
    catch (EmailServiceUnavailableException ex)
    {
        // Transient - Retry منطقی است
        _logger.LogWarning(ex, $"Email service unavailable. Will retry.");
        throw;
    }
    catch (Exception ex)
    {
        // Unexpected error - Log و Retry
        _logger.LogError(ex, $"Unexpected error sending email to user {userId}");
        throw;
    }
}
```

### نکات مهم

1. **Exponential Backoff**: فاصله بین Retry‌ها را به تدریج افزایش دهید
2. **Max Retry Attempts**: برای جلوگیری از Infinite Loop، حداکثر تعداد Retry را محدود کنید
3. **Dead Letter Queue**: Job‌هایی که بعد از تمام Retry‌ها Fail می‌شوند را در صف جداگانه قرار دهید
4. **Monitoring**: Job‌های Fail شده را Monitor کنید و Alert تنظیم کنید

### نکته در مصاحبه

در مصاحبه، اگر بپرسند: "چرا Retry همه خطاها خوب نیست؟" پاسخ: Retry کردن خطاهای Permanent (مثل Validation Error) فقط منابع را هدر می‌دهد و Database Load را افزایش می‌دهد. باید بین Transient و Permanent Error تمایز قائل شویم.

  

## 5. امنیت Dashboard Hangfire

### چرا امنیت Dashboard حیاتی است؟

Dashboard Hangfire دسترسی به **تمام** Job‌ها، تاریخچه اجرا، لاگ‌ها و حتی امکان **حذف یا Retry دستی** Job‌ها را فراهم می‌کند. در دسترس بودن این پنل برای عموم یک **خطر امنیتی جدی** است.

### پیاده‌سازی Authorization

```csharp
// ✅ Authorization Filter
public class HangfireAuthorizationFilter : IDashboardAuthorizationFilter
{
    public bool Authorize(DashboardContext context)
    {
        var httpContext = context.GetHttpContext();
        
        // بررسی Authentication
        if (!httpContext.User.Identity.IsAuthenticated)
            return false;
        
        // بررسی Role یا Policy
        return httpContext.User.IsInRole("Admin") || 
               httpContext.User.HasClaim("Permission", "Hangfire.Dashboard");
    }
}

// استفاده در Startup
app.UseHangfireDashboard("/hangfire", new DashboardOptions
 {
    Authorization = new[] { new HangfireAuthorizationFilter() },
    // غیرفعال کردن برخی قابلیت‌های خطرناک
    IsReadOnlyFunc = (DashboardContext context) => false, // برای Production می‌توان true کرد
    DashboardTitle = "Job Management"
});
```

### امنیت در سطح Network

```csharp
// محدود کردن دسترسی به IP‌های خاص (در Production)
app.UseHangfireDashboard("/hangfire", new DashboardOptions
{
    Authorization = new[] { new HangfireAuthorizationFilter() },
    // فقط از IP‌های داخلی دسترسی
    AppPath = null // مخفی کردن لینک به Dashboard از صفحه اصلی
});
```

### Best Practices امنیتی

1. **HTTPS Only**: Dashboard را فقط روی HTTPS در دسترس قرار دهید
2. **IP Whitelisting**: در Production، دسترسی را به IP‌های خاص محدود کنید
3. **Read-Only Mode**: اگر نیاز به تغییر ندارید، Dashboard را Read-Only کنید
4. **Audit Logging**: تمام دسترسی‌ها به Dashboard را Log کنید
5. **Rate Limiting**: برای جلوگیری از Brute Force Attack

### نکته در مصاحبه

در مصاحبه، اگر بپرسند: "چرا Dashboard را در Production غیرفعال نمی‌کنیم؟" پاسخ: Dashboard برای Monitoring و Troubleshooting ضروری است، اما باید با Authorization و Network Security محافظت شود. Trade-off بین Convenience و Security را توضیح دهید.

  

## 6. بهینه‌سازی استفاده از منابع

### مدیریت Worker Count

Hangfire به صورت پیش‌فرض **20 Worker** همزمان ایجاد می‌کند. این عدد باید بر اساس:

1. **تعداد CPU Cores**
2. **نوع Job‌ها** (CPU-bound یا I/O-bound)
3. **منابع موجود** (RAM، Network)
4. **Database Connection Pool**

تنظیم شود.

### تنظیم Worker Count

```csharp
// ✅ تنظیم بر اساس منابع
var options = new BackgroundJobServerOptions 
{ 
    // برای I/O-bound Jobs (مثل API calls، Database queries)
    WorkerCount = Environment.ProcessorCount * 2,
    
    // برای CPU-bound Jobs
    // WorkerCount = Environment.ProcessorCount
    
    Queues = new[] { "critical", "default", "low" },
    ServerTimeout = TimeSpan.FromMinutes(30)
};

app.UseHangfireServer(options);
```

### نکات مهم

- **Worker زیاد = Context Switching بیشتر**: می‌تواند Performance را کاهش دهد
- **Worker کم = Queue Backlog**: Job‌ها دیرتر پردازش می‌شوند
- **Database Connection Pool**: تعداد Worker نباید بیشتر از Connection Pool باشد

### فرمول پیشنهادی

```
I/O-bound Jobs: WorkerCount = CPU Cores × 2
CPU-bound Jobs: WorkerCount = CPU Cores
Mixed: WorkerCount = CPU Cores × 1.5
```

### مدیریت منابع و جلوگیری از Memory Leak

```csharp
// ❌ ارسال Object بزرگ به Job
var largeOrder = _orderService.GetOrderWithAllDetails(orderId);
BackgroundJob.Enqueue(() => ProcessOrder(largeOrder)); // Serialize شدن در Database!

// ✅ ارسال فقط ID
BackgroundJob.Enqueue(() => ProcessOrder(orderId));
```

**مشکلات ارسال Object بزرگ**:
- Serialization Overhead: Object باید در Database Serialize شود
- Database Load: حجم داده در Database افزایش می‌یابد
- Memory Usage: Worker باید Object را Deserialize کند
- Versioning: اگر Object تغییر کند، Job‌های قدیمی Fail می‌شوند

### Dispose Pattern در Jobs

```csharp
// ✅ Dispose صحیح منابع
public async Task ProcessFileAsync(int fileId)
{
    var file = await _fileService.GetFileAsync(fileId);
    
    using var stream = new FileStream(file.Path, FileMode.Open);
    using var reader = new StreamReader(stream);
    
    // Process file
    var content = await reader.ReadToEndAsync();
    await _processor.ProcessAsync(content);
    
    // Dispose به صورت خودکار انجام می‌شود
}
```

### استفاده از Batches برای Job‌های مرتبط

**Batch** در Hangfire به شما امکان می‌دهد چندین Job را به صورت یک واحد مدیریت کنید. اگر یک Job در Batch Fail شود، می‌توانید کل Batch را Retry کنید.

```csharp
// ✅ استفاده از Batch
var batchId = BatchJob.StartNew(x =>
{
    for (var i = 0; i < 1000; i++)
    {
        x.Enqueue(() => SendEmail(userIds[i]));
    }
});

// Continuation Job بعد از اتمام Batch
BackgroundJob.ContinueJobWith(batchId, () => NotifyBatchComplete(batchId));
```

**مزایای Batch**:
- **Atomicity**: می‌توانید کل Batch را به عنوان یک واحد مدیریت کنید
- **Monitoring**: می‌توانید پیشرفت Batch را Track کنید
- **Retry Strategy**: می‌توانید Retry را در سطح Batch مدیریت کنید

**نکته**: Batch در Hangfire.Pro (نسخه پولی) قابلیت‌های بیشتری دارد. در نسخه رایگان، می‌توانید از Continuation Jobs استفاده کنید.

### مدیریت Queue Polling Interval

**Queue Polling** به معنای بررسی دوره‌ای Database برای Job‌های جدید است. این Interval باید بر اساس:

1. **Latency Requirement**: چقدر سریع باید Job‌ها شروع شوند؟
2. **Database Load**: هر چه Interval کوتاه‌تر، بار Database بیشتر
3. **Job Frequency**: اگر Job‌ها به ندرت ایجاد می‌شوند، Interval طولانی‌تر منطقی است

```csharp
var options = new BackgroundJobServerOptions 
{ 
    QueuePollInterval = TimeSpan.FromSeconds(15), // پیش‌فرض
    // برای Job‌های Critical
    // QueuePollInterval = TimeSpan.FromSeconds(5),
    // برای Job‌های Non-Critical
    // QueuePollInterval = TimeSpan.FromSeconds(30)
};
```

**Trade-off**:
- **Interval کوتاه**: Latency کمتر، اما Database Load بیشتر
- **Interval طولانی**: Database Load کمتر، اما Latency بیشتر

**نکته**: در محیط‌های Production با Job‌های زیاد، Interval 15 ثانیه معمولاً مناسب است.

## 7. جلوگیری از Long-Running یا Blocking Tasks

### استفاده از Async/Await برای I/O-Bound Operations

در Background Jobs، استفاده از Async/Await برای عملیات I/O-Bound **حیاتی** است چون:

1. **Thread Pool Efficiency**: Thread را آزاد می‌کند تا Job‌های دیگر اجرا شوند
2. **Scalability**: می‌توانید Worker Count بیشتری داشته باشید
3. **Resource Utilization**: CPU و Memory بهتر استفاده می‌شود

### مثال: Sync vs Async

```csharp
// ❌ Blocking I/O
public void SendEmailNotification(int userId)
{
    var user = _userService.GetUserById(userId); // Blocking
    _emailService.Send(user.Email, "Notification"); // Blocking
    _logger.LogInformation("Email sent"); // Blocking
}

// ✅ Non-blocking I/O
public async Task SendEmailNotificationAsync(int userId)
{
    var user = await _userService.GetUserByIdAsync(userId);
    await _emailService.SendAsync(user.Email, "Notification");
    _logger.LogInformation("Email sent");
}
```

### چه زمانی از Async استفاده کنیم؟

**استفاده کنید**:
- درخواست‌های HTTP/API
- Database Queries
- File I/O
- Email/SMS Sending
- هر عملیات I/O که منتظر پاسخ خارجی است

**استفاده نکنید**:
- عملیات CPU-Bound (مثل Image Processing، Encryption)
- Legacy Code که Async را پشتیبانی نمی‌کند (اما سعی کنید Refactor کنید)

### استفاده از Cancellation Token

```csharp
// ✅ پشتیبانی از Cancellation
public async Task ProcessLargeFileAsync(int fileId, CancellationToken cancellationToken)
{
    cancellationToken.ThrowIfCancellationRequested();
    
    var file = await _fileService.GetFileAsync(fileId, cancellationToken);
    
    // Process in chunks
    foreach (var chunk in file.Chunks)
    {
        cancellationToken.ThrowIfCancellationRequested();
        await ProcessChunkAsync(chunk, cancellationToken);
    }
}

// تنظیم Cancellation Check Interval
services.AddHangfireServer(new BackgroundJobServerOptions
{
    CancellationCheckInterval = TimeSpan.FromSeconds(5) // پیش‌فرض
});
```

**مزایای Cancellation Token**:
- **Graceful Shutdown**: Job می‌تواند به صورت تمیز متوقف شود
- **Resource Cleanup**: می‌توانید منابع را Dispose کنید
- **کاهش ThreadAbortException**: که در .NET Core deprecated است

### نکته در مصاحبه

اگر بپرسند: "چرا در Background Job به Async نیاز داریم؟" پاسخ: Background Jobs معمولاً I/O-Bound هستند (Database، API، File). Async باعث می‌شود Worker Thread در زمان انتظار آزاد شود و Job‌های دیگر اجرا شوند. این Scalability را افزایش می‌دهد.

  

## 8. مدیریت Concurrency

### کنترل همزمانی (Concurrency Control)

در محیط‌های Distributed یا Multi-Server، ممکن است یک Job به صورت همزمان روی چند سرور اجرا شود. این موضوع می‌تواند منجر به:

- **Race Condition**: دسترسی همزمان به Shared Resource
- **Data Corruption**: داده‌های ناسازگار
- **Duplicate Processing**: پردازش تکراری

### استفاده از DisableConcurrentExecution

```csharp
// ✅ جلوگیری از اجرای همزمان
[DisableConcurrentExecution(timeoutInSeconds: 60)]
public void ProcessOrder(int orderId)
{
    // فقط یک نمونه از این Job در هر زمان اجرا می‌شود
    var order = _orderService.GetOrderById(orderId);
    // Process order
}
```

**چگونه کار می‌کند**:
- Hangfire از Database Lock استفاده می‌کند (مثل Distributed Mutex)
- اگر Job در حال اجرا باشد، Job بعدی منتظر می‌ماند
- Timeout تعیین می‌کند که چقدر منتظر بماند

### مثال: به‌روزرسانی موجودی

```csharp
// ❌ بدون Concurrency Control
public void UpdateInventory(int productId, int quantity)
{
    var product = _productService.GetProduct(productId);
    product.Stock -= quantity; // Race Condition!
    _productService.UpdateProduct(product);
}

// ✅ با Concurrency Control
[DisableConcurrentExecution(timeoutInSeconds: 30)]
public void UpdateInventory(int productId, int quantity)
{
    using var transaction = _dbContext.Database.BeginTransaction();
    try
    {
        // استفاده از Database Lock
        var product = _dbContext.Products
            .Where(p => p.Id == productId)
            .FirstOrDefault();
        
        if (product.Stock < quantity)
            throw new InsufficientStockException();
        
        product.Stock -= quantity;
        _dbContext.SaveChanges();
        transaction.Commit();
    }
    catch
    {
        transaction.Rollback();
        throw;
    }
}
```

### Timeout و Deadlock Prevention

```csharp
[DisableConcurrentExecution(timeoutInSeconds: 60)]
public void ProcessCriticalTask(int taskId)
{
    // اگر Job بیش از 60 ثانیه طول بکشد، Timeout می‌شود
    // این از Deadlock جلوگیری می‌کند
}
```

**نکته**: Timeout باید بر اساس زمان واقعی اجرای Job تنظیم شود. اگر Timeout خیلی کوتاه باشد، Job‌های معتبر Fail می‌شوند.

### Throttling و Rate Limiting

**Throttling** به معنای کنترل نرخ اجرای Job‌ها است. این موضوع برای:

- **API Rate Limits**: جلوگیری از عبور از محدودیت API خارجی
- **Database Load**: جلوگیری از Overload شدن Database
- **Resource Management**: مدیریت منابع محدود

**مهم است**.

### استفاده از Hangfire.Throttling

```csharp
// نصب: Install-Package Hangfire.Throttling

// ثبت در Startup
services.AddHangfireThrottling();

// استفاده در Job
[RateLimit("ApiRateLimiter", 10, 60)] // 10 درخواست در 60 ثانیه
public async Task CallExternalApiAsync(string endpoint)
{
    var response = await _httpClient.GetAsync(endpoint);
    // Process response
}
```

### مثال: فراخوانی API با Rate Limit

```csharp
// سناریو: API خارجی فقط 10 درخواست در دقیقه اجازه می‌دهد

[RateLimit("PaymentGateway", 10, 60)]
public async Task ProcessPaymentAsync(int orderId)
{
    var order = await _orderService.GetOrderByIdAsync(orderId);
    var result = await _paymentGateway.ChargeAsync(order);
    // Process result
}

// اگر 11 Job همزمان Enqueue شود:
// - 10 Job اول بلافاصله اجرا می‌شوند
// - Job 11ام منتظر می‌ماند تا یکی از Job‌های قبلی تمام شود
```

### استفاده پیشرفته: Semaphores

```csharp
// محدود کردن تعداد Job‌های همزمان
[Throttle("DatabaseOperations", 5)] // حداکثر 5 Job همزمان
public async Task HeavyDatabaseOperationAsync(int dataId)
{
    // فقط 5 Job می‌توانند همزمان اجرا شوند
    await _dbService.ProcessHeavyQueryAsync(dataId);
}
```

### نکته در مصاحبه

اگر بپرسند: "تفاوت بین DisableConcurrentExecution و Throttle چیست؟" پاسخ: 
- `DisableConcurrentExecution`: فقط **یک** نمونه از Job می‌تواند اجرا شود (Mutex)
- `Throttle`: **چند** نمونه می‌توانند اجرا شوند، اما با محدودیت (Semaphore)

### استفاده از IThrottlingManager (پیشرفته)

```csharp
public class CustomThrottlingService
{
    private readonly IThrottlingManager _throttlingManager;
    
    public CustomThrottlingService(IThrottlingManager throttlingManager)
    {
        _throttlingManager = throttlingManager;
    }
    
    public async Task ProcessWithCustomThrottle()
    {
        // Custom throttling logic
        await _throttlingManager.WaitAsync("CustomResource", 3, TimeSpan.FromMinutes(1));
        // Process
    }
}
```

**نکته**: برای جزئیات بیشتر به [مستندات Hangfire.Throttling](https://github.com/HangfireIO/Hangfire.Throttling) مراجعه کنید.

  

## 9. مقیاس‌پذیری (Scalability)

### Horizontal Scaling (مقیاس‌پذیری افقی)

Hangfire از **Distributed Processing** پشتیبانی می‌کند. این یعنی می‌توانید چندین سرور را به یک Storage مشترک (مثل SQL Server یا Redis) متصل کنید و همه از همان Queue‌ها Job دریافت کنند.

**مزایا**:
- **Throughput بیشتر**: با اضافه کردن سرور، تعداد Job‌های پردازش شده افزایش می‌یابد
- **High Availability**: اگر یک سرور Fail شود، بقیه به کار ادامه می‌دهند
- **Cost Effective**: می‌توانید از سرورهای کوچک‌تر استفاده کنید

**نکته مهم**: تمام سرورها باید به **همان Database** متصل باشند.

### Vertical Scaling (مقیاس‌پذیری عمودی)

افزایش RAM و CPU سرور موجود. این روش:

- **ساده‌تر** است (نیازی به تغییر Architecture نیست)
- **گران‌تر** است (هزینه سخت‌افزار)
- **محدود** است (نمی‌توانید بی‌نهایت CPU اضافه کنید)

### Auto-Scaling با Kubernetes

برای سیستم‌های با بار متغیر، Auto-Scaling می‌تواند بسیار مفید باشد:

```yaml
# Kubernetes HPA (Horizontal Pod Autoscaler)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hangfire-worker
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hangfire-worker
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

**Metrics برای Auto-Scaling**:
- Queue Length: اگر Queue طولانی شد، Scale Up
- CPU Utilization: اگر CPU بالا رفت، Scale Up
- Job Processing Rate: تعداد Job‌های پردازش شده در ثانیه

### نکته در مصاحبه

اگر بپرسند: "تفاوت Horizontal و Vertical Scaling چیست؟" پاسخ: Horizontal Scaling یعنی اضافه کردن سرورهای بیشتر (افزایش تعداد)، Vertical Scaling یعنی افزایش قدرت سرور موجود (افزایش اندازه). Horizontal Scaling معمولاً بهتر است چون محدودیت کمتری دارد و Cost-Effective‌تر است.

## 10. مدیریت استراتژیک Queue‌ها

### اولویت‌بندی با Queue‌ها

Queue‌ها در Hangfire به شما امکان می‌دهند Job‌ها را بر اساس اولویت دسته‌بندی کنید. Worker‌ها ابتدا Queue‌های با اولویت بالاتر را پردازش می‌کنند.

```csharp
// تنظیم Worker برای پردازش Queue‌های خاص
app.UseHangfireServer(new BackgroundJobServerOptions
{
    Queues = new[] { "critical", "high", "default", "low" } // ترتیب مهم است!
 });

// Enqueue کردن Job در Queue خاص
BackgroundJob.Enqueue(() => ProcessCriticalTask(), "critical");
BackgroundJob.Enqueue(() => ProcessNormalTask(), "default");
```

**استراتژی Queue**:
- **critical**: Job‌های حیاتی (پرداخت، اعلان‌های مهم)
- **high**: Job‌های مهم اما نه حیاتی
- **default**: Job‌های عادی
- **low**: Job‌های با اولویت پایین (مثل Cleanup)

### Monitoring Queue‌ها

```csharp
// استفاده از Hangfire API برای Monitoring
var monitoringApi = JobStorage.Current.GetMonitoringApi();
var queues = monitoringApi.Queues();

foreach (var queue in queues)
{
    _logger.LogInformation($"Queue: {queue.Name}, Length: {queue.Length}, Fetched: {queue.Fetched}");
    
    // Alert اگر Queue خیلی طولانی شد
    if (queue.Length > 1000)
    {
        _alertService.SendAlert($"Queue {queue.Name} has {queue.Length} pending jobs!");
    }
}
```

**Metrics مهم**:
- **Queue Length**: تعداد Job‌های در انتظار
- **Processing Time**: میانگین زمان پردازش
- **Failure Rate**: درصد Job‌های Fail شده

### Cleanup و Expiration

Hangfire به صورت خودکار Job‌های قدیمی را حذف می‌کند:

- **Successful Jobs**: بعد از 24 ساعت (پیش‌فرض)
- **Failed Jobs**: بعد از 7 روز (پیش‌فرض)
- **Batched Jobs**: بعد از 7 روز (پیش‌فرض)

```csharp
// تنظیم Expiration
services.AddHangfire(config => config
    .UseSqlServerStorage(connectionString, new SqlServerStorageOptions
    {
        JobExpirationCheckInterval = TimeSpan.FromHours(1), // هر ساعت چک کند
    }));
```

**نکته**: Expiration را بر اساس نیاز Business تنظیم کنید. اگر نیاز به Audit Trail دارید، Expiration را طولانی‌تر کنید.

### چرا DI در Hangfire مهم است؟

DI در Hangfire باعث می‌شود:

### Lifetime Management

**مشکل**: Background Jobs خارج از HTTP Request Lifecycle هستند، پس Scoped Services به صورت خودکار Dispose نمی‌شوند.

```csharp
// ❌ مشکل: Scoped Service در Background Job
public class EmailJob
{
    private readonly IEmailService _emailService; // Scoped
    
    public EmailJob(IEmailService emailService)
    {
        _emailService = emailService; // ممکن است Dispose شده باشد
    }
}

// ✅ راه‌حل 1: استفاده از IServiceProvider
public class EmailJob
{
    private readonly IServiceProvider _serviceProvider;
    
    public EmailJob(IServiceProvider serviceProvider)
    {
        _serviceProvider = serviceProvider;
    }
    
    public async Task SendEmailAsync(int userId)
    {
        using var scope = _serviceProvider.CreateScope();
        var emailService = scope.ServiceProvider.GetRequiredService<IEmailService>();
        await emailService.SendAsync(userId);
    }
}

// ✅ راه‌حل 2: استفاده از Transient Services
services.AddTransient<IEmailService, EmailService>(); // Transient بهتر است

// ✅ راه‌حل 3: استفاده از Hangfire Activator (پیشنهادی)
public class HangfireActivator : JobActivator
{
    private readonly IServiceProvider _serviceProvider;
    
    public HangfireActivator(IServiceProvider serviceProvider)
    {
        _serviceProvider = serviceProvider;
    }
    
    public override object ActivateJob(Type jobType)
    {
        return _serviceProvider.GetRequiredService(jobType);
    }
}
```

### Thread Safety و Singleton Services

```csharp
// ⚠️ خطر: Singleton با State
public class CacheService : ICacheService
{
    private readonly Dictionary<string, object> _cache = new(); // Not Thread-Safe!
    
    public void Set(string key, object value)
    {
        _cache[key] = value; // Race Condition!
    }
}

// ✅ راه‌حل: Thread-Safe Singleton
public class CacheService : ICacheService
{
    private readonly ConcurrentDictionary<string, object> _cache = new();
    
    public void Set(string key, object value)
    {
        _cache[key] = value; // Thread-Safe
    }
}
```

**نکته**: اگر از Singleton استفاده می‌کنید، مطمئن شوید Thread-Safe است.

### Best Practices

1. **ترجیح Transient**: برای Job‌ها، Transient Services بهتر است
2. **Scoped را با احتیاط استفاده کنید**: اگر نیاز به Scoped دارید، از IServiceProvider.CreateScope استفاده کنید
3. **Singleton فقط برای Stateless Services**: اگر State دارد، Thread-Safe باشد
4. **از Hangfire Activator استفاده کنید**: مدیریت Lifecycle را خودکار می‌کند

## 14. Graceful Shutdown

### چرا Graceful Shutdown مهم است؟

در Production، وقتی برنامه Restart می‌شود (مثلاً برای Deploy)، Job‌های در حال اجرا باید:

1. **تکمیل شوند**: برای جلوگیری از Data Inconsistency
2. **منابع آزاد شوند**: برای جلوگیری از Memory Leak
3. **Transaction‌ها Commit شوند**: برای جلوگیری از Data Loss

### پیاده‌سازی Graceful Shutdown

```csharp
public void Configure(IApplicationBuilder app, IWebHostEnvironment env, 
    IHostApplicationLifetime applicationLifetime, IBackgroundJobClient backgroundJobClient)
{
    applicationLifetime.ApplicationStopping.Register(() =>
    {
        _logger.LogInformation("Application is stopping. Waiting for jobs to complete...");
        
        // 1. جلوگیری از Enqueue شدن Job‌های جدید
        GlobalJobFilters.Filters.Add(new AutomaticRetryAttribute { Attempts = 0 });
        
        // 2. صبر کردن برای تکمیل Job‌های در حال اجرا
        var cancellationToken = new CancellationTokenSource(TimeSpan.FromSeconds(30)).Token;
        
        try
        {
            // اگر از IHostedService استفاده می‌کنید
            var hangfireServer = app.ApplicationServices.GetService<BackgroundJobServer>();
            if (hangfireServer != null)
            {
                hangfireServer.SendStop();
                hangfireServer.WaitForShutdown(cancellationToken);
            }
            
            _logger.LogInformation("Hangfire server stopped gracefully");
        }
        catch (OperationCanceledException)
        {
            _logger.LogWarning("Shutdown timeout. Some jobs may not have completed.");
        }
    });
}
```

### استفاده از IHostedService (روش بهتر)

```csharp
public class HangfireHostedService : IHostedService
{
    private BackgroundJobServer _server;
    
    public Task StartAsync(CancellationToken cancellationToken)
    {
        _server = new BackgroundJobServer();
        return Task.CompletedTask;
    }
    
    public Task StopAsync(CancellationToken cancellationToken)
    {
        _server?.SendStop();
        _server?.Dispose();
        return Task.CompletedTask;
    }
}

// ثبت در Startup
services.AddSingleton<IHostedService, HangfireHostedService>();
```

### نکات مهم

1. **Timeout**: حداکثر زمان انتظار را محدود کنید (مثلاً 30 ثانیه)
2. **Job Cancellation**: از CancellationToken در Job‌ها استفاده کنید
3. **Monitoring**: Log کنید که چه Job‌هایی در زمان Shutdown در حال اجرا بودند
4. **Health Checks**: از Health Checks استفاده کنید تا ببینید آیا Job‌ها در حال اجرا هستند

### نکته در مصاحبه

اگر بپرسند: "چرا Graceful Shutdown مهم است؟" پاسخ: در Production، Restart برنامه نباید منجر به Data Loss یا Incomplete Transactions شود. Graceful Shutdown تضمین می‌کند که Job‌های در حال اجرا تکمیل شوند قبل از اینکه برنامه بسته شود.

  

## سخن پایانی

پیاده‌سازی صحیح Hangfire در ASP.NET Core می‌تواند **Performance**، **Scalability** و **Maintainability** سیستم شما را به میزان قابل توجهی افزایش دهد. با رعایت Best Practices ارائه شده در این مقاله:

- **طراحی Idempotent و Stateless Jobs** برای قابلیت اطمینان
- **مدیریت صحیح Concurrency** برای جلوگیری از Race Condition
- **Error Handling و Retry Strategy** برای Resilience
- **استفاده صحیح از Dependency Injection** برای Testability
- **Monitoring و Logging** برای Observability
- **Graceful Shutdown** برای جلوگیری از Data Loss

می‌توانید سیستم‌های پردازش پس‌زمینه **قوی، قابل اعتماد و Production-Ready** ایجاد کنید.

### نکته نهایی

**هر یک از این Best Practices را بر اساس نیاز Business و منابع در دسترس خود انتخاب کنید**. Over-Engineering به اندازه Under-Engineering مضر است. در مصاحبه‌ها، نشان دهید که می‌دانید **چه زمانی** و **چرا** از هر تکنیک استفاده می‌کنید، نه فقط اینکه **چگونه** آن را پیاده‌سازی می‌کنید.
