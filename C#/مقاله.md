خیلی اوقات پیش میاد که برای مقیاس پذیری (Scalability) و مسدود نکردن رابط کاربری (Blocking-UI) یا استفاده کارآمد از منابع سیستم یا کنترل فرآیند ها (Workflows) دست به دامن سرویس های پس زمینه (Background Jobs) میشیم. در این زمان بسته به نیاز یا از پیاده سازی های Built-In استفاده میکنیم یا از Third-party package ها استفاده میکنیم.

که یکی از بهترین ها برای این کار Hangfire هست. جدای توضیحات نحوه تنظیم و استفاده از این پکیج و ویژگی هایی که در اختیار ما میزاره، موقع پیاده سازی کار های پس زمینه و استفاده از Hangfire باید نکاتی رو مد نظرمون داشته باشیم تا بتونیم سیستم رو هرچه کارآمد تر بنویسیم و به اصطلاح باید Best Practices رعایت کنیم.

نکته : این مقاله صرف کانفیگ کردن و معرفی قابلیت های Hangfire نمی باشد.

بیاین از رویکرد های ساده شروع کنیم و جلو بریم.

1. در محیط محصول نهایی (Production Environment) از فضای ذخیره سازی پایدار استفاده کن.

ذخیره سازی در حافظه (In-Memory) بی ثابت و غیر قابل اطمینانه و فقط باید برای محیط آزمایش (Test Environment) یا توسعه (Development Environment) استفاده بشه. در محیط محصول نهایی (Production Enviroment)، از یک پایگاه داده پایدار (Persistent storage) مثل SQL Server ، Redis یا PostgreSQL استفاده کنید تا اطمینان حاصل کنید که داده های کسب و کار در راه اندازی مجدد برنامه از بین نمیره.

services.AddHangfire(configuration => configuration
    .UseSqlServerStorage("YourConnectionString"));

1. کارهای پس زمینه را بدون وابستگی مهم و بی قدرت طراحی کن.

#### 

(Design Idempotent and Stateless Jobs)

- بی قدرت باشه؟ (Idempotency)
    

یعنی سعی کنید کارهایی که طراحی میکنید کمترین قدرت رو داشته باشن و قابلیت تکرار شوندگی موقعی که کار به مشکل میخوره و Hangfire میخواد اون رو تکرار کنه داشته باشه، بدون اینکه تکرار اون کار رو دوباره تکرار کنه یا بخواد تاثیر بدی روی سیستم داشته باشه.

مثال میزنم :

فرض کنید که یک سیستم فروشگاهی داریم که تو پس زمینه سفارش کاربرمون رو ثبت و پردازش میکنیم.

Non-Idempotent Implementation:
public void ProcessOrder(int orderId)
{
    var order = _orderService.GetOrderById(orderId);

    // Charge the customer's credit card
    _paymentService.Charge(order.CreditCardInfo, order.Amount);

    // Mark the order as processed
    order.Status = OrderStatus.Processed;
    _orderService.UpdateOrder(order);

    Console.WriteLine($"Order {orderId} processed.");
}

حالا فکر کنید اومدیم و حساب کاربر رو شارژ کردیم و قبل اینکه بتونیم سفارش رو ویرایش کنیم متد به مشکل خورده و fail شده. میپرسی چطوری؟ مثلا خطای شبکه رخ داده. حالا Hangfire میاد و این کارو میزاره تو صف و دوباره پردازش میکنه. حالا ای دل قافل حساب کاربر چندین بار شارژ میشه و تغییر وضعیت میده ولی ما متوجه نمیشیم. راه حل چیه؟

Idempotent Implementation:
public void ProcessOrder(int orderId)
{
     var order = _orderService.GetOrderById(orderId);

    // Check if the order has already been processed
    if (order.Status == OrderStatus.Processed)
    {
       Console.WriteLine($"Order {orderId} has already been processed.");
       return;
    }
    // Charge the customer's credit card
    _paymentService.Charge(order.CreditCardInfo, order.Amount);
   
    // Mark the order as processed
    order.Status = OrderStatus.Processed;
     _orderService.UpdateOrder(order);

    Console.WriteLine($"Order {orderId} processed.");
}

حالا درست شد:) فقط چند تا نکته داره اینجا قبل اینکه بخوایم عملیات شارژ رو انجام بدیم چک میکنیم اگر سفارش پردازش شده بود از شارژ کردن مجدد اون صرف نظر می کنیم. و حالا این کار امنیت اجرای مجدد رو داره و کار ما قابل اطمینان هست.

مسئله بعدی !

- کار وابستگی مهمی نداشته باشه (Stateless Jobs)
    

به این معنی هست که کار ما به وضعیت های داخل مموری (In-Memory) یا دیتا های مشترک (shared data) که ممکنه تحت تاثیر سیستم های دیگه قرار بگیرن وابستگی نداشته باشه؛ تا در صورت از دست رفتن یا تغییر اون دیتاها بتونیم کارمون رو انجام بدیم یا حتی موقع بروز خطا دوباره اون رو انجام بدیم. یعنی کار باید خودکفا (Self-contained) باشه و تنها وابستگی ما باید به مقادیر ورودی و دیتایی که قابل اطمینان (Reliable) باشه.

نکته: از دیتای تازه استفاده کنید: اگر پیاده سازی نیاز به اطلاعاتی داره که اون رو در کش کردید سعی کنید دیتا رو به صورت مجزا از دیتابیستون واکشی کنید و استفاده کنید تا مقیاس پذیری و اطمینان کارتون را بالا ببرید.

برای مثال وابستگی (Dependency) و استفاده از HttpContext در کار ها مشکل ایجاد میکنه به چند دلیل :

کار های پس زمینه با رشته های پس زمینه (Background Threads) کار میکنن و به درخواست Http فعلی ما یا Session State ها دسترسی ندارند. پس اگر اطلاعات درخواست رو داخل کار میخوای میتونی مقادیرت رو به عنوان ورودی (As a Parameter) به اون پاس بدی.

این کارو بکن :

public void SendUserNotification(int userId)
{
    var user = _userService.GetUserById(userId);
    //Logic
}

به جای اینکه اینکارو کنی :

public void SendUserNotification()
{
    int userId = (int)HttpContext.Current.Session["UserId"];
    var user = _userService.GetUserById(userId);
   //Logic
}

با این اقدامات تکرار پذیر بودن (Reentrancy) کارتون رو تضمین میکنید.

هر کار باید فقط و فقط یک مسئولیت تعریف شده و دلیل برای تغییر داشته باشه. با رعایت این اصل ما نگهداری (Maintainability) و خطایابی (Debug) رو برای خودمون و تیممون ساده میکنیم.

- کار های بزرگ رو به کار های کوچیک تر تبدیل کن.
    

اگر میبینی کار بزرگی داری که میتونی اجزای اون رو بدون آسیب و Side effect بشکنی، این کار رو بکن و با قابلیت ادامه دار کردن کارها در Hangfire اون هارو بهم زنجیر کن.

var jobId = BackgroundJob.Enqueue(() => PerformStepOne());
BackgroundJob.ContinueJobWith(jobId, () => PerformStepTwo());

(Handle Exceptions and Implement Retries)

- احیای اتوماتیک رو مدیریت کن (Automatic Retries)
    

پکیج Hangfire به طور پیشفرض کارهای به خطا خورده رو مجدد احیا و تکرار میکنه. بهتره که متناسب با نیازی که اون کار داره و محدودیتی که داریم تعداد احیای اون کار رو تنظیم کنیم چرا که عدم مدیریت درست بار دیتابیس (Database load) رو زیاد میکنه و درخواست هارو کند میکنه.

با تنظیم این مورد میتونی سیستمی با عملکرد (Performance) بهتر داشته باشی.

شما میتونین تعداد اینکار و زمان بین هر احیا رو به این صورت تنظیم کنید.

var options = new BackgroundJobServerOptions { ServerTimeout = TimeSpan.FromMinutes(30), Queues = new[] { "critical", "default", "low" } }; options.SchedulePollingInterval = TimeSpan.FromMinutes(1); 
var server = new BackgroundJobServer(options); 

- به خطاها رسیدگی کنید (Error Handling)
    

حتما مد نظرتون داشته باشین که استثناعات (Exceptions) رو داخل کارهاتون مدیریت کنید تا با یک کار مختل شده با خطای نامعلوم نخورید. تا بتونید به درستی اون ها برطرف کنید و از پیشروی سیستم با روند های ناقص جلوگیری کنید.

app.UseHangfireDashboard("/hangfire", new DashboardOptions
 {

6.استفاده از منابع را بهینه کن (Optimize Resource Usage)

- تعداد کارگر (Worker Count) ها رو مدریت کن
    

به صورت پیشفرض Hangfire یک استخر از کارگر ها (Workers pool) که در زیر سیستم سرور Hangfire (Serveer Subsystem) هست ایجاد میکنه که تعداد 20 کار رو به صورت همزمان (Concurrent) میتونن انجام بده. بسته به نیاز و منابعی که در اختیار دارین میتونین این تعداد رو کم یا زیاد کنید.

توجه کنید که بالا بردن تعداد کارگر ها کارآیی برنامه شما رو افزایش میده اما بار روی سرور شما هم افزایش پیدا میکنه پس یک بالانس بین منابع و کارگر هاتون پیدا کنید.

var options = new BackgroundJobServerOptions { WorkerCount = Environment.ProcessorCount * 5 };
app.UseHangfireServer(options);

- مدیریت بهینه منابع
    

برای جلوگیری از نشت حافظه (Memory Leak) و فرسودگی منابع (Resource exhaustion)، حافظه اشغال شده و منابع دیگر در دست کارتون رو به درستی مدیریت و دفع (Dispose) کنید. برای مثال ورودی های بزرگ (Large payloads/Objects) به کار هاتون ندید چرا که درخواست و بار روی دیتابیس (Database load) زیاد میشه و باعث کندی کار شما میشه.

به جای این کار از ابجکت های کوچیک استفاده کنید مثل Id ها و موارد دیگه که میتونن به شما تو دستیابی به اطلاعات مورد نیازتون کمکتون کنن.

- از دسته ها استفاده کن (Use Batches)
    

فرض کن داری 1000 ایمیل مهم برای کاربر هات ارسال میکنی اگر هر کدوم از اونها به مشکل بخورن چی؟ مجبور میشیم یکبار دیگه ایمیل ارسال کنیم تا مطمئن بشیم به دسته همه برسه تازه اگه برسه. شاید برای بعضی ها چند تا ایمیل بره که خیلی آزار دهندس. اینجا راه حل استفاده از دسته ها (Batches) هست.

BatchJob.StartNew(x =>
{
    for (var i = 0; i < 1000; i++)
        x.Enqueue(() => SendEmail(i));
});

که قابلیت های متعدد دیگه هم دارن که میتونید اون ها رو در پکیج Hangfire.Pro داشته باشید. البته پولیه :/

- بازه بررسی صف ها رو مدیریت کن
    

تعداد کارگر ها Worker ها و فاصله بررسی صف ها (queue polling) مسئله مهمیه که باید به اون توجه کنید به طور پیشفرض تعداد 20 کارگر هر 15 ثانیه یکبار صف ها را بررسی میکنن. بازه کوتاه به معنی پردازش سریع تره اما میتونه بار پایگاه داده رو افزایش بده. پس این تنظیمات رو بسته به حجم کاری که دارین تنظیم کنید.

var options = new BackgroundJobServerOptions { QueuePollInterval = TimeSpan.FromSeconds(15) }; 
var server = new BackgroundJobServer(options);

#### 

(Avoid Long-Running or Blocking Tasks)

- از برنامه نویسی غیر همزمان (Asynchronous Programming) استفاده کن
    

برای آزاد نگه داشتن رشته ها (Threads) از Async/await برای عملیات I/O bound استفاده کنید.

راهنما :

از روش Async برای عملیات محدود به I/O ، مثل درخواست های شبکه ، فایل I/O یا درخواست های پایگاه داده استفاده کنید ،یا به طور کلی جایی که بیشتر وقتمون رو صرف انتظار کشیدن از منابع خارجی می کنیم.

زمانی که میخواین UI رو ریسپانسیو نگهداریم و کاربر رو منتظر پاسخ طولانی عملیاتی نگه ندارین.

و زمانی که میخواین تعداد بیشتری درخواست همزمان (Concurrent) در وب اپلیکیشن (Web Application) رو پاسخ بدین.

حالا چه زمان هایی میتونیم از Sync استفاده کنیم؟

- عملیلیات های Cpu bound که قرار هست یک کار که نیاز به پردازش مداوم دارن چون روش Async در این عملیات ها ارزش افزوده ای ندارن.
    
- جاهایی که درگیر یک سورس قدیمی Legecy هستین و چاره ای ندارین :)
    

نکته : برای به مشکل نخوردن لغو فعایت هایی که موقع از دست رفتن اتصال یا موارد دیگه و بازگردانی دوباره اونها به اون صف از cancellation tokens استفاده کنید. که ThreadabortException رو موقع خاموش کردن برنامه به شدت کاهش میده. همچنین بازه تشخیص لغو درخواست ها قابل تنظیم هست.

services.AddHangfireServer(new BackgroundJobServerOptions
{
    CancellationCheckInterval = TimeSpan.FromSeconds(5) // Default value
});

8.کار های همزمان رو مدیریت کن

- کنترل همزمانی : به معنی مدیریت عملیات هایی هست که از یک منبع داده مشترک بدون مناقشه کردن با هم استفاده میکنند. در Hangfire از این روش استفاده می کنیم تا اطمینان حاصل کنیم که برخی از وظایف باهم همپوشانی (Overlap) ندارند و به داده های متناقض (Inconsistent) یا فاسد رو به رو نباشیم.
    

مثل استفاده از معامله های دیتابیسی (Transactions) یا استفاده از صفت (Attribute) زیر برای کارهامون.

[DisableConcurrentExecution(timeoutInSeconds: 60)]
public void ProcessOrder(int orderId) ...

در مثال بالا DisableConcurrentExecution مثل Mutex و Lock عمل میکنه و از دسترسی همزمان به منابع مشترک جلوگیری میکنه و این اطمینان رو به ما میده که در واحد زمان فقط یک نمونه از کار در حال انجام هست. خوبه برای زمانی که داریم کاره مهمی میکنیم مثلا وضعیت یک فرایندی رو در دیتابیس تغییر میدیم.

نکته : کنترل زمان انجام عملیات ها هم به این موضوع کمک میکنه ما با کنترل حداکثر زمان مورد انتظار برای انجام یک فعالیت (TimeOut) از رسیدن برنامه به بن بست (DeadLock) جلوگیری میکنیم.

- کار های زباله (Throttle Jobs)
    

جلوگیری از کار های زباله روش موثری هست که به ما در مدیریت منابع (Resources) خارجی مثل درخواست های Api، پایگاه داده و ... کمک میکنه و نرخ اجرای کارهامون رو کنترل میکنه.

در Hangfire با استفاده از Hangfire.Throttling میتونیم مباحث پایه ای مثل Mutex و Semaphores و محدودیت در نرخ اجرا (Rate Limiting) رو فراهم کنیم.

بیاین یک سناریو رو بررسی کنیم.

فرض کنید یک Api خارجی رو صدا میزنید که اجازه فقط 10 در خواست در دقیقه را به شما میده. ما با استفاده از Hangfire.Throttling مطمئن میشم که از این محدوده عبور نمیکنیم و کار های بی فایده و زباله رو تولید نمی کنیم.

به صورت ساده میتونیم با اقدامات زیر به هدفمون برسیم:

//add it to host service
services.AddHangfireThrottling();
then
[RateLimit("ApiRateLimiter", 10, 60)] // add this attribute on top of job that limits to 10 requests or times per minute
public async Task CallExternalApiAsync(string endpoint) ...
//and enqueue the job

یا به صورت پیشرفته می تونید با استفاده از اینترفیس IThrottlingManager به کنترل محدودیت تعداد کار های همزمان (Semaphores) یا استراتژی های محدودیت نرخ پاسخگویی (Rate Limiting) بپردازین. یا با استفاده از صفت ها (Attributes) استفاده فقط یک کار (Mutex) از منبع مشترک بین کارها را مدیریت کنید. که برای جزئیات بیشتر به داکیومنت Hnagfire مراجعه کنید. :)

1. مقیاس پذیری Scalability

اگر یک سرور نمی تونه بار کاری شما را تحمل کنه ، با اضافه کردن سرورهای بیشتر (Horizontal Scaling) ، مقیاس پروژه رو بیشتر کنید. Hangfire از پردازش توزیع (distributed processing) شده پشتیبانی می کنه و به چندین سرور اجازه می ده کار هارو از صف ها پردازش کنند. این می تونه توان (throughput) شما رو به میزان قابل توجهی افزایش بده و عملکرد (Performance) را بهبود ببخشه.

همچنین میتونید با اضافه کردن Ram و Cpu پروژه رو مقیاس بندی کنید (Vertical Scaling) که به مراتب هزینه برتر از روش های دیگر هست.

- بازی رو ببر
    

برای برنامه های با بار متغیر ، مقیاس پذیری خودکار می تونه بازی رو ببره. شما می تونید از ابزارهایی مثل Kubernetes استفاده کنید تا به طور خودکار سرورهای Hangfire خودتون رو بر اساس طول صف کار یا سایر معیارها مقیاس بندی کنید. این تضمین می کنه که شما همیشه منابع کافی برای تحمل بار شغلی خودتون رو بدون پیش بینی بیش از حد دارید.

10.با استراتژی صف هات رو مدیریت کن

- بسته به نوع کارت و اهمیتشون اون ها رو با صف ها الویت بندی کن
    

app.UseHangfireServer(new BackgroundJobServerOptions
{

1. تزریق وابستگی کن (Use dependency injection)

برگردیم یاد گذشته کنیم. DI یک الگوی طراحیه که اجازه می ده وابستگی های یک شیء در زمان اجرا تزریق شود ، نه اینکه مستقیم نمونه سازی (Hard-coded) شده باشن. این کار اتصال شل (Loose coupling) را مهیا می کنه و قابلیت آزمایش (Testability) و قابلیت حفظ (Maintainability) کد شما را افزایش می ده. در Hangfire ، استفاده از DI می توki مزایای مختلفی را ارائه بده.

نکته : حواستون به طول عمر (Lifetime) نمونه ها باشه:

خدمات Singleton : استفاده از Singleton Services در کار های Hangfire می تونه در صورتی امنیت اشتراک گذاری (Thread safe) مشکل ساز بشه همون مورد تغییر وضعیت داده یا همزمانی زمان در دسترسی به منبع.

خدمات Scoped: مدیریت طول عمر Scoped Services می تونه مشکل ساز باشه ، به خصوص هنگام برخورد با کار های پس زمینه که دارای طول عمر متفاوتی نسبت به درخواست های وب هستن.

برای رفع مشکلات Injection هم مواردی هست که میتونید لحاظ کنید مثلا مدیریت دستی scop ها (IServiceProvider) یا استفاده از Activator Hangfire برای تزریق وابستگی در کار ها و البته خدمات Transient Services برای دسترسی به داده های تازه ترجیح داده میشن.

1. از فیلتر کار ها (Using Job Filters)

همه فرآیندها با الگوی زنجیره ای از مسئولیت (Chain of resposibility) پیاده سازی شده و می تونید مثل Action Filter ها کار هارو رهگیری (intercept) کنید.

برای فیلترهای شغلی از موارد استفاده کنید

عملیات لاگ Logging : میتواند کار ها رو در مراحل مختلف پیگیری کنید.

عملیات احیا Retry : منطق و استراتژی های احیای کار های خطا خورده رو پیاده سازی کنید.

نظارت بر عملکرد Performance Monitoring: اندازه گیری زمان اجرای شغل و معیارهای عملکرد کارو داشته باشید.

امنیت Security : برای اطمینان از دسترسی مجاز ، قبل از اجرای مشاغل ، بررسی های امنیتی رو اجرا کنید.

اعلان Notification: اعلان ها یا هشدارها را بر اساس وضعیت اجرای شغل یا تغییرات ارسال کنید.

  

نکته: Hangfire رو اپدیت نگهدارید در ورژن های جدیدتر بسیاری از مشکلات حل میشن از جمله همین مورد که حل شده.

  

### 

1. لامپارو خاموش کن

### 

(Graceful Shutdown)

خاموش کردن برنامه در ASP.NET CORE تضمین می کنه که برنامه کاربردی را به طور هموار متوقف می کند و به کارهای در حال پیشرفت (In-progress Tasks) اجازه می ده تا منابع را به درستی تکمیل و آزاد کنن. این امر به ویژه برای سیستم های پردازش کارهای پس زمینه مثل Hangfire بسیار مهمه ، جایی که برای جلوگیری از ناسازگاری داده ها (Inconsistencies) یا کارهای ناقص (Incomplete Tasks)، باید کارهای در حال اجرا به پایان برسند.

خاموشی ...

از Ihostapplicationlifetime استفاده کنید. رابط IhostapplicationLifetime امکان انجام اقداماتی رو موقع شروع و خاموش شدن برنامه برامون فراهم می کنه. حالا به صورت کلی (Global) میتونیم بگیم که Hangfire عزیز شما هم درخواست های درحال اجرات رو انجام بده و درخواست جدیدی هم قبول نکن.

و حالا برنامه ما امادس تا خاموش بشه :)

someCodepublic void Configure(IApplicationBuilder app, IWebHostEnvironment env, IHostApplicationLifetime applicationLifetime)
{
    applicationLifetime.ApplicationStopping.Register(() =>
    {
        // Signal Hangfire to stop accepting new jobs and wait for ongoing jobs to complete
        GlobalJobFilters.Filters.Add(new AutomaticRetryAttribute { Attempts = 0 }); // Disable retries

        // Wait for Hangfire to complete ongoing jobs
        var cancellationToken = new CancellationTokenSource(TimeSpan.FromSeconds(30)).Token; // 30 seconds timeout
        using (var server = new BackgroundJobServer())
        {
            server.WaitForShutdownAsync(cancellationToken);
        }
        //Hangfire server stopped gracefully. :))
    });
}
