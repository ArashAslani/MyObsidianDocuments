command :به دستوراتی در سیستم گفته میشوند که قرار هست یک state رو تغییر میدن. ایجاد میکنند اپدیت میکنند و ...
Query : اطلاعات را واکشی میکنند.

در این الگو باید Command ها و Query ها از هم جدا شوند. و هر کدام مدل مختص به خود را دارند.
به دلیل اینکه حجم فایل ها در این الگو زیاد هست و پیچیده گی زیادی داریم برای کم کردن پیچیدگی از الگوی مدیاتور mediator استفاده میکنیم.

![[Pasted image 20240311165026.png]]

استفاده از این الگو باعث میشود تا توسعه پذیری و تغییرات طبق اصل SRP بهتر شوند.
بسته به نیاز بیزنس میتوان الگو CQRS را در سطح دیتابیس را نیز رعایت کرد. یعنی یک دیتایبس برای Command و یک دیتابیس برای Query داشته باشیم تا هم سرعت بهتری داشته باشیم و هم کشینگ راحت تر اتفاق بیوفتد.

MediatR به سه قسمت کلی Request , Response و pipeline و Notifications ها تقسیم میشوند.
Request, Response برای پیاده سازی Command , Query های ما هستند.
Notification برای Domain Events هستند.
Pipelines مانند Middleware ها هستند که قبل و بعد درخواست اجرا میشوند.

در لایه Application نصب و استفاده میشوند.
برای هر Use case باید یک کلاس مجزا داشته باشیم.
برای اینکه command ها و query ها در یک لایه انجام شوند.
بهتر هست که Repository های مجزایی در لایه Domain داشته باشیم.

در لایه Presentation فقط MedaitR صدا میشود و کامند ها به ان پاس داده میشوند.
در لایه Config به وسیله DI و نصب پکیج مورد نیاز آن را به پروژه اضافه میکنیم

در لایه application برای هر command میتوانیم یک validation مجزا با استفاده از Fluent Validation در نظر بگیریم.

که با استفاده از PipelineBehaviors میتوانیم Validation هارا از دل Handler بیرون کشیده و به اصل SRP نزدیک تر شویم.
