# SQL Server: In-Memory OLTP و Temporal Table (و ارتباط با EF)

## 1. Interview Relevance Summary

این فایل دو قابلیت **SQL Server** را پوشش می‌دهد که در مصاحبهٔ Backend برای **پرفرمنس** و **ثبت سوابق تغییرات** مطرح می‌شوند: **In-Memory OLTP** و **Temporal Table**. مصاحبه‌گران انتظار دارند بتوانی:

- بگویی **چرا** به‌جای بهینه‌سازی کوئری روی جدول معمولی، گاهی به In-Memory یا کش جدا فکر می‌کنی و **trade-off** (حافظه، دوام، پیچیدگی عملیاتی) را در نظر بگیری.
- برای **آدیت و تاریخچهٔ تغییرات** روش‌های مختلف (Trigger، CDC، جدول تاریخچه دستی، Temporal) را بشناسی و بگویی **کی کدام** مناسب است و Temporal چه مزیت و چه محدودیتی دارد.
- رابطهٔ این قابلیت‌ها با **EF Core** را بدانی: پشتیبانی مستقیم برای Temporal (از نسخهٔ ۶)، و برای In-Memory معمولاً استفادهٔ مستقیم از SQL یا سناریوی ترکیبی.

در سطح Senior نباید فقط نام قابلیت را بدانی؛ باید **چه زمانی استفاده کنی**، **چه زمانی استفاده نکنی** و **چه خطاهایی رایج است** را بتوانی توضیح دهی.

## 2. In-Memory OLTP

### چرا وجود دارد؟

در بار **OLTP** بالا، **قفل و Latch** روی جدول‌های معمولی باعث **Contention** و **تأخیر** می‌شود. In-Memory OLTP با قرار دادن داده در **RAM** و حذف Lock/Latch به‌صورت سنتی، **Latency** و زمان اجرا را کم می‌کند و برای سناریوهای با تراکنش بسیار زیاد و رقابت بالا طراحی شده است.

### ویژگی‌های اصلی

- **Memory-Optimized Table**: داده در حافظه؛ ساختار بهینه‌شده برای دسترسی سریع.
- **Lock-Free / Latch-Free**: الگوریتم‌های بدون قفل برای کاهش Contention.
- **Durability (دوام)**: می‌توانی انتخاب کنی:
  - **SCHEMA_AND_DATA**: هم طرح جدول هم داده روی دیسک persist می‌شود (پس از ریست، داده باقی می‌ماند).
  - **SCHEMA_ONLY**: فقط طرح جدول روی دیسک است؛ داده با ریست از بین می‌رود — برای دادهٔ موقت (مثلاً session یا صف موقت) مناسب است.
- **Logging**: برای جداول با دوام کامل، لاگ نوشته می‌شود ولی معمولاً سبک‌تر از جدول دیسکی است.

جداول معمولی در **Buffer Pool** از دیسک به RAM می‌آیند و با **Checkpoint** به دیسک برمی‌گردند. جداول Memory-Optimized خارج از Buffer Pool و مستقیماً در فضای مخصوص خود در حافظه نگه داشته می‌شوند.

### نحوهٔ استفاده (خلاصهٔ گام‌ها)

۱. **File Group** با نوع **MEMORY_OPTIMIZED_DATA** برای دیتابیس تعریف کن.  
۲. **جدول Memory-Optimized** روی این File Group بساز (سینتکس و محدودیت‌های خاص خودش را دارد).  
۳. برای حداکثر سرعت روی این جدول‌ها می‌توانی **Natively Compiled Stored Procedure** بنویسی که به کد ماشین کامپایل می‌شود و زیرمجموعهٔ T-SQL را پشتیبانی می‌کند (نه هر دستور دلخواه).

ساختار فایل‌ها شامل **Metadata**، **Data File** (رکوردهای درج‌شده)، **Delta File** (رکوردهای حذف‌شده) و **Log** است.

### محدودیت‌ها و trade-offها

- **حافظه**: همهٔ دادهٔ جدول در RAM است؛ حجم زیاد یعنی RAM زیاد و هزینهٔ سخت‌افزار.
- **Natively Compiled SP**: فقط بخشی از T-SQL پشتیبانی می‌شود (مثلاً بدون JOINهای پیچیدهٔ دلخواه یا توابع خاص). برای منطق ساده و پرتکرار عالی است؛ برای کوئری‌های پیچیده ممکن است مجبور باشی از SP معمولی (interpreted) استفاده کنی که روی همان جدول در حافظه کار می‌کنند ولی به‌سرعت Natively Compiled نیستند.
- **قابلیت‌های جدول**: در نسخه‌های اولیه محدودیت‌هایی مثل LOB (مثلاً NVARCHAR(MAX)) و بعضی نوع‌ها وجود داشت؛ بسته به نسخهٔ SQL Server مستندات را چک کن.
- **ارتباط با EF Core**: EF Core به‌صورت پیش‌فرض **جداول Memory-Optimized** را مثل جدول عادی مپ می‌کند و از مزایای دسترسی مستقیم به ساختار در حافظه یا Natively Compiled SP استفاده نمی‌کند. برای بهرهٔ واقعی از In-Memory OLTP معمولاً از **raw SQL**، **Stored Procedure** یا دسترسی جدا (مثلاً برای یک بخش خاص از اپلیکیشن) استفاده می‌کنی؛ نه لزوماً از DbSet و LINQ روی همان جدول به‌عنوان مسیر اصلی.

### کی مناسب است؟ کی خطرناک است؟

- **مناسب**: جدول با بار خواندن/نوشتن بسیار بالا و رقابت زیاد (مثلاً session، نرخ‌سنجی، جدول lookup داغ) که در صورت نیاز با دوام SCHEMA_AND_DATA یا با ریسک از دست رفتن با SCHEMA_ONLY قابل قبول است.
- **خطرناک**: قرار دادن دادهٔ بحرانی و پایدار فقط در جدول با **SCHEMA_ONLY** بدون مکانیزم جایگزین (replication یا بازیابی)؛ یا استفادهٔ بی‌رویه برای همهٔ جدول‌ها بدون توجه به هزینهٔ RAM و عملیات.

## 3. Temporal Table (جدول زمانی) — از SQL Server 2016

### چرا وجود دارد؟

برای **ثبت خودکار تاریخچهٔ تغییرات** هر رکورد (چه زمانی چه مقداری داشته و چه زمانی عوض یا حذف شده) بدون اینکه خودت با Trigger یا جدول تاریخچهٔ دستی این کار را بکنی. با **TempDB** (فضای موقت) فرق دارد؛ اینجا تاریخچهٔ **دائمی** خود جدول در یک **History Table** جدا ذخیره می‌شود.

### روش‌های دیگر ثبت تاریخچه (و محدودیت‌ها)

| روش | محدودیت یا هزینه |
|-----|-------------------|
| **جدول تاریخچهٔ دستی** | با رشد داده، فیلتر و ایندکس سنگین؛ منطق درج/آپدیت در اپلیکیشن یا SP. |
| **Trigger** | Overhead روی هر تراکنش؛ با تعداد کاربر و تراکنش زیاد می‌تواند کندی ایجاد کند. |
| **CDC (Change Data Capture)** | قوی برای ETL و replication؛ نیاز به نگه‌داری و تخصص؛ جدا از ساختار جدول اصلی. |
| **ثبت در اپلیکیشن + NoSQL** | اگر کسی مستقیم روی SQL تغییر بده، نسخه‌ها با دیتابیس اصلی هماهنگ نمی‌مانند. |

**Temporal Table** این را در خود موتور حل می‌کند: هر **UPDATE** یا **DELETE** به‌صورت خودکار نسخهٔ قبلی را در **History Table** ذخیره می‌کند و **زمان شروع و پایان** اعتبار هر نسخه ثبت می‌شود.

### کاربردها

- **Time Travel**: دیدن وضعیت جدول در یک زمان مشخص.
- **Data Audit / Compliance**: چه کسی چه زمانی چه چیزی را عوض کرده است.
- **Slowly Changing Dimensions** در انبار داده.
- **بازیابی رکورد خراب** در سطح رکورد (بازگرداندن به حالت یک زمان گذشته).

### پیکربندی (خلاصه)

جدول اصلی دو ستون **period** دارد با نوع **datetime2** که توسط سیستم پر می‌شوند (مثلاً `SysStartTime`, `SysEndTime` یا نام‌های دلخواه با `GENERATED ALWAYS AS ROW START/END`). یک **History Table** به آن وصل می‌شود و با **SYSTEM_VERSIONING = ON** هر تغییر خودکار در تاریخچه ثبت می‌شود.

### کوئری روی تاریخچه

با **FOR SYSTEM_TIME** می‌توانی بر اساس زمان کوئری بزنی:

- **AS OF** '2024-01-15 10:00': وضعیت جدول در آن لحظه.
- **FROM ... TO**, **BETWEEN ... AND**, **CONTAINED IN**: بازهٔ زمانی.

این کوئری‌ها روی جدول فعلی و جدول تاریخچه با هم کار می‌کنند. برای کارایی، روی ستون‌های زمانی جدول تاریخچه **ایندکس** بگذار؛ وگرنه کوئری‌های Time Travel روی حجم زیاد کند می‌شوند.

### رشد تاریخچه و Retention

جدول تاریخچه با هر UPDATE/DELETE رشد می‌کند. اگر **سیاست پاک‌سازی (retention)** نداشته باشی، حجم و زمان پشتیبان‌گیری زیاد می‌شود. از نسخهٔ ۲۰۱۷ به بعد می‌توانی **Temporal History Retention** تنظیم کنی تا دادهٔ قدیمی‌تر از یک بازهٔ مشخص خودکار حذف شود؛ وگرنه باید با job دوره‌ای خودت پاک‌سازی کنی.

### Index Rebuild

وقتی روی جدول اصلی **Index Rebuild** انجام می‌دهی، در برخی سناریوها یا با برخی تنظیمات، **جدول تاریخچه** هم تحت تأثیر قرار می‌گیرد یا باید جداگانه نگه‌داری و ایندکس آن را در نظر بگیری. مستندات نسخهٔ خودت را چک کن.

### ارتباط با EF Core

از **EF Core 6** پشتیبانی **Temporal** اضافه شده است: می‌توانی جدول را به‌عنوان Temporal تنظیم کنی و با متدهای مخصوص (مثلاً کوئری برای یک نقطهٔ زمانی) از همان مدل استفاده کنی. برای نسخه‌های قدیمی‌تر یا کوئری‌های پیشرفتهٔ FOR SYSTEM_TIME از **FromSqlRaw** یا کوئری خام استفاده می‌کنی.

### اشتباهات رایج

- **نداشتن ایندکس روی جدول تاریخچه** روی ستون‌های زمانی → کوئری‌های Time Travel کند.
- **فراموش کردن Retention** → رشد بی‌رویهٔ تاریخچه و افزایش حجم و هزینهٔ بکاپ.
- **فرض اینکه هر تغییری از طریق اپلیکیشن است**: تغییر مستقیم روی دیتابیس هم در تاریخچه ثبت می‌شود؛ پس طراحی و دسترسی را در نظر بگیر.

## 4. Key Interview Talking Points

- **In-Memory OLTP**: برای کاهش Contention و Latency؛ Lock/Latch-Free؛ دوام SCHEMA_AND_DATA یا SCHEMA_ONLY؛ Natively Compiled SP برای منطق ساده و پرتکرار؛ محدودیت T-SQL و هزینهٔ RAM؛ با EF معمولاً از raw SQL یا SP استفاده می‌شود.
- **Temporal Table**: ثبت خودکار تاریخچه با period columns و History Table؛ FOR SYSTEM_TIME برای Time Travel و Audit؛ رشد تاریخچه و نیاز به Retention و ایندکس روی تاریخچه؛ پشتیبانی EF Core 6+.
- **انتخاب روش آدیت**: Trigger (ساده ولی overhead)، CDC (قوی برای ETL)، Temporal (یکپارچه با جدول و مناسب Audit و بازیابی رکورد).

## 5. Common Mistakes & Red Flags

- گفتن اینکه «EF به‌طور کامل از In-Memory پشتیبانی می‌کند» — پشتیبانی معمول برای دسترسی به جدول هست ولی بهرهٔ واقعی از Natively Compiled و الگوی درست با raw SQL/SP است.
- استفاده از **SCHEMA_ONLY** برای دادهٔ بحرانی بدون جایگزین.
- **Temporal** بدون **Retention** و بدون **ایندکس روی تاریخچه** → حجم و کوئری کند.
- استفادهٔ بی‌رویه از In-Memory برای همهٔ جدول‌ها بدون سنجش هزینهٔ RAM و عملیاتی.

## 6. When to Use / When NOT to Use

**In-Memory OLTP**

- **استفاده**: بار تراکنش بسیار بالا روی یک یا چند جدول مشخص؛ session، rate limiting، lookup داغ؛ وقتی Latency و Contention مشکل اصلی است و RAM و عملیات قابل قبول است.
- **عدم استفاده**: به‌عنوان جایگزین ساده برای «همهٔ دیتابیس سریع‌تر شود» بدون تحلیل؛ برای دادهٔ بحرانی با SCHEMA_ONLY بدون طرح بازیابی.

**Temporal Table**

- **استفاده**: نیاز به Audit، Time Travel، یا بازیابی رکورد به حالت گذشته؛ ترجیح یکپارچه با موتور به‌جای Trigger یا جدول دستی.
- **عدم استفاده**: وقتی فقط لاگ سادهٔ «چه کسی لاگین کرد» کافی است و نیازی به نسخه‌گذاری هر تغییر رکورد نیست؛ یا وقتی نمی‌توانی Retention و حجم تاریخچه را مدیریت کنی.
