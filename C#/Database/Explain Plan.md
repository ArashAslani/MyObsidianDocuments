# ذخیره‌سازی داده و Execution Plan در SQL Server

## 1. Interview Relevance Summary

این فایل دو موضوع رو پوشش می‌ده: **نحوهٔ ذخیره‌سازی داده** (Page، Extent، Heap در برابر Clustered/Nonclustered) و **مراحل اجرای کوئری** تا رسیدن به **Execution Plan**. برای مصاحبهٔ Backend مفیده بدونیش داده چطور توی صفحه‌های ۸KB ذخیره می‌شه، چرا Heap برای OLTP معمولاً بد است، و Plan چطور ساخته می‌شه (Parsing → Algebrizer → Optimizer → Plan Cache). برای تیونینگ عملی به **[[Tuning Database]]** مراجعه کن.

---

## 2. ذخیره‌سازی داده: Page و Extent

SQL Server داده رو روی دیسک داخل **Page** ذخیره می‌کنه. هر **Page** یه بستهٔ **۸KB** است و داده داخل همین بسته‌ها قرار می‌گیره.

![[Pasted image 20240423210602.png]]

ساختار هر Page شامل **Page Header** (مثلاً آدرس صفحهٔ بعد/قبل)، **Row Offset**، و **فضای آزاد** است. فضای قابل استفاده برای داده در هر صفحه حدود **۸۰۸۶ بایت** است. در طراحی جدول بهتره به این اندازه توجه کنی تا استفاده از فضا بهینه باشه.

**Extent** = **۸ صفحهٔ ۸KB** کنار هم = **۶۴KB**. SQL Server به‌جای اختصاص یکی‌یکی صفحه، معمولاً یک Extent به جدول می‌ده. علاوه بر Data Page، صفحه‌های سیستمی مثل **IAM**، **GAM** و غیره هم وجود دارن.

## 3. Heap در برابر Clustered و Nonclustered Index

### Heap

جدولی که **Clustered Index** نداره **Heap** است. رکوردها ترتیب فیزیکی/منطقی خاصی ندارن؛ وقتی `SELECT` می‌زنی موتور مجبوره **کل جدول** رو اسکن کنه تا رکورد موردنظر رو پیدا کنه. برای OLTP معمولاً نمی‌خوایم جدول Heap داشته باشیم.

### Clustered Index

با ایجاد **Clustered Index** (مثلاً روی Primary Key)، SQL Server رکوردهای جدول رو **فیزیکی** بر اساس کلید ایندکس مرتب می‌کنه (مثل صفحات کتاب پشت‌سرهم). به‌همین دلیل **فقط یک** Clustered Index per table داریم. واکشی بر اساس آن کلید سریع‌تر می‌شه.

### Nonclustered Index

مثل **ایندکس آخر کتاب**: کلید (مثلاً کد ملی یا ایمیل) به **آدرس رکورد** در جدول نگاشت می‌شه. یعنی یه چینش **منطقی** بر اساس ستون‌های ایندکس در فضای جدا (مثلاً B-tree) ساخته می‌شه و با کلید به جدول اصلی bind می‌شه. می‌تونی چند Nonclustered Index داشته باشی.

## 5. ترتیب منطقی اجرای کوئری (Logical Query Processing)

ترتیب **منطقی** (نه لزوماً فیزیکی) اجرا معمولاً این است:

1. **FROM** — واکشی از منبع (مثلاً جدول از حافظه/دیسک)
2. **WHERE** — فیلتر (CPU)
3. **GROUP BY** — گروه‌بندی (CPU)
4. **HAVING** — فیلتر روی گروه‌ها (CPU)
5. **SELECT** — انتخاب ستون‌ها (CPU)
6. **DISTINCT** — حذف تکراری (CPU)
7. **ORDER BY** — مرتب‌سازی (CPU)

موتور می‌تونه برای بهینه‌سازی ترتیب **فیزیکی** رو عوض کنه، ولی نتیجه باید معادل این ترتیب منطقی باشه.

## 6. مراحل اجرای کوئری تا ساخت Plan

### ۱. Parsing

بررسی **سینتکس** کوئری؛ در صورت درست بودن یه **Parse Tree** ساخته می‌شه.

![[Pasted image 20240423233744.png]]

### ۲. Algebrizer

بررسی **معنایی**: جدول و ستون‌ها معتبرن؟ دیتابیس و صفحه‌ها کجان؟ در این مرحله دیتابیس و پارتیشن شناسایی می‌شن و بعداً جدول به حافظه می‌آد. یه **Hash** برای کوئری تولید می‌شه و **Query Processor Tree** ساخته می‌شه.

![[Pasted image 20240423233922.png]]

### ۳. Query Optimizer

بهینه‌ساز چند **Plan** ممکن رو در نظر می‌گیره و **Cost** (ترکیب CPU و I/O) رو تخمین می‌زنه و **کم‌هزینه‌ترین** رو انتخاب می‌کنه. اگه برای همین کوئری (با همون hash) از قبل **Plan** توی **Plan Cache** ذخیره شده باشه، این مرحله دوباره اجرا نمی‌شه و از همون Plan استفاده می‌شه. Plan Cache بخشی از حافظهٔ SQL Server است.

معیارهای انتخاب Plan: ایندکسهای قابل استفاده، ترتیب Joinها، هزینهٔ هر بخش، تأثیر Constraintها، و برای هر **ORDER BY** یک اپراتور **Sort**.

![[Pasted image 20240423235126.png]]
![[Pasted image 20240423235324.png]]

### علت‌های معمول کندی کوئری

- سرعت واکشی داده (**Disk I/O**)
- تعداد و سرعت **CPU**
- مقدار **حافظه**
- **شبکه**
- **کوئری‌نویسی نامناسب** یا ایندکس نامناسب

اول جداول، کوئری و ایندکس رو بررسی کن؛ بعد در صورت نیاز سخت‌افزار. **Statistics** برای تخمین بهتر بهینه‌ساز استفاده می‌شه. کوئری داینامیک داخل SP که هر بار با پارامترهای مختلف صدا زده می‌شه، ممکنه با Plan قبلی (مثلاً برای پارامتر دیگه) اجرا بشه و **Parameter Sniffing** یا انتخاب Plan نامناسب پیش بیاد.

## 7. Execution Plan (نقشهٔ اجرا)

**Execution Plan** نقشهٔ **فیزیکی** اجرای کوئری است: چه اپراتوری با چه ترتیبی انجام می‌شه. ساخت Plan یه **سربار** (مثلاً ۱ تا ۲ ثانیه) داره؛ به‌همین دلیل ترجیح بر استفاده از Planهای قبلی در **Plan Cache** است.

### سه نوع نمایش Plan

![[Pasted image 20240424001637.png]]

1. **Estimated Execution Plan**: کوئری **اجرا نمی‌شه**؛ فقط Cost بر اساس I/O و CPU **تخمین** زده می‌شه و ترتیب تخمینی اجرا نشون داده می‌شه. همیشه با واقعیت یکی نیست.
2. **Actual Execution Plan**: **بعد از اجرا** ساخته می‌شه؛ نقشهٔ واقعی و هزینهٔ واقعی اجرا.
3. **Live Query Statistics**: روند اجرای کوئری **در لحظه** (چند رکورد تا الان پردازش شده و غیره).

![[Pasted image 20240424002142.png]]

### نحوهٔ نمایش

- **متنی**: `SET STATISTICS PROFILE ON` — از پایین به بالا خوانده می‌شن.
- **XML**: `SET STATISTICS XML ON`
- **گرافیکی**: در SSMS

### اجزای Plan

از **سمت راست** به چپ خوانده می‌شن. ضخامت خطوط معمولاً نشان‌دهندهٔ **حجم داده**ای است که بین اپراتورها جریان داره. هر اپراتور (مثلاً **Nested Loop** برای Join) یه بخش از کار رو انجام می‌ده و **Cost** و سربارش زیرش نشون داده می‌شه. رنگ اپراتورها هم معنی دارن (هشدار، موازی و غیره).

## 8. Key Interview Talking Points

- **Page** = ۸KB؛ **Extent** = ۸ صفحه؛ داده توی Page ذخیره می‌شه.
- **Heap** = بدون Clustered Index؛ اسکن کامل؛ در OLTP معمولاً نامناسب. **Clustered** = یک per table، چینش فیزیکی. **Nonclustered** = چینش منطقی، چند تا مجاز.
- **مراحل**: Parsing → Algebrizer → Optimizer → Plan Cache → اجرا. Plan با کم‌ترین Cost انتخاب می‌شه.
- **Estimated vs Actual Plan**: یکی قبل از اجرا (تخمین)، یکی بعد از اجرا (واقعی).
