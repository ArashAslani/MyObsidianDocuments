# تیونینگ دیتابیس (SQL Server)

## 1. Interview Relevance Summary

تیونینگ و تشخیص کندی دیتابیس برای **Backend/Senior** که با SQL Server کار می‌کنن مهمه. تو مصاحبه ممکنه انتظار داشته باشن:

- بدونی **Heap** چیه و چرا توی OLTP معمولاً نباید جدول Heap داشته باشی
- با **SET STATISTICS IO** و **Execution Plan** آشنا باشی و بتونی بگی کجا bottleneck است
- **Scan** در برابر **Seek** رو بشناسی و رابطه‌اش با ایندکس رو بدونی
- برای پیدا کردن کوئری‌های در حال اجرا و کندی از **DMV**ها (مثل `sys.dm_exec_requests`) استفاده کنی
- **TempDB** و **Contention** (PFS, GAM, SGAM) رو در حد لازم بدونی و بدونی چطور با چند data file می‌شه فشار رو کم کرد

این فایل روی SQL Server متمرکزه. برای مفاهیم کلی ایندکس و طراحی به **[[Database]]** مراجعه کن.

---

## 2. Heap در برابر Clustered Index

**جدول Heap** یعنی جدولی که **Clustered Index** نداره. داده به‌ترتیب فیزیکی خاصی ذخیره نمی‌شه و برای واکشی موتور مجبوره کل جدول رو اسکن کنه (یا از non-clustered index استفاده کنه که خودش هزینه داره).

- **توی سیستم‌های OLTP** معمولاً جداول رو Heap نمی‌ذاریم؛ چون واکشی و جستجو بدون clustered index گرون‌تر می‌شه.
- **سرعت INSERT** توی Heap می‌تونه بیشتر باشه (چون نیازی به نگه‌داری ترتیب ایندکس نیست)، ولی برای خواندن و کوئری‌های معمول OLTP این مزیت جبران نمی‌کنه.
- جداول به‌طور پیش‌فرض با **Primary Key** اغلب به‌صورت **Unique Clustered Index** در نظر گرفته می‌شن؛ این همیشه بهترین انتخاب نیست و بسته به الگوی دسترسی و کوئری‌ها گاهی کلید دیگری برای clustered مناسب‌تره.

### پیدا کردن جداول Heap

```sql
SELECT OBJECT_NAME(object_id) AS TableName
FROM sys.indexes
WHERE type_desc = 'HEAP';
```

(ستون `type_desc` در `sys.indexes` نوع ایندکس رو نشون می‌ده.)

## 3. بررسی I/O کوئری (SET STATISTICS IO)

برای دیدن اینکه یه کوئری چقدر **خواندن** از حافظه/دیسک انجام داده، اول آمار I/O رو روشن می‌کنی:

```sql
SET STATISTICS IO ON;
-- کوئری موردنظر
SET STATISTICS IO OFF;
```

خروجی چی می‌گه:

- **logical reads**: تعداد **صفحه**هایی (هر صفحه معمولاً ۸KB) که از **buffer pool** (رم) خونده شدن و به CPU دادن برای پردازش. هر چه بیشتر، یعنی کار بیشتر روی حافظه و احتمالاً کوئری سنگین‌تر.
- **physical reads**: تعداد صفحه‌هایی که برای همین اجرا از **دیسک** به حافظه اومدن. اگه صفر باشه یعنی همهٔ داده قبلاً توی buffer بوده.
- **read-ahead reads**: صفحه‌هایی که به‌صورت پیش‌خوانی (read-ahead) از دیسک اومدن. عدد زیاد می‌تونه یعنی بار خواندن از دیسک زیاد است.
- **lob logical reads**: مربوط به خواندن **اشیای بزرگ** (LOB). اگه روی ستون‌های بزرگ عملیات زیاد داری، این عدد بالا می‌ره.

با این اعداد می‌تونی ببینی کوئری چقدر از حافظه/دیسک استفاده می‌کنه و بعد از بهینه‌سازی دوباره مقایسه کنی.

### پاک کردن cache (فقط برای تست)

برای تست تأثیر واقعی بدون cache، در محیط **تست** می‌تونی بافر و پلن کش رو خالی کنی. **توی production انجام نده.**

```sql
DBCC DROPCLEANBUFFERS;   -- پاک کردن بافرهای تمیز
DBCC FREEPROCCACHE;      -- پاک کردن cache پلن‌های اجرا
```

## 4. Execution Plan و Cost

**Execution Plan** نقشهٔ اجرای فیزیکی کوئری است: موتور چطور جدول‌ها رو می‌خونه، ایندکس استفاده می‌کنه، Join می‌زنه و غیره. **Cost** یه عدد نسبی است که ترکیب **CPU** و **I/O** رو نشون می‌ده؛ عملیاتی که **بیشترین Cost** رو دارن معمولاً اولویت بهینه‌سازی هستن. آیکون زرد به‌معنی **اجرای موازی** (parallel) است.

### Scan در برابر Seek

- **Scan** (Table Scan, Clustered Index Scan, Nonclustered Index Scan): یعنی **همهٔ صفحه‌های مربوط** بررسی می‌شن؛ ایندکس برای محدود کردن محدوده استفاده نشده (یا اصلاً ایندکس مناسبی نیست). روی جدول بزرگ معمولاً گرون است.
- **Seek** (Clustered Index Seek, Nonclustered Index Seek): یعنی موتور از **ساختار ایندکس (مثلاً B-tree)** استفاده کرده و با سطح کمتری از بررسی به نتیجه رسیده. معمولاً **Seek بهتر از Scan** است؛ و **Clustered Index Seek** اغلب از Nonclustered Index Seek بهینه‌تره چون بعد از seek دیگه نیازی به مراجعهٔ اضافه به جدول اصلی نیست (اگه همهٔ ستون‌های موردنیاز توی clustered index باشن).

Scan وقتی زیاد دیده می‌شه که یا ایندکس مناسبی نیست، یا کوئری طوری است که موتور مجبور به اسکن است؛ یا حجم داده کمه و موتور اسکن رو انتخاب می‌کنه. **Hash Match** توی پلن معمولاً به‌معنی **Join** است (مثلاً Hash Join).

برای فهم دقیق‌تر ترتیب منطقی اجرا، مبحث **Logical Query Processing** رو مطالعه کن.

## 5. Connection و پیدا کردن کندی و کوئری در حال اجرا

هر اتصال (connection) از client به سرور یه **session** داره و یه **SPID** (Session Process ID) می‌گیره. اتصال‌های کاربری معمولاً SPID بالای ۵۱ هستن (عددهای پایین‌تر اغلب سیستمی هستن).

### مشاهدهٔ sessionها و کوئری در حال اجرا

- **sp_who** / **sp_who2**: نشون دادن sessionها و وضعیت. این‌ها **legacy** هستن؛ برای کار جدی بهتره از **DMV**ها استفاده کنی.
- **sys.dm_exec_connections**: اتصال‌های فعال (غیر سیستمی). هر پنجرهٔ Query معمولاً یه connection باز می‌کنه.
- **most_recent_sql_handle**: هندل کوئری در حال اجرا برای اون connection. با این handle می‌تونی متن و پلن کوئری رو بگیری.

متن کوئری و پلن از روی handle:

```sql
SELECT * FROM sys.dm_exec_sql_text(sql_handle);
SELECT * FROM sys.dm_exec_query_plan(plan_handle);
```

لیست درخواست‌های در حال اجرا به‌همراه متن کوئری:

```sql
SELECT req.*, dm_est.text
FROM sys.dm_exec_requests req
CROSS APPLY sys.dm_exec_sql_text(req.sql_handle) dm_est;
```

- **sys.sysprocesses**: دید قدیمی‌تر روی processها؛ برای نگاه دقیق‌تر هنوز استفاده می‌شه ولی DMVهای جدیدتر ترجیح دارن.
- **Wait**: هر چیزی که باعث بشه در حین اجرای کوئری عملیات **متوقف** بشه (مثلاً منتظر I/O یا Lock). **LastWaitType** نوع wait رو نشون می‌ده. همهٔ کوئری‌ها تا حدی wait دارن؛ باید ببینی کدوم waitها غیرعادی زیادن.
- **آخرین دستور ارسالی برای یه session** (مثلاً SPID 53):

```sql
DBCC INPUTBUFFER(53);
```

**@@SPID** سشن فعلی خودت رو برمی‌گردونه.

### ابزارهای جمع‌آوری رویداد

- **SQL Server Profiler**: برای trace کردن رویدادها استفاده می‌شه؛ در نسخه‌های جدید **deprecated** است و **Extended Events** جایگزینش است.
- **Extended Events**: روش فعلی و سبک‌تر برای جمع‌آوری رویدادها و تحلیل عملکرد.

اگه کوئری حین اجرا **Kill** بشه، در آمار به‌عنوان «کامل‌شده» حساب نمی‌شه. برای دیدن traceهای فعال: `SELECT * FROM sys.traces`.

## 6. OLTP در برابر Data Warehouse

- **OLTP**: تراکنش‌های زیاد و معمولاً کوتاه؛ درخواست‌های کوچک با حجم بالا. کندی اغلب به‌خاطر **تعداد زیاد درخواست**، lock، یا کوئری‌های بی‌رویه است.
- **Data Warehouse**: بار گزارش‌گیری و کوئری‌های سنگین روی حجم زیاد داده؛ الگوی دسترسی با OLTP فرق داره.

**Query Profiler** (مثل ابزار تحلیل پلن و آمار) برای تحلیل رویدادها و فایل trace به‌کار می‌ره. برای رفع مشکل خواندن فایل trace بزرگ، می‌تونی رویدادها رو توی جدول دیتابیس بریزی و بعد همان جدول رو به ابزار بدی.

## 7. TempDB و Contention

**TempDB** یه دیتابیس **سیستمی** است و نقش «چرکنویس» و فضای موقت رو داره:

- ذخیرهٔ **Temp table** (#table) و **Variable**های جدول‌گونه
- **Sort** و عملیات سنگین مرتب‌سازی
- **Row Versioning** و بعضی سناریوهای ایزوله
- **Service Broker** (SSSB) و موارد دیگر

هر جا با `#` جدول موقت بسازی، اون جدول توی **TempDB** ساخته می‌شه.

### Contention (رقابت) در TempDB

**Contention** یعنی چند session هم‌زمان می‌خوان از TempDB فضا بگیرن و روی **صفحه‌های سیستمی تخصیص (Allocation)** با هم رقابت می‌کنن؛ در نتیجه **Wait** و کندی پیش می‌آد. این صفحه‌ها عبارتند از:

- **PFS (Page Free Space)**: در هر فایل داده، یکی از اولین صفحه‌ها PFS است. هر PFS حدود **۶۴MB** فضا رو ردیابی می‌کنه (۸۰۸۰ صفحهٔ ۸KB). هر **۱ بایت** در PFS وضعیت یک **صفحه** رو نشون می‌ده. وقتی یه درخواست بخواد از TempDB فضا بگیره، روی این صفحه‌ها **lock** گذاشته می‌شه و sessionهای دیگه باید صبر کنن → **Contention**.
- **GAM (Global Allocation Map)**: صفحهٔ شمارهٔ ۲. هر **Extent** = ۸ صفحهٔ کنار هم. GAM extentهای **Uniform** (همهٔ ۸ صفحه برای یک جدول/ایندکس) رو مدیریت می‌کنه. هر بایت یه extent رو نشون می‌ده (۰ = آزاد، ۱ = استفاده‌شده). حداکثر حدود ۶۴۰۰۰ extent یعنی حدود ۴GB.
- **SGAM (Shared GAM)**: برای **Mixed Extent**ها — یعنی هر صفحه در اون extent می‌تونه به جدول/ایندکس متفاوتی تعلق داشته باشه.

هر درخواستی که از TempDB فضا بخواد، به این صفحه‌های تخصیص مراجعه می‌کنه؛ پس هر چه این صفحه‌ها بیشتر باشن و بین sessionها پخش‌تر باشن، رقابت کمتر می‌شه.

### کاهش Contention در TempDB

- **چند Data File** برای TempDB: به‌جای یک فایل، چند فایل با **اندازهٔ یکسان** و **رشد یکسان (غیر درصدی)** تعریف کن. به‌ازای هر فایل، مجموعهٔ جداگانه‌ای از PFS/GAM/SGAM داریم و sessionها بین فایل‌ها پخش می‌شن → انتظار کمتر.
- **تعداد فایل**: معمولاً تا **هستهٔ CPU کمتر از ۱۶** به‌ازای هر هسته یک data file؛ بالای ۱۶ هسته به‌ازای هر ۴ هسته یک فایل. (راهنمای کلی؛ بسته به بار واقعی و توصیهٔ مایکروسافت نسخهٔ خودت تنظیم کن.)

## 8. Key Interview Talking Points

- **Heap**: جدول بدون Clustered Index؛ در OLTP معمولاً نمی‌ذاریم؛ واکشی بدون ایندکس گرون است.
- **آمار I/O**: `SET STATISTICS IO ON`؛ logical read = تعداد صفحهٔ خونده‌شده از buffer؛ با این می‌شه قبل/بعد بهینه‌سازی رو مقایسه کرد.
- **Execution Plan**: Cost ترکیب CPU و I/O؛ عملیات با Cost بالا اولویت بهینه‌سازی؛ **Scan** یعنی اسکن گسترده، **Seek** یعنی استفادهٔ درست از ایندکس؛ معمولاً Seek بهتر از Scan.
- **پیدا کردن کوئری کند**: DMVها مثل `sys.dm_exec_requests` و `sys.dm_exec_sql_text`؛ Extended Events به‌جای Profiler.
- **TempDB**: برای temp table، sort، versioning؛ **Contention** روی PFS/GAM/SGAM؛ با **چند data file یکسان** فشار رو کم می‌کنیم.

## 9. Common Mistakes & Red Flags

- **جدول Heap در OLTP** بدون دلیل قوی (مثلاً فقط برای insert موقت).
- **توجه نکردن به آمار I/O و Plan** و حدس زدن بدون اندازه‌گیری.
- **استفاده از Profiler روی production** بدون احتیاط (overhead و deprecated)؛ ترجیح Extended Events.
- **یک data file برای TempDB** تحت بار زیاد؛ بدون در نظر گرفتن Contention و تعداد هسته.

---

## 10. When to Use / When NOT to Use

- **STATISTICS IO / Execution Plan**: برای تشخیص bottleneck و مقایسهٔ قبل/بعد بهینه‌سازی؛ نه برای هر کوئری در production بدون نیاز.
- **DBCC DROPCLEANBUFFERS / FREEPROCCACHE**: فقط در **تست**؛ در production انجام نده.
- **چند data file برای TempDB**: وقتی بار موقت و Contention روی TempDB بالاست؛ با اندازه و رشد یکسان.
- **DMVها برای مانیتورینگ**: برای دیدن sessionها و کوئری در حال اجرا؛ sp_who/sp_who2 قدیمی‌ترن، DMVها ترجیح دارن.
