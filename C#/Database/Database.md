# دیتابیس: مفاهیم پایه و طراحی

## 1. Interview Relevance Summary

دیتابیس و طراحیاش از **پایه‌های مصاحبهٔ Backend** است. تو مصاحبه معمولاً انتظار دارن:

- انواع دیتابیس رو بر اساس **کاربرد** بشناسی و بتونی بگی **چرا** یکی رو انتخاب کردی، نه فقط اسمش
- تفاوت **SQL و NoSQL** و این که «جایگزین هم نیستن» رو بدونیش
- **طراحی جدول**، **ERD** و رفتار **Cascade / Set Null / No Action** رو بلد باشی
- **ایندکس** و **Composite index** و اثرشون روی خواندن/نوشتن رو درک کنی
- **View** و کی به‌درد می‌خوره رو بدونی

برای EF Core و کوئری پیشرفته به فایل‌های دیگهٔ همین پوشه برو.

---

## 2. دیتابیس چیه؟

یه جایی برای **ذخیرهٔ منظم اطلاعات** (متن، عدد، تاریخ، لینک و غیره). بسته به نوعش، داده یا روی **دیسک** می‌مونه (پایدار) یا توی **RAM** (سریع ولی با ریست معمولاً از بین می‌ره).

---

## 3. دسته‌بندی از نظر کاربرد

هر نوع دیتابیس برای یه جور کار بهینه‌ست؛ «بهترین مطلق» نداریم. اینا رو بر اساس **نوع کاربرد** می‌شناسیم:

### در-RAM (دسترسی خیلی سریع)

مثل **Redis** و **Memcached**. داده توی **RAM** است؛ خوندن و نوشتن خیلی سریعه، ولی با ریست یا خاموشی معمولاً از دست می‌ره (مگر persistence روش باشه). توی سرویس‌های پرترافیک معمولاً یه دیتابیس **اصلی** (پایدار) داریم و یه لایه **cache** (مثلاً Redis) برای دادهٔ داغ. وقتی **read خیلی بیشتر از write** است، cache یا دیتابیس در-RAM به‌درد می‌خوره.

### عمومی (General Purpose)

**SQL** (رابطه‌ای) و **NoSQL** (اسنادی، key-value، گراف، ستونی). برای ذخیرهٔ دائم و کوئری‌های معمول؛ انتخاب بینشون بسته به مدل داده، مقیاس و نیاز به تراکنش و ACID است.

### مخصوص جستجو

مثل **Elasticsearch**. برای **full-text search** و ایندکس پیشرفته روی حجم زیاد. وقتی جستجوی متنی و فیلتر پیشرفته اولویت داره، کنار دیتابیس اصلی از این نوع استفاده می‌شه.

### گراف

مثل **Neo4j**. وقتی **روابط** بین موجودیت‌ها خودش نقش اصلی داره (توصیه‌گر، شبکهٔ دوستان). توی سناریوهای رابطه‌محور می‌تونه کارآمدتر باشه؛ حرف‌های عددی مثل «x درصد سریع‌تر» بدون سناریو و معیار مشخص قابل تعمیم نیست.

### بهینه برای Write بالا

مثل **Cassandra**. وقتی **حجم write خیلی زیاده** (لاگ، رویداد، پیام توی کانال‌های بزرگ)، دیتابیس‌های بهینه‌شده برای write و توزیع‌شده انتخاب می‌شن.

## 4. فاکتورهای انتخاب دیتابیس (نگاه سینیور)

تو مصاحبهٔ سینیور فقط گفتن «برای cache از Redis استفاده می‌کنیم» کافی نیست؛ باید بتونی **فاکتورهایی** که انتخاب رو تعیین می‌کنن توضیح بدی و trade-offها رو بگی.

### الگوی خواندن و نوشتن (Read vs Write)

- **Read-heavy**: خوندن خیلی زیاد، نوشتن کم → cache (Redis)، ایندکس قوی، یا دیتابیس ستونی برای گزارش.
- **Write-heavy**: نوشتن زیاد (لاگ، event، پیام) → دیتابیس بهینه برای write و مقیاس افقی (مثل Cassandra) یا بچ‌نویسی.
- **متعادل**: معمولاً SQL یا NoSQL عمومی با طراحی و ایندکس درست.

### نیاز به سازگاری (Consistency)

- **Strong consistency** (مثلاً تراکنش بانکی، موجودی انبار) → SQL با ACID یا دیتابیس‌هایی که تراکنش و قفل درست دارن.
- **Eventual consistency** قابل قبول (مثلاً لایک، شمارندهٔ بازدید) → NoSQL توزیع‌شده با replication و احتمال تأخیر در همگام‌سازی.

### نوع کوئری و مدل داده

- **JOINهای زیاد، رابطهٔ ثابت بین موجودیت‌ها** → SQL رابطه‌ای.
- **سند با ساختار متغیر، scale افقی** → Document store (مثل MongoDB).
- **جستجوی متنی پیشرفته** → Elasticsearch کنار دیتابیس اصلی.
- **روابط پیچیده (توصیه، گراف)** → دیتابیس گراف.
- **دسترسی با کلید ساده (key-value)** → Redis یا مشابه برای cache؛ یا key-value store برای persistence.

### مقیاس و رشد

- **الان کوچیک، بعداً بزرگ؟** — آیا از اول به scale افقی یا sharding نیاز داری یا یه دیتابیس رابطه‌ای با ایندکس و بهینه‌سازی کافیه.
- **تیم و عملیات (Ops)**: آیا تیم با این دیتابیس آشناست؟ مانیتورینگ، بکاپ و بازیابی چطوره؟ دیتابیس عجیب‌غریب بدون تخصص تیم ریسک است.

### هزینه و استاندارد شرکت

- **لایسنس، هاست، نگه‌داری** — گاهی PostgreSQL رایگان و کافی است به‌جای یه دیتابیس گران.
- **استاندارد شرکت**: گاهی مجبوری از همون چیزی استفاده کنی که بقیهٔ سرویس‌ها استفاده می‌کنن تا پیچیدگی stack کم باشه.

**خلاصه برای جواب مصاحبه**: اول **الگوی دسترسی** (read/write) و **نیاز به consistency** و **نوع کوئری** رو روشن کن؛ بعد **مقیاس** و **تیم و ops** و **هزینه** رو در نظر بگیر. بعد بگو «با این فاکتورها ما X رو انتخاب کردیم» یا «برای این سناریو Y مناسب‌تره چون …».

## 5. اطلاعات چطور ذخیره می‌شن؟ SQL و NoSQL

### SQL (رابطه‌ای)

داده **ساخت‌یافته** توی **جداول** (ستون و سطر) ذخیره می‌شه و با **SQL** واکشی و عوض می‌شه. نقطهٔ قوتش **ACID** است (تراکنش اتمیک، سازگاری، ایزوله بودن، ماندگاری). **Entity** همون موجودیت‌های طراحی است (کاربر، محصول، سفارش و غیره)؛ جداول رو معمولاً روی همون موجودیت‌ها و رابطه‌هاشون می‌چینیم.

### NoSQL (Not Only SQL)

انواع متداول:

- **Key-Value**: هر کلید یه مقدار؛ ساختار سندها می‌تونه فرق کنه.
- **اسنادی (Document)**: سند (مثلاً JSON) با فیلد و آرایه؛ انعطاف بیشتر از جدول رابطه‌ای.
- **گراف**: برای رابطه‌های پیچیده بین موجودیت‌ها.
- **ستونی (Columnar)**: برای تحلیل و بار خواندن سنگین روی حجم زیاد.

**نکته**: SQL و NoSQL **جایگزین هم نیستن**؛ بسته به مدل داده، مقیاس و نیاز به تراکنش و کوئری، یکی یا ترکیبی انتخاب می‌شه.

## 6. طراحی دیتابیس و ERD

با **ERD** قبل از پیاده‌سازی مدل رو تصویر می‌کنیم. سطوح متداول:

- **Conceptual**: مدل مفهومی — موجودیت‌ها و رابطه‌ها بدون جزئیات فنی
- **Logical**: فیلدها، نوع داده، کلیدها
- **Physical**: همون چیزی که روی دیتابیس پیاده می‌شه

اجزای ERD: **Entity**، **Attribute**، **Key**، **Relation**، **Data Type**.

## 7. رفتار روی آپدیت یا حذف والد (Referential Actions)

وقتی بین دو جدول **رابطهٔ والد–فرزند** (با کلید خارجی) داری، **حذف یا آپدیت والد** می‌تونه روی فرزند اثر بذاره. این رفتار رو باید از اول توی طراحی روشن کنی:

| رفتار | معنی |
|--------|------|
| **Cascade** | با حذف/آپدیت والد، فرزندها هم حذف یا آپدیت می‌شوند. |
| **Set Null** | با حذف والد، مقدار کلید خارجی در فرزند **null** می‌شود (ستون باید nullable باشد). |
| **Default** | با حذف والد، مقدار **پیش‌فرض** در ستون کلید خارجی فرزند قرار می‌گیرد. |
| **No Action** | اگر فرزندی وجود داشته باشد، حذف والد **مجاز نیست** مگر اول فرزندها را عوض کنیم یا حذف کنیم. |

توی ERD و توی migrationها این رفتارها رو صریح بنویس تا حذف یا آپدیت ناخواسته پیش نیاد.

## 8. دو دام رایج توی طراحی رابطه‌ها

### Fan Trap

وقتی از یه موجودیت **میانی** به دو نوع موجودیت دیگه رابطه داری ولی بین اون دو نوع **رابطهٔ مستقیم** نیست. مثال: دانشکده → گروه آموزشی و دانشکده → استاد. از «دانشکده» نمی‌شی فهمید **کدوم استاد برای کدوم گروه آموزشی** است. راه‌حل: رابطهٔ مستقیم بین گروه آموزشی و استاد یا بازطراحی مدل تا این سؤال جواب داشته باشه.

## 9. دستورات SQL (خلاصه)

چند نمونهٔ متداول (غلط‌های رایج مثل `form` به‌جای `from` اصلاح شده):

```sql
-- انتخاب با محدودیت و شرط (نکته: from نه form)
SELECT TOP (100) * FROM TableName WHERE id <> 5 OR (userId = 0 OR userId = 6);

-- تجمع: COUNT, SUM, AVG
SELECT COUNT(Id) AS ColumnName FROM TableName;

-- محدوده
SELECT * FROM TableName WHERE age BETWEEN 19 AND 25;

-- MIN, MAX
SELECT MIN(age) FROM TableName WHERE age > 27;

-- حذف رکوردهای تکراری (بر اساس ستون‌های انتخاب‌شده)
SELECT DISTINCT column1, column2 FROM TableName;

-- مقدار در لیست
SELECT * FROM TableName WHERE age IN (25, 26, 27);
```

عملگر نابرابر توی SQL: `<>` یا `!=`. برای **DISTINCT** باید مشخص کنی بر اساس کدوم ستون‌ها یکتا می‌خوای؛ `SELECT DISTINCT *` همهٔ ستون‌ها رو مقایسه می‌کنه.

## 10. ایندکس (Indexing)

### جدول بدون ایندکس (Heap)

به جدولی که **ایندکس** نداشته باشه توی بعضی موتورها **Heap table** می‌گن. برای جستجو روی یه فیلد، موتور مجبوره **همهٔ رکوردها** رو بخونه و بعد فیلتر کنه (Full Table Scan)؛ روی حجم زیاد کند می‌شه.

### ایندکس چطور کمک می‌کنه؟

ایندکس روی یک یا چند ستون یه **ساختار مرتب** از مقادیر می‌سازه تا به‌جای اسکن کل جدول، جستجو با چیزی شبیه **جستجوی دودویی** (در حد **O(log n)**) انجام بشه. توی MySQL و خیلی از دیتابیس‌ها از **B-tree** برای ایندکس استفاده می‌شه. برای **UNIQUE** کردن یه فیلد (مثل email) هم از ایندکس استفاده می‌کنیم.

**هزینه**: به‌ازای هر ایندکس، ساختار مرتب نگه داشته می‌شه و **INSERT/UPDATE/DELETE** باید اون رو هم به‌روز کنن؛ پس ایندکس زیاد **نوشتن** رو کند می‌کنه و **فضا** می‌گیره. ایندکس فقط برای ستون‌هایی که واقعاً توی **WHERE**، **JOIN** یا **ORDER BY** استفاده می‌شن معقوله.

![[Pasted image 20240201002842.png]]

اگه فقط ستون‌های داخل ایندکس رو بخوای، گاهی موتور فقط ایندکس رو می‌خونه (Index-Only Scan). با `SELECT *` بعد از پیدا کردن رکوردها از روی ایندکس، بقیهٔ ستون‌ها از جدول اصلی خونده می‌شن.

### Composite Index (ایندکس مرکب)

وقتی فیلتر روی **چند ستون** داری (مثلاً شهر + تاریخ ثبت)، یه **ایندکس مرکب** روی همون ستون‌ها تعریف می‌کنی. موتور معمولاً اول فیلتری رو که نتیجه رو بیشتر کوچک می‌کنه اعمال می‌کنه و روی مجموعهٔ کوچک‌تر اسکن یا ایندکس بعدی رو استفاده می‌کنه. **ترتیب ستون‌ها مهمه**: ایندکس روی `(X, Y, Z)` برای شرط‌های `X`، `X, Y` و `X, Y, Z` قابل استفاده است، ولی برای فقط `Z` یا `Y, Z` معمولاً درست استفاده نمی‌شه. پس ترتیب رو بر اساس **کوئری‌های واقعی** و انتخاب‌گری هر ستون انتخاب کن.

## 11. View در SQL Server

**View** یعنی یه **جدول مجازی** که از یک یا چند جدول با یه `SELECT` ساخته می‌شه. از نظر کاربر مثل جدول است (ستون و سطر)، ولی **دادهٔ فیزیکی جدا** ذخیره نمی‌کنه؛ هر بار که به View کوئری بزنی، در واقع کوئری پشتش اجرا می‌شه. وقتی اطلاعات موردنیاز توی **چند جدول** است و می‌خوای یه «نما»ی واحد داشته باشی بدون اینکه هر بار JOINها رو تکرار کنی، View به‌درد می‌خوره. بعد از ساخت View می‌تونی روش `SELECT` بزنی (و در بعضی موارد با محدودیت `INSERT/UPDATE/DELETE`).

![[Pasted image 20240306200100.png]]

```sql
CREATE VIEW ViewName
AS
SELECT col1, col2 FROM TableName
WHERE condition;
```

## 12. یه نکته: واکشی تصادفی (Random)

وقتی می‌خوای مثلاً **۱۰ مقاله تصادفی** برگردونی، با کلید عددی می‌تونی با مقدار تصادفی (مثلاً GUID) و مرتب‌سازی یا فیلتر به نمونهٔ تصادفی نزدیک بشی. روش دقیق بسته به موتور و حجم داده فرق می‌کنه (مثلاً `ORDER BY NEWID()` توی SQL Server برای مجموعهٔ کوچک).

## 13. Key Interview Talking Points

- **انواع دیتابیس**: در-RAM، عمومی (SQL/NoSQL)، جستجو، گراف، write بالا — و **چرا** یکی رو انتخاب می‌کنی (فاکتورها: read/write، consistency، نوع کوئری، مقیاس، تیم، هزینه).
- **SQL vs NoSQL**: SQL برای ساختار و ACID؛ NoSQL برای انعطاف یا مقیاس؛ **جایگزین هم نیستن**.
- **طراحی**: ERD، رفتار روی حذف/آپدیت والد (Cascade, Set Null, No Action, Default).
- **Fan Trap / Chasm Trap**: وقتی از یه موجودیت نمی‌شی به رابطهٔ موردنظر رسید؛ با رابطهٔ مستقیم یا بازطراحی حل می‌شه.
- **ایندکس**: جستجو رو با ساختار مرتب (مثلاً B-tree) سریع‌تر می‌کنه؛ هزینه روی write و فضا؛ **ترتیب ستون توی composite index** مهمه.
- **View**: جدول مجازی از یک یا چند جدول؛ داده جدا ذخیره نمی‌شه.

## 14. Common Mistakes & Red Flags

- **غلط SQL**: مثلاً `form` به‌جای `from`؛ یا `SELECT DISTINCT *` بدون توجه به اینکه تکراری بودن بر اساس همهٔ ستون‌هاست.
- **ایندکس بی‌رویه**: ایندکس روی هر ستون → write کند و مصرف فضا.
- **نادیده گرفتن ترتیب Composite Index**: ایندکس `(A, B, C)` برای فیلتر فقط روی `B` یا `C` معمولاً درست استفاده نمی‌شه.
- **تعریف نکردن Cascade/Set Null/No Action**: حذف والد می‌تونه خطا بده یا دادهٔ فرزند رو ناخواسته عوض کنه.
- **انتخاب دیتابیس بدون فاکتور**: گفتن «NoSQL بهتره» یا «همیشه Redis» بدون در نظر گرفتن الگوی دسترسی، consistency و تیم.

---

## 15. When to Use / When NOT to Use

- **در-RAM / Cache**: وقتی read زیاد و دادهٔ داغ محدوده؛ نه به‌عنوان تنها منبع حقیقت برای دادهٔ بحرانی.
- **SQL**: وقتی مدل رابطه‌ای و تراکنش و یکپارچگی مهمه.
- **NoSQL**: وقتی مدل انعطاف‌پذیر یا مقیاس یا الگوی دسترسی خاص داری؛ نه به‌خاطر «جدیده».
- **View**: وقتی می‌خوای یه کوئری پیچیده یا چند جدول رو پشت یه نام ساده پنهان کنی؛ برای کوئری خیلی سنگین گاهی materialized view یا جدول واقعی بهینه‌تره.
- **ایندکس**: روی ستون‌هایی که توی WHERE/JOIN/ORDER BY استفاده می‌شن؛ نه روی همهٔ ستون‌ها.
