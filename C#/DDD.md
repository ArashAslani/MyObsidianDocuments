Core Domain بخش اصلی برنامه است که نقطه عطف و برگ برنده کسب و کار است که نمیتوان از سیستم آماده استفاده کرد. دارای Value proposition های مهم و بسیار است.
 یک مسئله میتواند چند Core Domain داشته باشد.
 مثلا کارگزاری ها : اگر دید کلی بازار نباشد که نمیتواند خرید فروش کرد و اگر دید کلی باشد و خریدو فروش نباشد سودی ندارد. پس مسئله دارای 2 Core Domain مهم هست. 

Supporting subdomain :
	برای بیزنس حیاتی نیست و در صورت وجود سیستم اماده میتوان از آن استفاده کرد. تا تمرکز روی Core domain باشد.

Generic subdomain :
	بین بسیاری از برنامه ها مشترک هست، نمونه گزارشگیری و ارسال پیام که استفاده از سرویس های اماده بهتر است.
	مانند بخش ویژیولایز کردن داده ها و بحث احراز هویت یا سیستم ارسال ایمیل
	عمومی هستند.
	محصول تولید میشود نه پروژه در اصل محصول ادامه دار است و تکامل پیدا میکند و نیاز به خروجی دارد.
	به علاوه نیاز به سرمایه گذاری دارند و چگونگی مدیریت و زمانبدی و ارائه خروجی در بازه زمانی درست بسیار مهم هست.


Anti Corruption Layer :
	تعیین نکردن مرز و زمانبدی و دادن راه حل های بی مورد باعث میشود تا مشکلات در تمام پروژه پخش شوند و ارائه خدمات به صورت ایده عالی ارائه نشوند.
	اگر ارتباط بین Context ها به صورت مطلوب اتفاق نیوفتاد میتوانیم با کشیدن یک پوسته درست روی آن مشکلات رو موقتا حل کرد. مانند استفاده از Design pattern Adapter 
	
 در زمان تست بازار Core Domain میتواند دارای نواقصی باشد تا به بازار و خروجی برسیم.
 در زمانی که به این صورت کار میکنیم باید به فکر ریفکتورینگ و تولید دانش موجود باشیم.

Domain : (Domain Model)
	اصطلاح Domain به حوزه و دامنه‌ی اصلی فعالیت نرم‌افزار اطلاق می شود که نرم‌افزار برای پیاده‌سازی آن توسعه می‌یابد. که مهم تر از دانش فنی و غیره هست.
	از این جهت تیم توسعه هم باید غرق در دامنه و حوزه کسب و کار شوند.
	دستاورد دانش دامنه :
	1. یافتن نکات کلیدی برای توسعه
	2. ساخت مدلی مناسب برای صورت مسئله

	تحلیلگر کسب و کار در این بخش کمک به افراد میکند برای انتقال صحیح نیازمندی ها و در صورت نبود تیم فنی کمک به تعامل کارآمد میکند. در اصل در برخی از سازمان ها تیم فنی مهارت ارتباطی کم دارند بین بیزنس و تیم فنی حالت کاتالیزور ایجاد میکنند.
	مثلا حسابداری، CRM و...
	که شامل فایل های base یا Shared ما و Aggregates و Entities هست.

Value Objects :
	Identity-less یعنی بدون ایدی هستند و با مقادیر داخلشون شناخته و مقایسه میشوند.
	Attribute Based equality به معنی اینکه برای مقایسه باید از مقادیر فیلد های آنها استفاده کرد. چون از جنس کلاس هستن و نمونه ها دارای ادرس متفاوتی هستند باید مواردی را در نظر گرفت. چون به صورت پیشفرض کلاس ها با HashCode هایشان مقایسه میشوند.
	Behavior-rich یعنی باید رفتار های مشخص رو داخل خودشون معرفی کنند. اعم از اپراتور ها مقایسه ها فرمت ها و حالت های مختلف ورودی برای Price مثلا تومان هست یا ریال.
	Immutable یعنی نباید مقدارشان تغییر کند. یعنی هنگام تغییر یک نمونه جدید از ان ساخته میشود. 
	Combinable یعنی باید بتوانیم دو ابجکت را باهم جمع کنیم که کلاس های دیگر نمیتوانند.
	Self-validate (should never be in  an invalid sate) یعنی باید این ابجکت خودش رو اعتبار سنجی کنه تا مقدار اشتباهی نگیرد.
	Value Object میتونه با Class یا Struct ساخته بشه از این جهت که با EF همپوشانی ندارن و موارد دیگر زیاد توصیه نمیشن.
	زمانی Value Object میسازیم که قرار هست مقدار داخلش باید حتما Validate شود و تکرار شود یا میخواهیم خوانایی کد بالاتر باشه.
	به خودی خود هیچ منفعتی ندارد و تکمیل کننده یک Entity یا Aggregate هستند.
	مثلا مشخص کردن تایپ بخصوص برای فیلد Price که مثلا در مجصول و سفارش وجود دارند و هربار validate شده است. 
	یعنی بین موجودیت ها ممکن است به اشتراک گذاشته شوند.
	زمانی ذخیره سازی  prop های آن در دیتابیس ذخیره میشوند و به صورت یک Table جدا ذخیره نمیشن.
	که در آن Static Factory Method پیاده سازی میشود تا کار نمونه سازی را به ازای هر Behavior انجام دهد.
	نکته این هست که Value Object ها نباید به صورت لیست گرفته شوند. چون دسترسی به دیتا در ان ها به دلیل نبود شناسه دشوار است.
	در صورت نیاز باید یک Value Object با مقدایر محدود ایجاد کنیم.
	مثال PhoneNumber و PhoneBook
	به مراتب خوانایی ، صحت اطلاعات ، Usability و منسجم سازی بالا میرود.
	
Aggregates : 
	به مجموعه ای از اشیاء بهم مرتبط گفته میشود که جهت کنترل تغییرات، به عنوان یک واحد در نظر گرفته میشوند. اریک ایوان
	که به عنوان یک ترنزکشن شناخته میشود.
	
	![[Pasted image 20240311035855.png]]
	مثلا Product که روت Aggregate ما هست وجود نداشته باشد Product images , Specifications معنی ندارند. و به عنوان یک موجودیت واحد در نظر گرفته نمیشوند و مجموعه آنهاست که یک موجودیت Product که Root هست را تشکیل میدهند.
	معمولا سعی میشود تا Aggregate root سبک باشد و بیش از 3 ارتباط نداشته باشند.
	ارتباط Root با زیر مجموعه ها به صورت Composition هست.
	تمام زیر مجموعه ها توسط Root ایجاد و تغییر میکند. 
	Aggregate ها به هیچ عنوان به صورت مستقیم باهم ارتباطی ندارند. و ارتباط آنها در حد نگهداری یک آیدی از Aggregate دیگر هست.
	و ارتباط زیر مجموعه ها با Aggregate ها دیگر با Root خودشان اتفاق می افتد.   
	Check Invariant : مسئولیت چک کردن قوانین ثابت و Business Rules با روت هست.
	Aggregate access : اشیا خارج از مرز Aggregate نمیتوانند به شیء به غیر از Root دسترسی داشته باشند. 
	Single Repository : به ازای هر Aggregate Root یک Repository در نظر گرفته میشود.
	بسته به منطق برنامه و بیزنس مشخص میشود که Root کدام است.
	چون هنگام نمونه سازی و کار با Aggregate و زیر مجموعه های (Entities) آن نیاز داریم که کنترل ایجاد کلید را خودمان در نظر بگیریم، مقادیر ایدی به صورت یک کلاس با کلید Guid توسط برنامه خودمان ایجاد و داده میشوند.
	در صورتیکه از کلاس استفاده نکنیم و Id از جنس عددی باشد میتوانیم از الگو Hylo استفاده کنیم که قبل انجام transaction مقدار Id را برای ما میسازد. و لازم نیست حتما SaveChanges فراخوانی شود.

Domain Service :
	یک سرویس هست که مختص به یک Aggregate هست. لازم هست Aggregate باهم ارتباط داشته باشند چون روی شرایط بیزنس تاثیر گذار هستند مثلا یافتن و بودن یک محصول برای ثبت یک سفارش.
	Aggregate ها دارای رفتار و فاقد State هستند. یعنی اطلاعات داخل خودشون رو اعتبار سنجی میکنند و چیزی رو تغییر نمیدن. بین بقیه Aggregate ها share میشن  و در داخل خوده Aggregate قابل پیاده سازی نیستند و  زمانی که به اطلاعات و محتوای یک Aggregate دیگر نیاز داریم. زمانی که به Context نیاز داریم از Domain Services استفاده میشود. 
	مانند Repository نیستند و زمانی که یک کار از نوع Infrastructure داشته باشیم از آنها استفاده میکنیم. و به صورت singleton اضافه نمیشوند. و صرفا یک دیتایی گرفته و پاس میدهند.
	چون از نمونه ان در همه جای Domain نیاز نداریم به صورت Constructor Injection عمل نمیکنیم یا که از Manual Instantiation بسته به Domain Service استفاده میکنیم. روش دیگر Service locator pattern هست که چون یک آنتی پترن هست پیشنهاد نمیشود.
	پس بهترین پیشنهاد Method Injection میتواند باشد.
	تا در صورت نیاز فانکشن به آن پاس داده شود.
	بسته به کاری مد نظر اگر توانایی پیاده سازی در Core را نداشتیم و کارمان از جنس Infrastructure بود میتوانیم در لایه Infra پیاده سازی را انجام دهیم. در غیر این صورت در Core که شامل Domain, Application و Contracts هست.
	که Best Practice آن در لایه Application انجام میشود.

Domain Events :
	زمانی که اتفاقاتی از جنس Transaction یا تغییرات تاثیر گذار در برنامه پیش می آیند که در صورت بروز این اتفاق کار خاصی باید انجام شود از Domain Event استفاده میکنیم. تا عملیاتی که به آن گوش میدادن عملیات مد نظر رو انجام بدن. مثلا ارسال پیام بعد از ثبت سفارش.
	که مفهوم Publisher , Subscriber در اینجا به وسیله MediatR عملی و اجرایی میشوند.
	در Aggregate Root ساخته و پرتاب میشوند.
	پس داخل یک Aggregate ما درای مجموعه ای از Domain Event ها هستیم.
	البته در پیاده سازی Aggregate, Entity و Domain Event از کلاس های Base استفاده میکنیم تا SRP را با استفاده از Polymorphism و Inheritance پیاده سازی کنیم.
	هر Aggregate دارای مجموعه کلاس های Event Model  مخصوص به Domain و بیزنس خود هست. که از DomainEventBase را ارث بری میکنند.
	زمانی که مثلا یک User داریم که باید هم در دیتابیس ثبت شود و هم در سیستم Register شود بهتر است از Static Factory Method استفاده کنیم. چرا که در زمان نمونه سازی مثلا آواتار و وضعیت را از کاربر نمیگیریم و برایشان پیشفرض تعریف میکنیم و مقادیر خاصی را در زمان نمونه سازی خارج از Root لازم داریم و همچنین برای Register کردن هم بخشی از فیلد ها کافی هستند پس از این الگو استفاده میکنیم.
	Domain Event ها میتوانند به دو صورت Async و Sync استفاده شوند. یعنی میتوانیم اپلیکشن را منتظر جواب Event بگذاریم و عملیات دیگر را بعد آن انجام شود یا به صورت Async باشد تا در Background انجام شوند.
	بهتر هست در سیستم های monolith از مدل sync استفاده کنیم چرا که میخواهیم مطمئن شویم ترنزکشن کامل انجام شده. و در صورتی که لازم نداریم حتما یک event اجرا شود میتوانیم از async استفاده کنیم.
	sync برای ارسال کد verify که ارسال شدن پیام مهم هست و async برای پیام ثبت سفارش که اهمیت خاصی ندارد پیام ارسال شود یا نه.


Custom Exceptions :
	برای اینکه بین Exception ها بسته به اهمیت و کاربردی که دارند بتوانیم تبعیض قائل شویم و ردگیری با خطا ها در Domain ها تسهیل شود از Custom Exceptions استفاده میکنیم. 
	مثلا بعضی اکسپشن ها روی کنسول log زده میشوند بعضی در دیتابیس ذخیره میشوند مانند 500 Errors و بعضی در فایل ذخیره میشوند.
	پس مهم هست که بدانیم چه خطایی با چه تایپی و در کجا رخ داده است.
	  


Domain Model :
	تمرکز و توجه اصلی این رویکرد، بر روی توسعه‌ی این مدل می‌باشد. تحلیل و طراحی Domain Model به طور اختصاصی، به منظور تولید نرم‌افزار در ابعاد Enterprise و با فرآیند‌های پیچیده و زیاد مناسب می باشد.
	در زمان ایجاد Domain Model، با دقت به جزئیات توجه کرده و مفاهیم و قوانین (‌Business Rule) را در آن پیاده‌سازی می‌کنیم.

Stack Holder :
	مالک کسب و کار هست و میداند ورودی و خروجی کدامند و میداند کسبو کار چیست. ولی نمیداند چطور و چگونه

	  به کسانی که بر روی موضوع و رویه‌های سامانه مسلط می‌باشند Domain Expert اطلاق می‌شود.

Ubiquitous Language :
	برای بحث درمورد مسائل بین تیم توسعه و متخصص دامنه لازم هست زبانی مشترک وجود داشته باشد. زبان مشترک برای درک مفاهیم Domain برای هردو تیم الزامی هست.
	
Bounded Context :
	در این رویکرد رهکارهایی درمورد تقسیم اجزا مختلف نرم افزار مطرح شده. بخش هایی مستقل و جدا از هم که انعطاف پذیری را به تیم توسعه میدهد. و Principle های سالید را پشتبانی میکند.
	یک مرز بین تمام مفاهیم و مفهوم Bounded Context باید کشیده شود.
	باعث افزایش قابلیت استفاده میشوند و در سیستم های مختلف مفاهیم شفافیت پیدا میکنند. مانند تیکت سینما یا تیکت رفع اشکالات.
	راهنمای یافتن BC :
	واژه ها ، بخش های کسب و کار ، ساختار و شرایط تیم مشخص کننده کانتکس هستند نه اندازه انها.
	Context Game (greg young) : ارائه یک مفهوم به تموم تیم ها جمع آوری نتایح بعد از مدت کوتاه. تیم های مختلف روی یک موضوع فکر میکنند در جلسه درمورد ان صحبت میکنیم تا بخش های مختلف یک موضوع شفاف شوند.
	بعضی از مفاهیم مثل تیکت در سیستم رزرو بلیط یا رفع اشکال دو مفهوم جدا هستند که باید جداگانه هم پیاده سازی شوند.
	اما یک مفهوم مثل کارمند در سیستم حقوق دست مزد و مرخصی یک مفهوم با کاربرد های متفاوت دارند. در حالت یک پیاده سازی داریم و نیاز های سرویس های دیگر را لحاظ میکنیم در این حالت ممکن هست داپلیکشن دیتا به وجود بیاد که صرف نظر از ان در صورت لزوم ایرادی ندارد.
	معماری هر قسمت کاملا اختصاصی هست و میتوان زبان و ابزار متفاوتی استفاده کرد.

Domain Centric :
	در معماری Onion می‌توان این‌گونه در نظر گفت که Domain Domain Centric‌ / Model، مدلی انتزاعی از دامنه‌ی فعالیت سامانه می‌باشد که توسط تیم توسعه‌ی نرم‌افزار، در قالب یک مدل شی‌گراء طراحی و پیاده‌سازی می‌شود. این مدل ممکن است در طول زمان و با تغییر فرآیندها تغییر یافته و تکمیل شود. باید دقت داشته باشیم که Domain Model تنها یک ساختار داده‌ای ساده (Anemic) نبوده و مجموعه‌ای از داده‌ها، رفتارها و نیز قوانین (Business Rule) در آن تعبیه شده و در نظر گرفته می‌شود.

Anemic Or Rich Domain Model :
	در این رویکرد از Domain Model هایی که صرفا ساختار داده ای ساده داشته باشند و تعیین رفتار میکنند (Anemic Domain Model) عقب نشینی میکنیم.
	و از دامین هایی استفاده میکنیم که علاوه بر ساختار داده ای رفتار و نیز قوانین و حتی Validation های آن نیز در درون  Domain انجام میدهیم.(Rich Domain Model)
	
Persistence Ignorance :
	از آنجا که مهم‌ترین موضوع در طراحی Domain Model، اطمینان از صحت فرآیند‌ها و Business های سامانه نرم‌افزاری می‌باشد، لذا در هنگام طراحی، از پرداختن به دغدغه‌ها و نکات فنی، زیرساختی و دیتابیسی اجتناب می‌کنیم. به این رفتار در طراحی و پیاده‌سازی Domain Model اصطلاحا Persistence Ignorance اطلاق می‌شود.

	انواع روش های پیاده سازی Domain Model :
	1- 20% Domain Model (Rich Domain Model) :

	3- Table Modual :

Anticorruption Layer :
	ممکنه دو Context داشته باشیم یکی سالم و دیگری دارای ایراد هست و نمیخواهیم که ایرادات موجود در Context ایراد دار به Context سالم سرایت کند. 
	میایم یک لایه ارتباطی ایجاد میکنیم که دارای لاجیک و بیزنس نیست و کار ترنسلیت از سرویس مشکل دار به سرویس سالم هست.
	و به محظ رفع مشکل باید بتوان این لایه را حذف کرد.
	پیاده سازی همان Adapter pattern در سطح یک Context هست.

Shared Kernel :
	در دو Context مختلف بخش های مشترک وجود دارد

	باعث کاهش ریسک با  Continues Integration Test میشود.

Separate Way :
	هزینه ادغام بالا دارای پیاده سازی کاملا مجزا و یکسان سازی در End point است.
	میتوان از روش هایی که وابستگی ایجاد نمیکند استفاده کنیم به هرروشی مانند هندل کردن در UI

Upstream/Downstream :
	طرف اصلی و سرویس دهنده Upstream است و طرف وابسته و سرویس گیرنده Downstream هست.
	ارتباطات با توجه به جهت مشخص میشوند. که باید در Context Map هم مشخص شوند.
	من باب دو تیم میتوانیم ارائه بدیم :
	Customer-supplier :
		تیم ها باید به توافق تغییرات را اعمال کنند و تنهایی تصمیم نگیرند. 

Conformist :
	در شرایطی از این ارتباط استفاده میکنیم که طرف بالا دستی امکان همکاری ندارد و امکان ایجاد ACL هم نیست.
	مثل تغییراتی که یک شرکت در نحوه دادن سرویس میدهد مانند درگاه بانک یا سیستم پیامکی که نمیتوان درمورد تغییرات مذاکره کرد.
	![[Pasted image 20240324144019.png]]
	سعی میکنیم در این روش تغییرات لحاظ شده را در لایه ACL اعمال کنیم و به Context دست نزنیم.

با دانستن این ارتباطات و مشخص شدن آن در Context Map حفظ یکپارچگی و تعیین نقاط مهم برای شروع کار و شناسایی مالکان و وظایف راحت تر اتفاق میوفتد.
مثلا اگر تغییرات یک سرویس اگر به Supporting Domain تاثیر گذار است ملاحظات کمتر از تاثیرات روی Core هست.

***Technical Pattern

Application Architecture :
	بزرگ ترین هدفی که میخواهیم به ان برسیم جداسازی پیچیدگی فنی از Business  هست. و باید دامنه ایزوله شود.
	با رعایت SOC (Separation of Concerns ) امکان تغییرات را فراهم کنیم.
	یعنی هر قسمت باید عملیات خودش را انجام دهیم به وسیله IOC اتفاق میوفتد.
	در کار های ساده از لایه بندی UI - BL - DAL استفاده میکنیم. در روش های Table Model - Transaction Model استفاده دارند. و IOC به صورت گسترده یا شاید اصلا در آنها استفاده نشده است.
	در DDD لایه Domain هیچ وابستگی به لایه های دیگر ندارد.
	در پیاده سازی اینوع معماری و ارتباطش با دیتابیس از دو لایه Core و Infrastructure استفاده میکنیم که اگر Domain به Infra نیاز داشت باید شامل Contract های ان باشد.
	یک قسمت دیگر Core شامل Domain Model هست که میتواند Rich یا Anemic باشد.
	لایه Domain Service  که اگر Anemic باشیم تمام قواعد Invariant داخل Entity به عنوان یک Domain Service تعریف میشود و اگر Rich  باشیم فقط بیزنس هایی که نیاز به چند Entity دارند را در این لایه پیاده سازی میکنیم.
	در Rich پیش می افتد که Domain service  خالی باشد.
	لایه Application Service شامل Use Case های ما هستند. الگو Grasm خوانده شود. یکی از پترن های ان Controller هست که دقیقا کاری هست که لایه application ما انجام میدهد. شامل دوتا روش پیاده سازی است.
	Facade Controller Or Session Controller 
	session : در هرکدامشان یک Use Case قرار دارد. مانند Command Pattern
	facade : هرکدام از انها شامل چند Use Case هستند.
