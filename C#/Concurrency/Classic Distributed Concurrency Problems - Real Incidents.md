# مسائل کلاسیک Concurrency در معماری توزیع‌شده — همراه با اتفاق‌های واقعی

## چرا این فایل؟

هفت مسئلهٔ کلاسیک Concurrency توزیع‌شده رو قبلاً فهرست کردیم. این فایل هر کدوم رو با یه **اتفاق واقعی و مستند** (پست‌مورتم رسمی شرکت‌ها، گزارش SEC، یا تحلیل‌های Jepsen که یه پروژهٔ معروف تست سیستم‌های توزیع‌شده‌ست) ترکیب می‌کنه. هدف اینه که وقتی این مفاهیم رو تو مصاحبه توضیح می‌دی، به‌جای تعریف کتابی خشک، بتونی بگی «این دقیقاً همون چیزیه که فلان شرکت رو با این جزئیات زمین زد» — که هم عمق دانشت رو نشون می‌ده هم قابل‌یادآوری‌تره.

منبع همهٔ اتفاق‌های این فایل مستنده (پست‌مورتم رسمی خود شرکت، گزارش SEC، یا گزارش Jepsen)، نه شایعه یا نقل قول دست‌دوم.

## 1. Two Generals Problem → چرا Stripe اسلحه‌ی اصلی‌ش «Idempotency Key»‌ است

### تئوری
دو نود که فقط از طریق یه شبکهٔ غیرقابل‌اعتماد حرف می‌زنن، هیچ‌وقت نمی‌تونن ۱۰۰٪ مطمئن بشن پیام‌شون رسیده — چون حتی خود پیام تأیید (ACK) هم ممکنه گم بشه. این یه قضیهٔ ریاضی اثبات‌شدهٔ **غیرقابل‌حل** است، نه یه محدودیت مهندسی که با تلاش بیشتر برطرف بشه.

### اتفاق واقعی: مسئلهٔ Double Charge در Stripe
Stripe به‌طور مستقیم این مسئله رو در مستندات فنی خودش توضیح داده: وقتی یه کلاینت درخواست پرداخت می‌فرسته و **قبل از دریافت پاسخ**، کانکشن قطع می‌شه (timeout یا خطای شبکه)، کلاینت نمی‌دونه سرور واقعاً پرداخت رو پردازش کرده یا نه. سه حالت ممکنه اتفاق افتاده باشه:
1. درخواست اصلاً به سرور نرسیده — retry کاملاً امنه.
2. درخواست رسیده، پردازش شده، ولی پاسخ برنگشته — retry باعث **پرداخت دوم** می‌شه.
3. درخواست وسط پردازش قطع شده — نامشخصه.

Stripe به‌صراحت میگه این دقیقاً همون مسئلهٔ کلاسیک Distributed Systems هست و حتی خود Stripe API به‌همراه یه سرور دیگه که بهش وصل می‌شه، یه سیستم توزیع‌شده محسوب می‌شه.

**راه‌حلی که Stripe واقعاً پیاده کرده**: هر درخواست POST یه هدر `Idempotency-Key` (یه UUID) داره. اگه Stripe همون کلید رو قبلاً دیده باشه، به‌جای پردازش دوباره، **همون پاسخ قبلی رو کش‌شده برمی‌گردونه** (حتی اگه پاسخ قبلی یه خطای 500 بوده باشه). این کلید تا ۲۴ ساعت نگه داشته می‌شه. نکتهٔ ظریفی که Stripe تأکید می‌کنه: کلاینت باید کلید رو **قبل از اولین تلاش** بسازه و در تمام retryها همون کلید رو بفرسته — نه یه کلید جدید برای هر retry، وگرنه کل مکانیزم بی‌فایده می‌شه.

**درسی که می‌گیریم**: نمی‌تونی Two Generals Problem رو "حل" کنی؛ می‌تونی طوری طراحی کنی که **حتی اگه پیام دو بار برسه، اثرش فقط یه بار اعمال بشه**. این دقیقاً همون Idempotency Pattern هست که قبلاً برای RabbitMQ Consumer هم گفتیم — حالا می‌دونی این ایده از کجا میاد و چرا حتی بزرگ‌ترین شرکت‌های پرداخت دنیا هم مجبورن باهاش کنار بیان، نه که دورش بزنن.

## 2. Clock Skew و Last-Write-Wins → وقتی Riak و MongoDB داده گم کردن

### تئوری
هر نود ساعت خودش رو داره؛ حتی با NTP هم چند میلی‌ثانیه تا چند صد میلی‌ثانیه اختلاف طبیعیه. اگه یه سیستم توزیع‌شده تصمیم بگیره «آخرین نوشته (بر اساس timestamp) برنده‌ست» (Last-Write-Wins یا LWW)، این فرض رو داره که همهٔ ساعت‌ها دقیقاً sync هستن — که هرگز واقعیت نداره.

### اتفاق واقعی #۱: از دست رفتن ۷۱٪ نوشته‌ها در Riak
پروژهٔ Jepsen (کار Kyle Kingsbury، معروف‌ترین محقق مستقل تست سیستم‌های توزیع‌شده) یه تست ساده روی دیتابیس Riak انجام داد: چند کلاینت هم‌زمان به یه key عدد اضافه می‌کردن. نتیجه: از ۲۰۰۰ نوشتهٔ تأییدشده (acknowledged) توسط دیتابیس، فقط ۵۶۶ تاش زنده موند — یعنی **۱۴۳۴ نوشتهٔ تأییدشده به‌طور خاموش گم شد**. دلیلش این بود که وقتی دو کلاینت تقریباً هم‌زمان به یه value می‌نوشتن، Riak فقط اونی که timestamp بزرگ‌تر داشت رو نگه می‌داشت و بقیه رو (که ممکن بود عدد جدیدی اضافه کرده باشن) کاملاً نادیده می‌گرفت.

**نکتهٔ کلیدی از این تست**: حتی اگه یه Distributed Lock هم جلوی نوشتن هم‌زمان رو بگیری، چون خود سرویس Lock هم باید طبق CAP Theorem در زمان Partition یا در دسترس باشه یا Consistent، این مشکل کاملاً حل نمی‌شه — باید مدل داده و استراتژی conflict resolution رو عوض کنی (مثلاً استفاده از CRDT به‌جای LWW ساده).

### اتفاق واقعی #۲: از دست رفتن نوشته‌های اکثریت‌تأییدشده در MongoDB به‌خاطر Clock Skew
Jepsen توی تحلیل نسخهٔ ۳.۴ MongoDB نشون داد که وقتی یه Primary با ساعت جلوتر (fast clock) از بقیهٔ نودها ایزوله می‌شد، پروتکل replication نسخهٔ قدیمی (v0) اجازه می‌داد نوشته‌هایی که با `write concern: majority` تأیید شده بودن (یعنی طبق تعریف MongoDB باید تضمین‌شده و دائمی باشن) **گم بشن**. این باگ بعداً در نسخه‌های ۳.۲.۱۲ و ۳.۴.۰ برطرف شد.

**درسی که می‌گیریم**: وقتی یه سیستم می‌گه «این نوشته acknowledged شده»، این ادعا فقط به‌اندازهٔ الگوریتم توافقی (consensus) که پشتشه معتبره. اگه اون الگوریتم به ساعت وال‌کلاک (wall-clock) به‌جای شمارندهٔ منطقی (مثل Lamport Clock) یا Raft Term تکیه کنه، حتی «تأیید شده» هم می‌تونه دروغ باشه.

### راهی که Google انتخاب کرد: به‌جای امیدوار بودن، عدم قطعیت رو اندازه بگیر
Google برای دیتابیس توزیع‌شدهٔ جهانی Spanner، به‌جای تلاش برای «کامل sync کردن ساعت‌ها» (که تئوریاً غیرممکنه)، یه سیستم به‌نام **TrueTime** ساخت که با GPS و ساعت اتمی، **بازهٔ عدم قطعیت** هر timestamp رو صریحاً اندازه می‌گیره (مثلاً «الان بین ساعت X و X+7 میلی‌ثانیه است») و قبل از commit کردن یه تراکنش، عمداً صبر می‌کنه تا این بازه رد بشه. این یه مثال خوبه از اینکه راه‌حل واقعی «قبول کردن عدم قطعیت و مدیریت صریح‌ش» است، نه «تظاهر به این‌که ساعت‌ها sync هستن».

## 3. Split-Brain → قطعی ۲۴ ساعته‌ی GitHub از یه Partition ۴۳ ثانیه‌ای

### تئوری
وقتی شبکه بین دو بخش یه کلاستر قطع می‌شه، هر طرف ممکنه فکر کنه طرف دیگه مرده و خودش تصمیم بگیره لیدر جدید انتخاب کنه. نتیجه: دو Leader هم‌زمان که هر دو مستقل می‌نویسن.

### اتفاق واقعی: ۲۱ اکتبر ۲۰۱۸، GitHub
طبق پست‌مورتم رسمی GitHub:

**اتفاق چی بود؟** طی یه کار نگهداری روتین شبکه، یه ارتباط بین دیتاسنتر شرق آمریکا و بقیهٔ زیرساخت GitHub برای فقط **۴۳ ثانیه** قطع شد. GitHub از MySQL با معماری Primary-Replica استفاده می‌کنه و برای مدیریت failover از یه ابزار متن‌باز به‌نام **Orchestrator** استفاده می‌کنه که خودش با الگوریتم اجماع Raft کار می‌کنه.

**زنجیرهٔ خرابی**: نودهای Orchestrator که توی سواحل غربی و روی cloud عمومی بودن، وقتی سواحل شرقی رو "قطع" دیدن، چون هنوز بین خودشون Quorum (اکثریت) داشتن، تصمیم گرفتن یه Primary جدید توی سواحل غربی **promote** کنن. مشکل این بود: بعضی نوشته‌ها که روی Primary اصلی (شرقی) ثبت شده بودن، هنوز فرصت replicate شدن به غرب رو پیدا نکرده بودن. وقتی اتصال ۴۳ ثانیه‌ای برگشت، GitHub با **دو تا تاریخچهٔ داده‌ی واگرا (divergent)** مواجه شد: بعضی نوشته‌ها فقط روی کلاستر شرقی (قدیمی) بودن و اصلاً به کلاستر جدید غربی نرسیده بودن.

**نتیجه**: باوجود اینکه خود Partition فقط ۴۳ ثانیه طول کشید، GitHub **۲۴ ساعت و ۱۱ دقیقه** با اختلال جدی مواجه بود — چون merge کردن دو تاریخچهٔ متناقض داده به‌صورت خودکار امکان‌پذیر نبود و نیاز به تطبیق دستی (manual reconciliation) داشت. در این مدت، ارسال webhook و ساخت GitHub Pages به‌طور کامل غیرفعال بود و بیش از ۵ میلیون webhook و ۸۰ هزار build صف شده بودن که باید بعداً پردازش می‌شدن.

**چرا این اتفاق افتاد با وجود این‌که از Raft Consensus استفاده می‌کردن؟** چون Orchestrator طبق طراحی خودش عمل کرد — مشکل این بود که **کل توپولوژی سیستم اپلیکیشن** برای این سناریو (تغییر Primary بین دو ریجن جغرافیایی با تأخیر شبکهٔ بالا) طراحی نشده بود. یعنی صرفاً داشتن Consensus کافی نیست؛ باید تمام زنجیرهٔ سیستم (از جمله چیزهایی مثل connection string اپلیکیشن‌ها) برای همچین failoverی آماده باشه.

**درسی که می‌گیریم**: Split-Brain همیشه به‌معنای «باگ» در Consensus Protocol نیست؛ گاهی خود Protocol درست کار می‌کنه ولی نتیجه‌ش برای معماری بالادستی غیرمنتظره‌ست. راه‌حل صرفاً «از Raft استفاده کن» نیست؛ باید **صریحاً تصمیم بگیری** که در زمان Partition، سیستم Availability رو فدای Consistency می‌کنه یا برعکس — و GitHub بعد از این اتفاق گفت که Consistency رو انتخاب کرده بود (به قیمت این قطعی طولانی)، نه این‌که این یه شکست تصادفی باشه.

## 4. Partial Failure در Deployment توزیع‌شده → ضرر ۴۴۰ میلیون دلاری Knight Capital در ۴۵ دقیقه

این دقیقاً یکی از هفت مسئلهٔ کلاسیک نیست، ولی نسخهٔ افراطی یه مسئلهٔ نزدیک بهشونه: **وقتی حالت (state) بین نودهای یه سیستم توزیع‌شده inconsistent می‌شه چون deployment atomic نبوده**.

### اتفاق چی بود؟
در اول اوت ۲۰۱۲، Knight Capital (یکی از بزرگ‌ترین market makerها در بازار سهام آمریکا) می‌خواست یه فیچر جدید (برنامهٔ Retail Liquidity Program بورس نیویورک) رو روی سیستم معاملاتی‌شون به‌نام SMARS فعال کنه. این سیستم روی **۸ سرور** پخش شده بود.

طبق گزارش‌های تحلیلی و پست‌مورتم‌های منتشرشده: تکنسینی که کد جدید رو deploy می‌کرد، فراموش کرد کد جدید رو روی **یکی از ۸ سرور** کپی کنه. اون سرور هشتم، هنوز یه کد قدیمی و متروکه از سال ۲۰۰۳ به‌نام "Power Peg" رو داشت که قرار بود فقط برای تست استفاده بشه — ولی به‌خاطر استفادهٔ مجدد از یه پرچم (flag) قدیمی در کد جدید، این ماژول متروکه به‌طور ناخواسته **فعال شد**.

**نتیجه**: از اون به بعد، سیستم توزیع‌شدهٔ Knight یه **حالت ناسازگار (inconsistent state)** بین نودهاش داشت — ۷ سرور طبق منطق جدید و درست عمل می‌کردن، ولی سرور هشتم طبق یه منطق کاملاً متفاوت و قدیمی سفارش می‌فرستاد. چون SMARS سفارش‌های ورودی رو بین این ۸ سرور **توزیع** می‌کرد (فرض بر این‌که همه‌شون یه منطق دارن)، سفارش‌هایی که به سرور هشتم می‌رسیدن باعث میلیون‌ها معاملهٔ ناخواسته می‌شدن. در عرض ۴۵ دقیقه، Knight بیش از ۴ میلیون معامله روی ۱۵۴ سهم انجام داد که در مجموع ارزشی حدود ۷ میلیارد دلار داشت، و در نهایت **۴۴۰ میلیون دلار** ضرر کرد — رقمی که تقریباً شرکت رو ورشکسته کرد و باعث شد ظرف چند روز با ۴۰۰ میلیون دلار تأمین مالی اضطراری نجات پیدا کنه.

**نکتهٔ فنی مهم**: این دقیقاً یه نسخهٔ افراطی از مشکلیه که تو معماری Multi-Pod هم باهاش روبه‌رو می‌شی — اگه Deployment روی همهٔ Podها **atomic** نباشه (یعنی یا همه به نسخهٔ جدید برن یا هیچ‌کدوم)، برای یه بازهٔ زمانی چند Pod با نسخه‌های متفاوت کد، به یه Request مشابه پاسخ‌های متفاوت می‌دن. توی Kubernetes این با استراتژی‌های Rolling Update معمولاً کنترل‌شده‌ست، ولی اگه سرویس‌ت **Backward Compatible** نباشه (مثلاً یه فیلد جدید توی پیام RabbitMQ که نسخهٔ قدیمی Consumer نمی‌فهمه)، دقیقاً همین کلاس مشکل رخ می‌ده — فقط شاید نه به این شدت فاجعه‌بار.

**درسی که می‌گیریم**: در سیستم‌های Distributed، «چند نود که ظاهراً باید یکسان باشن» یه فرضه که باید صریحاً تضمینش کنی (با Deployment atomic، Feature Flag متمرکز، یا Backward-Compatible Message Schema)، نه این‌که فرض کنی درسته.

## 5. Distributed Deadlock — یه سناریوی واقع‌گرایانه (نه یه حادثهٔ خاص، بلکه یه الگوی تکرارشونده در میکروسرویس‌ها)

### چرا اینجا اسم یه شرکت خاص نمیارم
برخلاف موارد بالا، شرکت‌ها به‌ندرت پست‌مورتم عمومی برای Deadlockهای توزیع‌شده منتشر می‌کنن (چون معمولاً به‌عنوان "کندی موقت سیستم" یا "timeout" ثبت می‌شن، نه یه حادثهٔ نام‌گذاری‌شده). ولی این الگو در معماری میکروسرویس **خیلی رایجه** و ارزش داره با جزئیات ببینیش.

### سناریوی واقع‌گرایانه
فرض کن یه فروشگاه آنلاین داری با دو سرویس مستقل:
- **Order Service**: وقتی سفارش ثبت می‌شه، یه Lock روی رکورد "موجودی محصول" توی سرویس Inventory می‌گیره (از طریق یه HTTP call synchronous) تا مطمئن بشه موجودی حین محاسبهٔ قیمت نهایی تغییر نمی‌کنه.
- **Inventory Service**: وقتی موجودی یه محصول آپدیت می‌شه (مثلاً از انبار مرکزی sync می‌شه)، یه Lock روی رکورد "سفارش‌های در انتظار" توی Order Service می‌گیره تا مطمئن بشه هم‌زمان یه سفارش با موجودی قدیمی confirm نمی‌شه.

اگه هم‌زمان یه Request به Order Service بیاد (که منتظر Lock از Inventory هست) و یه Sync Job در Inventory Service اجرا بشه (که منتظر Lock از Order هست)، این دو **منتظر یکدیگر می‌مونن** — دقیقاً همون Circular Wait کلاسیک، ولی حالا بین دو process مستقل که هیچ‌کدوم دید کاملی از این‌که "کی منتظر کیه" ندارن.

### چرا کشف کردنش سخت‌تره
توی یه process، runtime می‌تونه با بررسی گراف Lockها Deadlock رو تشخیص بده. توی این سناریو، هیچ‌کدوم از دو سرویس نمی‌دونه اون یکی هم منتظره — فقط هر دو یه Timeout HTTP می‌گیرن که به نظر یه "کندی شبکه" میاد، نه یه Deadlock واقعی. تیم‌های مهندسی معمولاً هفته‌ها طول می‌کشه تا بفهمن این کندی‌های متناوب، الگوی یه Deadlock دوره‌ای بین دو سرویسه، نه یه مشکل performance ساده.

### راه‌حل واقعی که تیم‌ها معمولاً می‌رسن بهش
- **حذف Synchronous Lock بین سرویس‌ها**: به‌جای اینکه Order Service منتظر Lock از Inventory بمونه، از **Optimistic Concurrency** (چک کردن موجودی در لحظهٔ commit، نه گرفتن Lock از قبل) یا از **Event-Driven** (Inventory یه Event می‌فرسته، Order به‌صورت async واکنش نشون می‌ده) استفاده می‌کنن.
- **Timeout کوتاه + Circuit Breaker**: به‌جای صبر نامحدود، بعد از X میلی‌ثانیه Timeout بده و کل عملیات رو retry یا fail کن (Deadlock واقعی رو به یه خطای قابل مدیریت تبدیل می‌کنی).
- **قانون طلایی**: بین دو سرویس مستقل، هیچ‌وقت نباید یه Call synchronous منتظر Call synchronous دیگه‌ای از همون مسیر برگردون باشه (یعنی از یه گراف وابستگی synchronous بدون چرخه مطمئن شو).

## 6. مشکل بلوکه‌شدن در Two-Phase Commit (2PC) — چرا XA Transaction در عمل کم‌طرفدار شد

### تئوری
2PC می‌خواد چند سیستم مستقل (مثلاً دو دیتابیس) رو atomic هماهنگ کنه: یه Coordinator از همه می‌پرسه «آماده‌ای Commit کنی؟»، اگه همه بله گفتن، بهشون می‌گه «حالا Commit کن».

### چرا این یه مشکل شناخته‌شدهٔ صنعتیه (نه فقط تئوری)
مشکل اصلی اینه: اگه Coordinator دقیقاً **بعد از این‌که همه گفتن "آماده‌ام"** ولی **قبل از فرستادن دستور نهایی Commit** از کار بیفته (crash کنه)، همهٔ Participantها توی یه حالت "منتظر" گیر می‌کنن — Resource رو (مثلاً یه ردیف دیتابیس) قفل نگه می‌دارن چون نه می‌تونن Commit کنن نه Rollback، تا وقتی Coordinator برگرده و بگه نتیجه چی بود. این می‌تونه دقیقه‌ها تا ساعت‌ها طول بکشه، و در این مدت هیچ Transaction دیگه‌ای نمی‌تونه اون Resource رو لمس کنه.

این دقیقاً دلیلیه که فناوری‌هایی مثل **MSDTC** (Microsoft Distributed Transaction Coordinator) و **XA Transactions** در دنیای enterprise، با وجود این‌که سال‌ها استاندارد بودن، به‌مرور از خیلی معماری‌های High-Throughput کنار گذاشته شدن — چون:
1. **Blocking Problem بالا**: دقیقاً همون مشکلی که گفتیم.
2. **Throughput پایین**: هر Transaction باید منتظر کندترین Participant بمونه.
3. **Coupling زیاد**: همهٔ سیستم‌های درگیر باید از یه پروتکل مشترک (XA) پشتیبانی کنن، که خیلی از سیستم‌های مدرن (مثل اکثر Message Brokerها و NoSQL DBها) اصلاً پشتیبانی نمی‌کنن.

**چیزی که صنعت به‌جاش رفت سراغش**: Saga Pattern (که قبلاً توضیح دادیم) — قبول کردن اینکه هر سرویس Transaction محلی خودش رو انجام بده و در صورت خطا، به‌جای Rollback واقعی، از **Compensating Transaction** استفاده کنه. این باعث می‌شه هیچ Resource برای مدت طولانی قفل نمونه، به قیمت پیچیده‌تر شدن منطق error handling.

## 7. Write Skew — باگی که حتی Row-level Lock هم نمی‌بینتش

### تئوری
دو Transaction هم‌زمان، هر کدوم یه **ردیف متفاوت** می‌خونن و می‌نویسن (نه یه ردیف مشترک)، ولی با هم یه **Invariant سراسری** رو نقض می‌کنن که به هیچ‌کدوم از اون ردیف‌ها به‌تنهایی مربوط نیست.

### اتفاق مستند: تست Jepsen روی PostgreSQL
Jepsen به‌طور خاص PostgreSQL رو برای این کلاس دقیق از مشکل تست کرد. نتیجه این بود: در سطح **Isolation عادی** (Read Committed، که پیش‌فرض PostgreSQL هست)، این مشکل **اتفاق می‌افته** — دو Transaction که به نظر مستقل می‌رسن (هر کدوم یه ردیف جدا می‌خونن/می‌نویسن)، می‌تونن با هم یه ناسازگاری منطقی بسازن. PostgreSQL برای حل این مشکل یه سطح خاص به‌نام **Serializable Snapshot Isolation (SSI)** پیاده‌سازی کرده که Jepsen تأیید کرد این کلاس مشکل رو **درست جلوگیری می‌کنه** — ولی فقط اگه صریحاً از سطح `SERIALIZABLE` استفاده کنی، نه سطح پیش‌فرض.

### مثال کلاسیک (که در ادبیات علمی این حوزه، از جمله کتاب معروف *Designing Data-Intensive Applications* نوشتهٔ Martin Kleppmann، به‌عنوان نمونهٔ آموزشی اصلی استفاده می‌شه)
یه سیستم نوبت‌دهی پزشکی که قانونش اینه: **حداقل یک پزشک باید در هر شیفت on-call باشه**. دو پزشک هم‌زمان از اپ درخواست می‌کنن که خودشون رو off-call کنن:

```sql
-- Transaction دکتر A (روی کانکشن ۱)
SELECT COUNT(*) FROM doctors WHERE shift_id = 5 AND on_call = true;
-- نتیجه: 2 (من و دکتر B هر دو on-call هستیم)
-- پس امنه که من off بشم
UPDATE doctors SET on_call = false WHERE id = 'A';

-- Transaction دکتر B (هم‌زمان، روی کانکشن ۲)
SELECT COUNT(*) FROM doctors WHERE shift_id = 5 AND on_call = true;
-- نتیجه: 2 (چون Transaction A هنوز commit نشده، B هم می‌بینه هنوز 2 نفریم)
-- پس امنه که من هم off بشم
UPDATE doctors SET on_call = false WHERE id = 'B';

-- نتیجهٔ نهایی: هر دو کوئری COMMIT می‌شن، هر دو ردیف مجزا آپدیت شدن،
-- هیچ Row-level Lock نقض نشده، ولی حالا صفر پزشک on-call داریم!
```

**چرا Row-level Lock کمکی نمی‌کنه**: چون هر Transaction روی ردیف **خودش** (شناسهٔ خودش) می‌نویسه، نه روی ردیف اون یکی. یه Lock معمولی روی رکورد دکتر A، جلوی خوندن یا نوشتن روی رکورد دکتر B رو نمی‌گیره — درحالی‌که مشکل واقعی، ناسازگاری بین **نتیجهٔ COUNT روی کل شیفت** است، نه یه رکورد خاص.

**راه‌حل واقعی**:
- استفاده از سطح Isolation واقعی `SERIALIZABLE` (که PostgreSQL با SSI پیاده‌سازی درستی داره، طبق تست Jepsen).
- یا یه `CHECK constraint` سراسری در سطح دیتابیس (پیچیده‌تر برای پیاده‌سازی).
- یا یه Lock صریح روی یه ردیف نماینده (مثلاً یه ردیف "shift_lock" که هر دو Transaction قبل از تصمیم‌گیری باید بگیرنش، نه ردیف خودشون).

## 8. Out-of-Order Delivery — چرا Partitioning در Kafka/RabbitMQ صرفاً برای Scale نیست

### تئوری
وقتی چند Consumer به‌صورت موازی از یه صف می‌خونن (که خودمون قبلاً برای بالا بردن throughput پیشنهاد دادیم!)، هیچ تضمینی نیست که پیام‌ها به همون ترتیبی که فرستاده شدن پردازش بشن — چون سرعت پردازش هر Consumer متفاوته.

### چرا این یه مسئلهٔ شناخته‌شدهٔ صنعتیه
این دقیقاً دلیلیه که Kafka از اول با مفهوم **Partition** طراحی شده: Kafka **فقط داخل یه Partition** ترتیب رو تضمین می‌کنه، نه در کل Topic. این یه انتخاب طراحی آگاهانه‌ست، نه یه محدودیت اتفاقی — چون تضمین ترتیب سراسری با موازی‌سازی کامل ذاتاً در تضاده (یا ترتیب داری یا موازی‌سازی کامل، نمی‌تونی هر دو رو با هم بدون هزینه داشته باشی).

**پیامد عملی**: اگه بدون توجه به این موضوع، پیام‌های `OrderCreated` و `OrderCancelled` مربوط به یه سفارش رو به Partitionهای/Consumerهای متفاوت بفرستی، ممکنه `OrderCancelled` قبل از `OrderCreated` پردازش بشه — و یه سفارش لغوشده، دوباره به‌اشتباه فعال بشه.

**راه‌حل استانداردی که صنعت استفاده می‌کنه**: انتخاب یه **Partition Key معنادار** (مثل `OrderId`) که تضمین کنه همهٔ پیام‌های مربوط به یه سفارش، همیشه به همون Partition (و در نتیجه همون Consumer) برن و به‌ترتیب پردازش بشن. توی RabbitMQ معادلش استفاده از **Consistent-Hash Exchange** با همون کلید هست. این یه نکتهٔ ظریفه که خیلی از توسعه‌دهنده‌ها موقع طراحی اولیهٔ سیستم صف پیام نادیده می‌گیرنش و بعداً با یه باگ عجیب (که فقط زیر بار بالا رخ می‌ده) روبه‌رو می‌شن.

## جمع‌بندی: جدول کامل برای مرور سریع قبل از مصاحبه

| مسئله | ریشه | اتفاق واقعی مستند | راه‌حل صنعتی |
|---|---|---|---|
| Two Generals Problem | شبکهٔ غیرقابل‌اعتماد، عدم قطعیت دریافت پیام | مکانیزم Idempotency Key در Stripe | Idempotency Key + کش پاسخ |
| Clock Skew / LWW | نبود ساعت مشترک بین نودها | از دست رفتن ۷۱٪ نوشته در Riak؛ از دست رفتن نوشتهٔ majority در MongoDB | Lamport/Vector Clock، یا TrueTime (Google Spanner)، یا CRDT |
| Split-Brain | Network Partition + Leader Election مستقل هر طرف | قطعی ۲۴ ساعتهٔ GitHub از یه Partition ۴۳ ثانیه‌ای | Quorum-based Consensus (Raft/Paxos) + Fencing Token |
| Partial Failure در Deployment | عدم atomic بودن تغییر حالت روی چند نود | ضرر ۴۴۰ میلیون دلاری Knight Capital | Atomic/Rolling Deployment + Backward-Compatible Schema |
| Distributed Deadlock | Circular Wait بین سرویس‌های مستقل بدون دید مشترک | الگوی رایج در معماری میکروسرویس (بدون حادثهٔ نام‌گذاری‌شدهٔ عمومی) | حذف Lock synchronous بین سرویس‌ها، Timeout کوتاه |
| 2PC Blocking Problem | Coordinator تک‌نقطه‌ی شکست در پروتکل Commit | مشکل شناخته‌شدهٔ XA/MSDTC در enterprise systems | Saga Pattern + Compensating Transaction |
| Write Skew | Invariant سراسری که به یه رکورد خاص مربوط نیست | تأیید توسط تست Jepsen روی PostgreSQL (Read Committed آسیب‌پذیره) | Serializable Isolation واقعی، یا Lock روی رکورد نماینده |
| Out-of-Order Delivery | پردازش موازی بدون رعایت ترتیب | محدودیت طراحی شناخته‌شدهٔ Kafka (ترتیب فقط داخل Partition) | Partition Key معنادار / Consistent-Hash Exchange |

**یه نکتهٔ آخر برای دفاع از عنوانت**: تقریباً همهٔ این هشت مورد از **سه فرض ازدست‌رفته** میان که تو یه process تک‌هسته‌ای مجانی داری ولی توی Distributed System باید با هزینه دوباره بسازیشون: **حافظهٔ مشترک، ساعت مشترک، و دید کامل و آنی از وضعیت کل سیستم**. اگه بتونی هر سؤال مصاحبه رو به این سه فرض ازدست‌رفته وصل کنی، نشون می‌دی که فقط اسم تکنولوژی‌ها رو حفظ نکردی، بلکه **چرایی ریشه‌ای** مسئله رو فهمیدی — که دقیقاً همون چیزیه که یه Specialist واقعی رو از یه توسعه‌دهندهٔ معمولی جدا می‌کنه.
