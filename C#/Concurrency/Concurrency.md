# Concurrency: مفاهیم پایه از CPU تا Thread و Task

## 1. Interview Relevance Summary

این یادداشت **پیش‌زمینهٔ سخت‌افزار و OS** برای Concurrency و Multi-threading را پوشش می‌دهد: از نقش CPU و Program Counter تا Multi-tasking، تفاوت Concurrency و Parallelism، و مدل حافظهٔ Process و Thread. در مصاحبهٔ Backend انتظار نمی‌رود جزئیات CPU یا Batch Processing را عمیق بدانید، اما این موارد به شما کمک می‌کنند:

- تفاوت **Concurrency** و **Parallelism** را با تعریف درست و بدون اشتباه توضیح دهید (در هر لحظه یکی روی CPU در مقابل واقعاً هم‌زمان روی چند هسته)
- بگویید چرا **Context Switch** بین Thread از Process ارزان‌تر است (فقط stack و register؛ heap و کد مشترک است)
- **Thread Pool** و **Task** را به‌عنوان abstraction بالاتر از Thread و دلیل استفاده از آن‌ها (کاهش overhead ایجاد thread) توضیح دهید
- رابطهٔ **Process، Thread، حافظهٔ مشترک (heap، کد) و جدا (stack، register)** را بدانید و چرا همین مشترک بودن heap منبع race condition است

برای جزئیات sync primitives، async/await، Deadlock و Concurrent collections به فایل **Concurrency and multi Threading.md** مراجعه کنید.

## 2. CPU، OS و اجرای برنامه

### CPU چه کار می‌کند؟

**وظیفهٔ CPU** فقط یکی است: اجرای **دستورالعمل‌ها (instructions)** که در حافظهٔ RAM قرار دارند. CPU اصلاً نمی‌داند «برنامه» چیست — نه فتوشاپ را می‌شناسد، نه مرورگر را. به‌طور ساده: آدرسی از RAM می‌خواند، دستور را اجرا می‌کند (مثلاً جمع دو عدد)، نتیجه را جایی در RAM می‌نویسد، و به آدرس بعدی می‌رود. هر معماری (Intel، AMD، ARM) مجموعه‌ای از این دستورالعمل‌ها را تعریف کرده است. پس **قلب اجرا همین چرخهٔ خواندن دستور → اجرا → نوشتن نتیجه** است.

این دستورالعمل‌ها یا مستقیم به CPU داده می‌شوند یا — در دنیای واقعی — از طریق **سیستم‌عامل (OS)**. یعنی **OS واسط بین برنامهٔ ما و سخت‌افزار** است: وقتی شما یک برنامه را اجرا می‌کنید، OS آن را از دیسک در RAM لود می‌کند و یک **Program Counter** (اشاره‌گر به آدرس دستور بعدی) تنظیم می‌کند. CPU از آن به بعد فقط «خط به خط» جلو می‌رود تا جایی که برنامه تمام شود یا OS اجرا را به برنامهٔ دیگری بسپارد.

**چرا این برای Concurrency مهم است؟** چون در هر لحظه فقط **یک** دستور روی **یک** هسته اجرا می‌شود. پس «چند کار همزمان» یا با سوئیچ سریع بین کارهاست (Concurrency) یا با چند هسته که واقعاً هم‌پوشانی دارند (Parallelism).

### از کد منبع تا اجرا در .NET

قبل از اینکه CPU دستور اجرا کند، کد ما باید به **زبان ماشین** (همان دستورالعمل‌های قابل‌اجرا توسط CPU) برسد. در **.NET** این مسیر دو مرحله دارد:

1. **کامپایل به IL**: کد C# (یا F# و غیره) به **IL (Intermediate Language)** تبدیل و در فایل‌های DLL ذخیره می‌شود. IL مستقل از نوع CPU و OS است.
2. **اجرا با CLR**: **CLR** (Common Language Runtime) — شبیه JVM در جاوا — یک **ماشین مجازی** است: وقتی برنامه اجرا می‌شود، IL را لود می‌کند و با **JIT (Just-In-Time)** همان‌طور که هر متد فراخوانی می‌شود، آن را به زبان ماشین همان ماشین کامپایل می‌کند. پس کد واقعی که روی CPU اجرا می‌شود، خروجی JIT است نه خود IL.

به مجموعهٔ این مراحل (از کد خوانا تا زبان ماشین) **کامپایل** گفته می‌شود. **چرا زبان میانی؟** تا یک بار بنویسیم و روی ویندوز، لینوکس و مک با یک DLL (یا مشابه آن) اجرا شود. در **C++** معمولاً در زمان کامپایل هدف (OS و معماری) مشخص است و خروجی مستقیم زبان ماشین است؛ پس برای هر پلتفرم باید جدا کامپایل کنیم. از **.NET 6/7** با **Native AOT** می‌توان برای یک OS مشخص مستقیماً به زبان ماشین کامپایل کرد و بدون JIT در آن محیط اجرا کرد؛ در عوض برخی قابلیت‌های runtime (مثل reflection گسترده) در AOT محدود است و در صورت نیاز باید مستندات را چک کرد.

## 3. Multi-Tasking در سطح OS

### چرا چند کار «همزمان»؟

CPU در هر لحظه فقط **یک** دستور از **یک** برنامه را اجرا می‌کند. اگر OS فقط یک برنامه را تا انتها اجرا می‌کرد، تا وقتی آن برنامه تمام نشده بود بقیه هیچ کاری نمی‌کردند و کاربر باید مدام منتظر می‌ماند. **Multi-tasking** یعنی OS به‌صورت ظاهری چند کار را «همزمان» پیش می‌برد: کمی برنامهٔ A، بعد کمی برنامهٔ B، بعد دوباره A، و همین‌طور. در عمل با **سوئیچ سریع** بین برنامه‌ها این حس ایجاد می‌شود که همه با هم در حال اجرا هستند. واحد اجرا در این سطح **process** است: هر برنامهٔ در حال اجرا معمولاً حداقل یک process دارد. مثلاً با کلیک روی یک فایل، OS یک process ایجاد می‌کند و آن فایل را به‌عنوان پارامتر به آن می‌دهد.

مدیریت این سوئیچ با **Job Scheduler** انجام می‌شود: OS تصمیم می‌گیرد الان کدام process روی CPU باشد و **Program Counter** همان process را جلو می‌برد. علاوه بر این، OS **منابع** را هم مدیریت می‌کند: حافظه (هر process محدودهٔ آدرس خودش را دارد و دسترسی خارج از آن منجر به **Trap** و در نهایت exception می‌شود)، شبکه، فایل، و غیره. پس هر process در فضای خودش اجرا می‌شود و به‌صورت پیش‌فرض به حافظهٔ processهای دیگر دسترسی ندارد.

![[Pasted image 20250116005309.png]]

### Context Switch چیست و چرا گران است؟

هر بار که OS از یک process به process دیگر برود، یک **Context Switch** رخ می‌دهد: باید وضعیت process فعلی (registerها، اشاره‌گر stack، و هر چیزی که برای ادامهٔ بعدی لازم است) **ذخیره** شود و وضعیت process بعدی **بارگذاری** شود. علاوه بر این، **cache** داخل CPU برای process قبلی پر شده؛ با عوض شدن process، آن داده‌ها دیگر به‌کار process جدید نمی‌آیند و cache باید کم‌کم با دادهٔ process جدید پر شود. پس context switch **زمان‌بر** است و **سربار** روی CPU ایجاد می‌کند.

**راه‌حل سخت‌افزاری**: **چند هستهٔ فیزیکی**. اگر دو هسته داشته باشیم، دو process می‌توانند واقعاً در یک لحظه اجرا شوند و تعداد context switch کمتر می‌شود. توجه کنید با دو برابر کردن هسته، زمان کل لزوماً نصف نمی‌شود؛ همگام‌سازی و تقسیم کار خودش هزینه دارد. **هستهٔ منطقی (Logical Core)**: یک هستهٔ فیزیکی را می‌توان به چند واحد مجازی تقسیم کرد (مثلاً Hyper-Threading)؛ هر واحد صف و registerهای مجازی خودش را دارد. OS به این واحدها هم کار می‌دهد تا با همان تعداد هستهٔ فیزیکی، سوئیچ بین کارها سبک‌تر شود.

## 4. Concurrency در برابر Parallelism

این دو اصطلاح در مصاحبه زیاد می‌آیند و باید دقیق تفکیک شوند.

### Concurrency (همروندی)

چند کار **در بازه‌های زمانی مختلف** پیش می‌روند؛ OS (یا runtime) آن‌قدر سریع بین آن‌ها سوئیچ می‌کند که به‌نظر می‌رسد «همزمان» هستند. **در یک لحظهٔ مشخص ممکن است فقط یک کار واقعاً روی CPU در حال اجرا باشد.** مثال: یک هسته، سه کار — CPU یک میلی‌ثانیه به کار اول، بعد به دوم، بعد به سوم، و دوباره به اول می‌پرد. از دید کاربر هر سه جلو می‌روند، ولی در هر لحظه فقط یکی اجرا می‌شود.

### Parallelism (موازی‌سازی)

در **یک واحد زمانی** واقعاً **بیش از یک** کار روی CPU در حال اجرا است؛ معمولاً روی **چند هسته**. مثال: دو هسته، دو کار — هر هسته یکی را اجرا می‌کند؛ پس در همان لحظه هر دو جلو می‌روند.

**خلاصه برای مصاحبه**: Concurrency = «چند کار در حال پیشرفت»، حتی اگر در هر لحظه فقط یکی روی CPU باشد. Parallelism = «چند کار در همان لحظه روی CPU» (با چند هسته یا واحد اجرا).

![[Pasted image 20250116012551.png]]

تا اینجا واحد کار را در سطح **process** دیدیم. همان ایده در سطح **thread** داخل یک process هم برقرار است: **multi-threading** یعنی چند thread در یک process داریم که یا با سوئیچ سریع (Concurrency) یا روی چند هسته (Parallelism) اجرا می‌شوند. از این به بعد تمرکز روی **threadهای داخل یک process** و ابزارهای .NET برای آن است.

## 5. Processها، ارتباط و زمان‌بندی

### ارتباط بین Processها

دو process در یک ماشین **حافظهٔ RAM مشترک** ندارند؛ هر کدام فضای آدرس خودشان را دارند. پس برای ارتباط باید از **مکانیزم‌های OS** استفاده کنند: **socket**، **named pipe**، **فایل نگاشت‌شده در حافظه (memory-mapped file)**، یا سرویس‌های دیگر. این یعنی هر گونه «اشتراک داده» بین دو process باید عمداً و از طریق این APIها انجام شود.

### Starvation و نقش Scheduler

اگر یک منبع (مثلاً یک فایل یا یک lock بین processها) توسط یک process گرفته شده باشد و process دیگر به همان منبع نیاز داشته باشد، thread مربوط در آن process **block** می‌شود و تا آزاد شدن منبع صبر می‌کند. اگر طراحی یا زمان‌بندی غلط باشد، ممکن است یک process مدام منبع را بگیرد و process دیگر هرگز نوبت نگیرد — به این **قحطی (starvation)** گفته می‌شود. **Scheduler** OS جدولی از threadها و وضعیت هر process نگه می‌دارد و قبل از هر context switch تصمیم می‌گیرد کدام thread اجرا شود. **هزینهٔ context switch** باید از زمان مفید اجرای هر برنامه کمتر باشد؛ وگرنه CPU مدام مشغول جابه‌جا کردن context است و کار واقعی کم انجام می‌شود.

### Kernel Thread و User Thread؛ نقش .NET

در سطح **kernel**، OS threadهایی دارد که به هسته‌های CPU مپ شده‌اند. ایجاد یک **thread جدید** در kernel یعنی یک **system call**: OS باید فضای stack، ساختارهای داخلی و زمان‌بندی را آماده کند — این کار **زمان‌بر** است. در سطح **user**، کتابخانه‌ها و runtimeها (مثل .NET) می‌توانند مدل ساده‌تری به برنامه‌نویس بدهند: به‌جای اینکه برای هر کار کوچک یک thread جدید از OS بخواهیم، **Thread Pool** یک استخر از threadها را نگه می‌دارد و کارها را روی آن‌ها توزیع می‌کند؛ در نتیجه فراخوانی مستقیم و مکرر system call برای ساخت thread نداریم.

## 6. Process تک‌thread در برابر Multi-Threading

### حافظهٔ مشترک و جدا

وقتی یک **process** اجرا می‌شود، فضایی برای **کد** (دستورالعمل‌ها)، **heap** (اشیاء و دادهٔ پویا)، **stack** (فراخوانی توابع و متغیرهای محلی) و **registerها و program counter** دارد. در حالت ساده فقط یک **Main Thread** روی این فضا اجرا می‌شود.

در **multi-threading** داخل **همان** process:

| چه چیزی | وضعیت |
|--------|--------|
| **کد** | مشترک — همهٔ threadها همان دستورالعمل‌ها را اجرا می‌کنند |
| **Heap** | مشترک — همهٔ threadها به همان اشیاء دسترسی دارند |
| **Stack** | **جدا** برای هر thread — فراخوانی‌ها و متغیرهای محلی هر thread در stack خودش |
| **Register و PC** | **جدا** برای هر thread — هر thread نقطهٔ اجرای خودش را دارد |

پس **دادهٔ مشترک** (مثلاً یک فیلد یا یک لیست در heap) می‌تواند توسط چند thread هم‌زمان خوانده یا نوشته شود؛ همین جاست که **race condition** و نیاز به **همگام‌سازی** پیش می‌آید. جزئیات در **Concurrency and multi Threading.md**.

### چرا Context Switch بین Thread ارزان‌تر از Process است؟

برای عوض کردن **process**، OS باید جداول حافظه، محدودهٔ آدرس، و منابع اختصاص‌یافتهٔ آن process را هم در نظر بگیرد و مسیر طولانی‌تری در kernel طی کند. برای عوض کردن **thread** داخل همان process، فضای مشترک (کد و heap) عوض نمی‌شود؛ فقط **stack و register** thread قبلی ذخیره و stack و register thread بعدی بارگذاری می‌شوند. پس دادهٔ کمتری جابه‌جا می‌شود و context switch **سبک‌تر** است.

## 7. Thread Pool و Task

### چرا ایجاد Thread گران است؟

هر بار که یک **thread جدید** از OS بخواهیم، باید اتفاق‌های زیادی بیفتد: اختصاص **stack** (معمولاً در حد یک مگابایت یا بیشتر)، ثبت thread در scheduler، و آماده‌سازی ساختارهای داخلی kernel. این کار **زمان‌بر** است و اگر برای هر کار کوچک یک thread جدید بسازیم و بعد تمامش کنیم، بخش زیادی از CPU صرف همین ایجاد و نابودی می‌شود.

### Thread Pool چه می‌کند؟

**Thread Pool** یک **استخر از threadهای از قبل ساخته‌شده** است که runtime (مثلاً CLR) آن را نگه می‌دارد. وقتی شما یک **کار (work item)** می‌فرستید، آن کار در یک **صف** قرار می‌گیرد و یکی از threadهای استخر — که در آن لحظه آزاد است — آن را برمی‌دارد و اجرا می‌کند. بعد از اتمام، آن thread دوباره به استخر برمی‌گردد و **ساخته یا نابود نمی‌شود**؛ فقط **وضعیتش** (مثلاً در حال اجرای کدام کار) عوض شده. پس **allocation مکرر** نداریم و استفاده از CPU و حافظه بهینه‌تر می‌شود. ایده شبیه **Object Pool** است: به‌جای ساخت و تخریب مکرر، از یک استخر استفاده می‌کنیم.

### Task یعنی چه؟

در .NET معمولاً به‌جای کار مستقیم با `Thread`، با **Task** کار می‌کنیم. **Task** یک **واحد کار** است که ممکن است روی یک thread از Thread Pool (یا گاهی thread جدا) اجرا شود. شما «چه کاری باید انجام شود» را به‌صورت Task تعریف می‌کنید؛ runtime تصمیم می‌گیرد آن را روی کدام thread و چه زمانی اجرا کند. پس Task یک **abstraction سطح بالا** روی thread است: شما با «کار» سروکار دارید، نه با «thread». مزیت‌های دیگر Task شامل پشتیبانی از **نتیجه (result)**، **لغو (cancellation)** و **ادامه با async/await** است — همهٔ این‌ها در فایل **Concurrency and multi Threading.md** آمده است.

![[Pasted image 20250116161955.png]]

Thread Pool را می‌توان با حداقل و حداکثر تعداد thread سفارشی کرد، اما معمولاً بهتر است به **تنظیمات پیش‌فرض** CLR اعتماد کنیم. یک مزیت مهم دیگر: اگر یک thread منتظر **I/O** (مثلاً پاسخ شبکه) بماند، با **async/await** می‌توان آن thread را به استخر **برگرداند** و وقتی I/O تمام شد، ادامهٔ کار روی یک thread دیگر از استخر اجرا شود. به این ترتیب thread در زمان انتظار block نمی‌ماند و استخر برای کارهای دیگر آزاد است.

## 8. Paging و Swapping (خلاصهٔ OS)

در سطح OS حافظهٔ هر process به **صفحه (page)** تقسیم می‌شود. **Paging** یعنی این صفحه‌ها بسته به نیاز از **دیسک** (HDD/SSD) به **RAM** آورده یا از RAM به دیسک برده می‌شوند تا فضای RAM برای کارهای فعال آزاد بماند. به جابه‌جایی دادهٔ process بین RAM و دیسک **Swapping** گفته می‌شود. برای مصاحبهٔ Backend معمولاً همین سطح کلی کافی است؛ جزئیات بیشتر مربوط به درس OS است.

## 9. منابع اشتراکی و Thread Safety (مهم)

چون **heap** بین threadهای یک process **مشترک** است، هر شیء در heap می‌تواند از چند thread در یک لحظه خوانده یا نوشته شود. اگر **همگام‌سازی** نکنیم، **race condition** پیش می‌آید: دو thread هم‌زمان یک مقدار را بخوانند، تغییر دهند و بنویسند و یکی از تغییرها از دست برود؛ یا ساختار داخلی یک collection خراب شود و برنامه crash کند. پس برای هر **منبع اشتراکی** (یک لیست، دیکشنری، یا هر حالت مشترک) باید یا از **lock** (یا primitiveهای دیگر) استفاده کنیم یا از **collectionهای thread-safe** مثل **ConcurrentDictionary** و **ConcurrentQueue**.

**اشتباه رایج و خطرناک**: این باور که «List برای نوشتن همزمان مناسب نیست ولی **Dictionary** برای همزمانی درست است» **کاملاً نادرست** است. در .NET هر دو **List** و **Dictionary** برای دسترسی همزمان از چند thread **thread-safe نیستند**. استفادهٔ همزمان بدون lock یا بدون concurrent collection می‌تواند به خرابی داده یا crash منجر شود. راه‌حل درست: **lock** (یا Monitor) دور دسترسیهای مشترک، یا **ConcurrentDictionary** / **ConcurrentQueue** و مشابه آن‌ها برای سناریوهای مناسب. جزئیات و trade-offها در **Concurrency and multi Threading.md**.

## 10. Async و سبک‌های برنامه‌نویسی

**برنامه‌نویسی async** در ASP.NET و .NET به‌طور کلی شکلی از **Concurrency** است: به‌جای اینکه یک thread منتظر تمام شدن I/O (مثلاً پاسخ شبکه یا خواندن فایل) بماند و **block** شود، با **callback** یا در .NET با **async/await** به runtime می‌گوییم وقتی I/O تمام شد ادامهٔ کار را اجرا کن؛ در این فاصله آن thread به **Thread Pool** برمی‌گردد و می‌تواند کار دیگری انجام دهد. پس با همان تعداد thread، درخواست‌های بیشتری سرو می‌شوند. سبک‌های دیگر شامل **Reactive Programming** (مثل Rx یا event-driven) است که در آن به رویدادها واکنش نشان می‌دهیم، و الگوهایی مثل **Wait و Polling** برای هماهنگی بین threadها. برای جزئیات async/await، CancellationToken، ConfigureAwait و بهترین روش‌ها به **Concurrency and multi Threading.md** مراجعه کنید.

## 11. Key Interview Talking Points

- **تفاوت Concurrency و Parallel**: Concurrency = چند کار در بازه‌های زمانی با سوئیچ سریع (در هر لحظه ممکن است فقط یکی روی CPU باشد). Parallel = در یک لحظه واقعاً بیش از یک کار روی CPU (چند هسته).
- **چرا Context Switch بین thread از process ارزان‌تر است**: فقط stack و register عوض می‌شوند؛ heap و کد مشترک است و جابه‌جا نمی‌شوند. در switch بین process جداول حافظه و منابع هم عوض می‌شوند.
- **Thread Pool**: استخر از قبل ساخته‌شدهٔ threadها؛ کارها در صف قرار می‌گیرند و threadهای استخر آن‌ها را اجرا می‌کنند؛ overhead ایجاد/حذف thread کم می‌شود. Task = واحد کار (abstraction سطح بالا) که معمولاً روی Thread Pool اجرا می‌شود.
- **Process و Thread؛ حافظه**: process = فضای آدرس و منابع جدا. در یک process چند thread: کد و heap **مشترک**، stack و register **جدا** برای هر thread. همین مشترک بودن heap منبع race condition است.
- **منابع اشتراکی**: List و Dictionary معمولی برای دسترسی همزمان thread-safe نیستند؛ Dictionary هم مثل List ناامن است. از lock یا concurrent collections استفاده شود.

## 12. Common Mistakes & Red Flags

- **این باور که «برای نوشتن همزمان به‌جای List از Dictionary استفاده کنیم»** — هر دو در صورت دسترسی همزمان بدون sync ناامن‌اند؛ باید از ConcurrentDictionary یا lock استفاده شود.
- **اشتباه گرفتن Concurrency و Parallel** در مصاحبه (مثلاً گفتن اینکه «هر دو یعنی همزمان»).
- **نادیده گرفتن هزینهٔ Context Switch** و ایجاد تعداد زیاد thread بدون استفاده از Thread Pool.
