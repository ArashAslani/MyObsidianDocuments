معماری نرم افزار چیست؟
دقیقا مثل معماری و نقشه ساختمان هست.
دقیقا مشخص هست که این ساختمان برای چی و کجا ساخته شده.
باید با نگاه اول مشخص باشه که یک معماری برای چه بیزنسی چیده شده.
هدف معماری بهبود چرخه حیات سیستمه.
معماری خوب باعث میشه درک، نگهداری و استقرار سیستم آسون بشه.
هدف نهایی به حداقل رسوندن هزینه طول عمر سیستم و به حداکثر رسوندن بهرهوری نرم افزار و پوسه برنامه نویسیه.
یک معمار باید روی بیزنس و use case های مسئله باشه.
نگاه فنی و انتخاب ابزار به وسیله چرخه تعامل برنامه نویس فنی و معمار نرم افزار مشخص میشود.

 Entities Layer: که به لایه Core یا Domain هم میشناسیمش. در این لایه طبق اصل کم کردن وابستگی ها و رسیدن به DIP و OCP نباید هیچ تکنولوژی و کتابخونه ای استفاده شود. همچنین به تکنولوژی های وابسته با آن مثل نوع دیتابیس فکر نمیکنیم. و فقط با زبان انتخاب شده باید نوشته شود به این معنی که باید pure باشد.
 در این لایه برای هر موجودیت تمام enum ها Exception ها و Contract ها در خوده مدل قرار میگیرند.
entity ها باید به صورت Rich Model پیاده سازی شوند.
در معماری های قبلی نگاه Anemic Model داشتیم. به این معنی که entity های ما صرفا یکسری prop بودن که در لایه های دیگر کنترل میشدن.
اما Rich Model نگاه متفاوتی دارد یعنی باید تمام مسائل مربوط به دیتا همراه دیتا باشد. و نباید بتوانیم از خارج از Model تغییراتی در اون انجام بدیم.
Unit Test در این مدل بسیار خوب پیاده سازی میشود. 
مثال Order و OrderDetails 

Application Layer : 
بهتره قوانین نام گذاری و پوشه بندی باید در تمام لایه ها یکسان باشد و مشابه با Domain.
این لایه یک ارکستریشن هست یعنی مواردی که لازم هست رو کنار هم میگذاره تا یک عملیات و use case به سرانجام برسه.
وظیفه صدا زدن قابلیت های موجود Domain را دارد.

Infrastructure Layer :
 این لایه از تکنولوژی های مختلف کمک میگیرد تا به وسیله آن ها عملیات های معرفی شده Domain را عملیاتی و پیاده سازی کنند.
 مانند استفاده از سرویس های خارجی api
 
Contracts Layer :
میتوان برای اینترفیس های تکنولوژی ها مانند ارسال پیام و...
که در نهایت ارتباط بین Domain و Contrancts اتفاق می افتد و Application با Contracts که ارتباط بین Domain و Application از بین میرود.
که در لایه Infra در پیاده سازی به عنوان Services میشناسیم و در انجا پیاده سازی میکنیم.

Presentation Layer :
لایه درگیر با کاربر است که نیاز های خود را از Application صدا میزند.
Abstraction ها و Implementation ها در این لایه به DI Container اضافه میشوند.
تفاوتی نمیکند به چه صورت سرویس میدهد.

Bootstrapper/Config Layer :
لایه وابسته به Presentation هست که Abstraction ها به Implementation ها متصل میشوند و DI را عملیاتی میکنیم.
تا در DI Container  فانکشن های داخل این لایه را صدا بزنیم.

که در صورت استفاده از Config Layer ارتباط بین Presentation و Application برداشته شده بینشان Config Layer قرار میگیرد.
