# بخش اول: نقشه کلی معماری‌ها (فاز ۱)

اول یه نمای کلی از معماری‌هایی که هست و چطور به هم ربط دارن.

## طبقه‌بندی معماری‌ها (و الگوهای مرتبط)

### قبل از شروع: معماری، اصل، الگو

- **معماری / سبک معماری**: شکل کلی ساختار سیستم و نحوهٔ ارتباط اجزا؛ مثل `Monolith`, `Layered`, `Hexagonal`, `Clean Architecture`, `Microservices`, `Modular Monolith`.  
- **اصل (Principle / Law)**: قاعده‌ای که به ما کمک می‌کند طراحی بهتری داشته باشیم؛ مثل `SOLID`, `DRY`, «قانون کانوی»، `Bounded Context`, «Autonomy + Alignment». این‌ها خودشان «معماری» نیستند، اما روی معماری اثر می‌گذارند.  
- **الگوی معماری (Pattern)**: راه‌حل تکرارشونده در سطح طراحی/معماری که روی یک معماری سوار می‌شود؛ مثل `CQRS`, `Event Sourcing`, `Saga`. این‌ها معمولاً کنار یکی از سبک‌های معماری استفاده می‌شوند، نه به‌عنوان جایگزین کامل آن‌ها.

در جدول‌های این سند، سعی شده **معماری‌ها** (مثل Monolith، Clean، Microservices) از **الگوها و اصول** (مثل [[CQRS]]، [[SOLID]]، [[Conway's Law]]) جدا باشند؛ هر جا CQRS یا Event-Driven را کنار بقیه می‌بینی، منظور «الگوی معماریِ مکمل» است، نه یک سبک مستقل مثل Monolith.

### تعریف هر معماری

**معماری Monolith:** یک برنامه واحد که همه عملکردها در آن قرار دارد. ساده برای شروع، سخت برای مقیاس و نگهداری در بلندمدت.

**معماری Data-Centric:** دیتابیس مرکز تصمیم است. منطق بیزنس کم یا در DB (Stored Procedure) یا در لایه نازک بالای آن.

**معماری Layered (N-Tier):** لایه‌های افقی: UI، Business Logic، Data Access. معمولاً ۳ یا ۴ لایه. ساده و قابل فهم.

**معماری Hexagonal (Ports & Adapters):** اینجا Domain در مرکز هست. Port = Interface. Adapter = پیاده‌سازی (مثل DB، REST). تست‌پذیری بالا.

**معماری Onion:** مثل پیاز. Domain در هسته. لایه‌های بیرونی به درونی وابسته‌اند. هیچ وابستگی به سمت بیرون نیست.

**معماری Clean:** نسخه Uncle Bob از همان ایده. نام‌های مشخص برای لایه‌ها. تمرکز روی Business Rules و Dependency Rule.

**معماری Modular Monolith:** اینجا Monolith با مرزهای واضح. هر ماژول مستقل است. راه میانی قبل از رفتن به Microservices.

**الگو CQRS:** یعنی جداسازی Command (نوشتن) و Query (خواندن). مدل write با مدل read فرق داره. مثلاً برای ثبت سفارش یه مدل داری، برای نمایش گزارش یه مدل دیگه. وقتی read ها خیلی زیادن (مثلاً داشبورد با هزاران رکورد) می‌تونی read رو جدا scale کنی، حتی با دیتابیس جدا یا Read Replica. توی .NET با MediatR خیلی استفاده میشه.

**Event-Driven:** به جای اینکه سرویس الف مستقیم سرویس ب رو صدا بزنه، یه Event میفرسته (مثلاً OrderPlaced). هر کس گوش بده، کار خودش رو می‌کنه. لوز کاپلینگ. مناسب سیستم‌های توزیع‌شده. اشکالش اینه که debug و tracing سخت‌تر میشه، و ordering رو باید درست مدیریت کنی.

**Microservices:** سرویس‌های کوچک و مستقل. هر کدوم تیم و دیتابیس خودش داره. deploy مستقل. ولی هزینه‌اش بالاست: شبکه، monitoring، DevOps.

### رابطه بین معماری‌ها

**جایگزین (یا این یا آن):**
- Data-Centric ↔ Domain-Centric
- Monolith ↔ Microservices
- Layered ساده ↔ Clean/Hexagonal/Onion

**مکمل (با هم استفاده می‌شوند):**
- Clean + DDD
- Clean + CQRS
- Microservices + Event-Driven
- Microservices + CQRS
- Modular Monolith + Clean (در هر ماژول)

**سلسله‌مراتب (یکی زیرمجموعه یا نسخه پیشرفته دیگری):**
- Hexagonal، Onion، Clean ← همه Domain-Centric هستند
- Modular Monolith ← نوعی Monolith با مرزهای ماژولار

## معماری نرم‌افزار یعنی چی؟

یه جورایی مثل نقشه ساختمونه. وقتی می‌خوای خونه بسازی، اول نقشه می‌کشی. معماری نرم‌افزار هم همینه: قبل از کد زدن، مشخص می‌کنی اجزا کجا باشن، چطور به هم وصل باشن، و چه کسی مسئول چی باشه.

**چرا اصلاً به معماری فکر کنیم؟**
سوال خوبیه. یه وقتی پروژه کوچیکه و همه چیز تو یه فایل یا چند کلاس خلاصه میشه. ولی وقتی رشد می‌کنه، اگه از اول فکر نکرده باشی کد کجا بره و منطق کجا باشه، بعداً گیر می‌کنی. تغییر یک چیز، ده تا چیز دیگه رو خراب می‌کنه. تست نوشتن غیرممکن میشه. تیم جدید نمی‌تونه سر در بیاره. معماری خوب این دردها رو کم می‌کنه.

**یک معماری خوب چیه؟**
با یه نگاه به ساختارش باید حدس بزنی برای چه بیزنسی نوشته شده. هدفش اینه که درک، نگهداری و deploy رو راحت‌تر کنه. در نهایت هزینه کل پروژه کمتر بشه و تیم راحت‌تر کار کنه.

**معمار نرم‌افزار چیکار می‌کنه؟**
روی بیزنس و use case ها تمرکز می‌کنه. انتخاب ابزار و تصمیمات فنی رو معمولاً با تیم انجام میده، نه تنهایی. معماری که همیشه حرف آخر رو میزنه و کسی رو گوش نمیده، معمولاً نتیجه‌اش بد میشه.

## دو رویکرد اصلی

### معماری Data-Centric

**ایده اصلی:** دیتابیس مرکز است. UI و Business Logic به صورت مستقیم با DB کار می‌کنند.

*[نمودار: Data-Centric — دیتابیس در مرکز، UI و Logic مستقیم به DB متصل]*

**مزایا:**
- توسعه سریع در ابتدا
- ساده برای پروژه‌های کوچک
- مناسب برای CRUD ساده

**معایب:**
- دیتابیس مرکز نرم‌افزار می‌شود
- اگر مرکز اشتباه انتخاب شود، refactor بسیار سخت است
- **Testable نیست** – بدون DB واقعی نمی‌توان unit test نوشت
- قوانین کسب‌وکار پراکنده و تکرارشونده می‌شوند
- Tight coupling بین لایه‌ها

**چه زمانی استفاده کنیم؟**
- دمو و پروتوتایپ
- زمان بسیار محدود
- پروژه‌های کوچک با منطق بیزنس کم
- **نه برای production طولانی‌مدت**

**Use Case چیست؟**
یک use case یعنی چند فرآیند که با هم یک سناریوی کسب‌وکار را کامل می‌کنند. مثلاً «خرید مشتری» که باید در انبار، حساب، موجودی و... کار انجام شود.

**سوال:** پس Data-Centric اصلاً نباید استفاده کنیم؟
نه، اشتباهه. برای دمو، پوک و پروژه‌های خیلی کوچک عالیه. مشکل وقتیه که با همون ساختار بخوای scale کنی یا منطق پیچیده اضافه کنی.

### معماری Domain-Centric

**ایده اصلی:** Domain در مرکز است. فریمورک‌ها و ابزارها در لایه‌های بیرونی هستند و به Domain وابسته‌اند، نه برعکس.

**مزیت کلیدی:** مستقل از فریمورک و ابزار. می‌توان دیتابیس، UI یا فریمورک را عوض کرد بدون اینکه Domain تغییر کند.

**معماری‌های معروف Domain-Centric:**

#### Hexagonal (Ports & Adapters)

*[نمودار: Hexagonal — Domain در مرکز، Port ها و Adapter ها]*

Domain در مرکز است. Port ها (interface ها) ورود و خروج را مشخص می‌کنند. Adapter ها پیاده‌سازی واقعی هستند (مثلاً SQL Server Adapter، REST API Adapter). هر وابستگی به سمت داخل (به Domain) است.

#### Onion Architecture
*[نمودار: Onion — Domain در هسته، لایه‌های دایره‌ای]*

Domain در هسته. لایه‌های بیرونی به لایه‌های درونی وابسته‌اند. هیچ لایه‌ای به لایه بیرونی‌تر وابسته نیست.

**تفاوت با Hexagonal:** Onion بیشتر روی لایه‌بندی تمرکز دارد؛ Hexagonal روی Port و Adapter.

## Clean Architecture

*[نمودار: Clean Architecture — لایه‌های Entities، Use Cases، Interface Adapters، Frameworks]*

**منبع:** کتاب Clean Architecture از Robert C. Martin (Uncle Bob)

**ایده اصلی:** Business Rules در مرکز. وابستگی‌ها به سمت داخل. لایه‌های بیرونی جزئیات (دیتابیس، UI، فریمورک) هستند.

### لایه‌های Clean Architecture

*[نمودار: لایه‌های Clean Architecture با جهت وابستگی]*

**قانون وابستگی (Dependency Rule):** وابستگی‌ها فقط به سمت داخل هستند. لایه‌های بیرونی به لایه‌های درونی وابسته‌اند؛ هرگز برعکس.

---

#### Entities Layer (Domain / Core)

به لایه Core یا Domain هم معروف است.

**اصول:**
- طبق DIP و OCP هیچ وابستگی به تکنولوژی یا کتابخانه خارجی نداشته باشد
- به نوع دیتابیس، فریمورک وب یا هر چیز زیرساختی فکر نکنیم
- فقط با زبان برنامه‌نویسی خالص نوشته شود – **Pure Domain**

**محتویات:**
- برای هر موجودیت: enum ها، Exception ها، Contract ها (Interface ها) در خود مدل
- Entity ها به صورت **Rich Model** پیاده‌سازی می‌شوند

**Anemic vs Rich Model:**

| Anemic Model | Rich Model |
|--------------|------------|
| Entity ها فقط prop دارند | Entity ها رفتار و قوانین دارند |
| منطق در لایه‌های دیگر | منطق داخل خود Entity |
| کنترل از خارج | Encapsulation و کنترل از داخل |

**چرا Rich Model؟**
- نمی‌توان از خارج به‌راحتی state نامعتبر ساخت
- Unit Test راحت‌تر است چون منطق در یک جا است
- تغییر قوانین بیزنس فقط در یک محل

**مثال:** `Order` و `OrderDetails` – قوانین مثل «حداقل یک آیتم در سفارش» یا «مجموع مقدار نباید منفی باشد» داخل خود Order باشند.

**نکته مصاحبه:** اگر Entity ها فقط DTO باشند و همه منطق در Service باشد، Anemic دارید، نه Rich.

---

#### Application Layer (Use Cases)

**نکته:** بهتر است قوانین نام‌گذاری و پوشه‌بندی در تمام لایه‌ها یکسان و مشابه Domain باشد.

**نقش:** این لایه **Orchestrator** است – کارها و سرویس‌های لازم را کنار هم می‌چیند تا یک use case تمام شود.

**وظیفه:**
- صدا زدن قابلیت‌های Domain
- هماهنگ کردن تراکنش‌ها
- **بدون منطق بیزنس پیچیده** – منطق در Domain است

**مثال:** برای «ثبت سفارش»، Application لایه: Order را از Domain می‌گیرد، Repository را صدا می‌زند، Domain Event ها را dispatch می‌کند. خودش «چگونه محاسبه شود» را نمی‌داند.

**نکته مصاحبه:** اگر Application لایه پر از if/else و منطق بیزنس باشد، یعنی منطق از Domain به لایه اشتباه رفته است.

---

#### Infrastructure Layer

**نقش:** پیاده‌سازی عملیات‌هایی که Domain تعریف کرده ولی خودش انجام نمی‌دهد.

**مثال‌ها:**
- Repository ها (دسترسی به دیتابیس)
- سرویس‌های خارجی (API، ارسال ایمیل، پیام‌رسان)
- File System
- کش
- Message Queue

**نکته:** Domain فقط Interface می‌شناسد. Infrastructure همان Interface را implement می‌کند.

---

#### Contracts Layer (Abstractions)

**نقش:** Interface های تکنولوژی‌ها و زیرساخت.

**چرا جدا؟**
- Domain فقط با Contract کار می‌کند
- Application هم با Contract کار می‌کند
- Infrastructure پیاده‌سازی Contract را می‌دهد

**مثال:** `IEmailSender`، `IOrderRepository`، `IMessageBus`

**جریان وابستگی:**
- Domain ← Contracts (Domain Interface ها را تعریف می‌کند)
- Application ← Domain, Contracts
- Infrastructure ← Contracts (پیاده‌سازی می‌کند)
- **بدون وابستگی مستقیم Domain به Application یا Infrastructure**

---

#### Presentation Layer

**نقش:** لایه درگیر با کاربر. می‌تواند Web API، MVC، Blazor، Console و... باشد.

**وظیفه:**
- دریافت درخواست کاربر
- فراخوانی Application (مثلاً یک Command/Query)
- برگرداندن پاسخ

**DI:** در این لایه معمولاً Abstraction ها به Implementation ها در DI Container متصل می‌شوند.

**تفاوت با بقیه:** این لایه می‌فهمد سرویس چطور ارائه می‌شود (REST، gRPC، و...) اما منطق بیزنس را نمی‌داند.

---

#### Bootstrapper / Config Layer

**نقش:** وابسته به Presentation است. Abstraction ها را به Implementation متصل می‌کند و DI را راه‌اندازی می‌کند.

**با Config Layer:**
- ارتباط مستقیم Presentation و Application کم می‌شود
- Config Layer بین آن‌ها قرار می‌گیرد
- Composition Root جایی است که همه‌چیز به هم وصل می‌شود

---

## سوالاتی که معمولاً برای میدل‌ها پیش میاد

**۱. چرا اصلاً لایه‌بندی؟ نمیشه همه چیز تو یه پروژه بود؟**
میشه، ولی وقتی پروژه بزرگ میشه، پیدا کردن یه باگ یا اضافه کردن یه feature شبیه پیدا کردن سوزن تو انبار میشه. لایه‌بندی باعث میشه بدونی چیزها کجا هستن. منطق بیزنس تو Domain، دسترسی به DB تو Infrastructure، و غیره. علاوه بر این تست نوشتن راحت‌تر میشه چون می‌تونی Domain رو بدون DB تست کنی.

**۲. Repository Pattern چیه و چرا استفاده میشه؟**
Repository یعنی یه لایه انتزاعی بین Domain و دیتابیس. به جایی که مستقیم `DbContext` یا SQL صدا بزنی، از `IOrderRepository` استفاده می‌کنی. Domain فقط می‌دونه «یه جایی Orders رو ذخیره و برمیداره»، نمیدونه SQL Server هست یا MongoDB. این باعث میشه تو تست بتونی با یه Mock جایش رو عوض کنی و بدون DB تست بنویسی.

**۳. Service Layer با Application Layer فرق داره؟**
بله. Service Layer معمولاً توی معماری Layered قدیمی‌تر به کار میره و می‌تونه منطق بیزنس رو هم داشته باشه (که اشتباهه اگه زیاد باشه). Application Layer توی Clean Architecture فقط orchestrate می‌کنه؛ منطق توی Domain هست. Application میگه «این کار رو بکن»، Domain میگه «چطور».

**۴. Big Ball of Mud یعنی چی؟**
همون حالتیه که پروژه هیچ ساختار مشخصی نداره. هر کس هر جا دوست داره کد میزنه. Controller مستقیم به DB وصل میشه، منطق بیزنس تو چند جا تکرار شده، وابستگی‌ها پراکنده. بعد از مدتی کسی نمی‌تونه تغییری بده بدون اینکه چیز دیگه‌ای خراب بشه. Layered و Clean برعکس این هستن؛ هر چیز جای خودش رو داره.

**۵. چطور بفهمم پروژه‌م Anemic شده؟**
اگه Entity ها فقط property و get/set دارن و همه منطق (validation، محاسبه، قوانین) تو Service ها یا Controller هاست، Anemic داری. Rich Model یعنی منطق داخل خود Entity باشه. مثلاً Order خودش چک کنه که حداقل یک Item داشته باشه، نه اینکه یه OrderService بیاد و چک کنه.

**۶. در عمل چطور از Clean Architecture شروع کنم؟**
یک پروژه ASP.NET Core بساز. چهار پروژه: Domain (کلاس‌های خالص، بدون وابستگی)، Application (Use Case ها، Interface ها)، Infrastructure (Repository ها، EF)، Web (API و DI). Domain هیچ reference به بقیه نداره. Application به Domain وابسته. Infrastructure به Application (برای implement کردن Interface ها). Web همه رو به هم وصل می‌کنه. اول ساده نگه دار، بعداً CQRS یا MediatR اضافه کن.

**۷. دو تیم روی یک Monolith کار می‌کنن، چی میشه؟**
معمولاً merge conflict و انتظار برای deploy زیاد میشه. هر تیم می‌خواد سریع feature خودش رو بزنه. راه‌حل‌ها: Modular Monolith (مرزهای ماژول واضح، هر تیم روی ماژول خودش کار می‌کنه)، یا در نهایت جدا کردن به Microservices. ولی قبل از Microservices حتماً Modular Monolith رو امتحان کن؛ هزینه و پیچیدگی کمتری داره.

**۸. چطور تیم رو قانع کنیم refactor کنیم؟**
با عدد و مثال. نشون بده چقدر زمان صرف باگ‌گیری میشه، چقدر تست نوشتن سخت شده، یا چقدر اضافه کردن یه feature ساده طول می‌کشه. refactor رو به صورت تدریجی و ماژول به ماژول پیش ببر، نه یک‌دفعه. یه ماژول رو درست کن، نشون بده نتیجه چیه، بعد بقیه رو.

**۹. پروژه قدیمیه و هیچ ساختاری نداره، چی کار کنم؟**
بازنویسی کامل معمولاً گزینه خوبی نیست. از جایی که بیشتر باگ داره یا بیشتر تغییر می‌کنه شروع کن. اون بخش رو کم‌کم جدا کن، با Interface و تست. بقیه رو دست نزن تا مجبور نشی. Strangler Fig Pattern هم می‌گن: کم‌کم سیستم قدیم رو با سیستم جدید جایگزین می‌کنی.

**۱۰. چطور به مدیر یا کارفرما توضیح بدم چرا این معماری رو پیشنهاد می‌کنم؟**
از درد و تاثیر شروع کن، نه از نام معماری. بگو الان چه مشکلی هست و این انتخاب چطور اون رو حل می‌کنه. عدد بده: زمان، هزینه، ریسک. گزینه بدی و بذار تصمیم بگیرن. جزئیات بیشتر تو بخش «معماری از نگاه کارفرما و مدیر پروژه» اومده.

---

## جمع‌بندی و نکات مصاحبه

**سوال رایج:** «تفاوت Clean Architecture و Onion چیه؟»
- Onion روی لایه‌های دایره‌ای تمرکز دارد
- Clean Architecture همان ایده را با نام‌های مشخص‌تر (Entities, Use Cases, …) بیان می‌کند
- در عمل بسیار شبیه هم هستند

**سوال:** «چه زمانی Clean Architecture overkill است؟»
- پروژه‌های خیلی کوچک
- CRUD ساده بدون منطق بیزنس
- تیم بسیار کوچک و زمان کم

**سوال:** «چطور تست‌پذیری با Clean Architecture بهتر می‌شود؟»
- Domain و Application را می‌توان بدون دیتابیس، HTTP و... تست کرد
- Repository ها و سرویس‌های خارجی با Mock جایگزین می‌شوند

---

## ضدالگوها و اشتباهات رایج

**۱. وابستگی معکوس:**
- Domain به Infrastructure وابسته شود (مثلاً استفاده از `DbContext` در Entity)
- **راه‌حل:** Domain فقط Interface ببیند؛ پیاده‌سازی در Infrastructure

**۲. منطق بیزنس در لایه اشتباه:**
- if/else و قوانین کسب‌وکار در Controller یا Application
- **راه‌حل:** منطق در Domain یا داخل Entity ها

**۳. لایه چاق (Fat Layer):**
- Application لایه همه کار انجام دهد
- **راه‌حل:** Application فقط orchestrate کند؛ منطق در Domain

**۴. Entity های Anemic:**
- Entity ها فقط get/set داشته باشند
- **راه‌حل:** Rich Model با رفتار و validation در Entity

**۵. عبور از لایه‌ها (Layer Skipping):**
- Presentation مستقیم Domain یا Infrastructure را صدا بزند
- **راه‌حل:** همه درخواست‌ها از Application عبور کنند

## چه زمانی کدام معماری؟

| وضعیت | پیشنهاد |
|-------|---------|
| پروژه کوچک، CRUD ساده | Data-Centric یا حتی تک لایه |
| منطق بیزنس متوسط | Layered ساده |
| پروژه بزرگ، منطق پیچیده | Clean / Onion / Hexagonal |
| نیاز به تعویض DB یا فریمورک | Domain-Centric |
| تیم بزرگ، چند ماژول | احتمالاً Bounded Context + Clean |

# بخش دوم: Superpowers و تعادل (فاز ۲)

## Superpower هر معماری

| معماری               | Superpower (قوت اصلی)                        | چه مشکلی حل می‌کند؟               |
| -------------------- | -------------------------------------------- | --------------------------------- |
| **Data-Centric**     | سرعت اولیه توسعه                             | رسیدن سریع به MVP و دمو           |
| **Layered**          | سادگی و درک آسان                             | تیم‌های کم‌تجربه، پروژه‌های متوسط |
| **Hexagonal**        | تست‌پذیری، تعویض آسان DB/UI                  | وابستگی به فریمورک و تکنولوژی     |
| **Onion**            | وابستگی به سمت داخل                          | نگهداری بلندمدت، تغییر آسان       |
| **Clean**            | Business Rules در مرکز، Testability          | منطق پیچیده، تیم‌های بزرگ         |
| **Modular Monolith** | آمادگی برای scale بدون پیچیدگی Microservices | رشد تدریجی، کاهش ریسک             |
| **CQRS**             | Scale جدا برای read و write                  | Read-heavy، گزارش‌گیری سنگین      |
| **Event-Driven**     | Loose coupling، مقیاس افقی                   | تیم‌های توزیع‌شده، async          |
| **Microservices**    | Deploy مستقل، مقیاس مستقل هر سرویس           | تیم‌های بزرگ، نیاز به scale جدا   |

---

## نقاط ضعف و هزینه‌ها (Overhead)

| معماری | ضعف اصلی | هزینه (Overhead) |
|--------|----------|------------------|
| **Data-Centric** | عدم تست‌پذیری، coupling بالا | refactor سخت در آینده |
| **Layered** | احتمال تبدیل به Big Ball of Mud | لایه‌های چاق، عبور از لایه‌ها |
| **Hexagonal/Onion/Clean** | پیچیدگی اولیه، تعداد فایل‌ها | زمان توسعه بیشتر در ابتدا |
| **Modular Monolith** | نیاز به انضباط تیمی | باید مرزهای ماژول رعایت شود |
| **CQRS** | دو مدل، eventual consistency | پیچیدگی ذهنی و عملیاتی |
| **Event-Driven** | Debug سخت، tracing | ناهمزمانی، ordering |
| **Microservices** | شبکه، deployment، ops | تیم DevOps، monitoring، چالش‌های توزیع‌شده |

---

## تعادل: چطور ترکیب کنیم؟

هیچ معماری کامل نیست. همه trade-off دارن. تعادل اینه که ببینی وضعیت تو چیه و کدوم ترکیب بهت می‌خوره.

**استارتاپ تو مرحله MVP؟**
Data-Centric یا Layered ساده کافیه. سرعت مهمه. بعد که PMF پیدا کردی و فهمیدی محصول قراره بمونه، شروع کن به refactor. می‌تونی ماژول‌های اصلی رو به سمت Clean ببری یا Modular Monolith بسازی.

**سیستم Enterprise با تیم بزرگ؟**
Clean یا Onion توی هر ماژول منطقیه. Modular Monolith برای جداسازی تیم‌ها خوبه. CQRS رو فقط برای بخش‌هایی که واقعاً read-heavy هستن (مثل داشبورد یا گزارش‌گیری) اضافه کن، نه همه جا. Microservices رو هم وقتی بذار وسط که واقعاً به deploy مستقل یا scale جدا نیاز داری.

**سیستم real-time و توزیع‌شده؟**
Event-Driven برای ارتباط بین سرویس‌ها مناسبه. CQRS برای reporting. Microservices اگه تیم‌ها و scale واقعاً جدا هستن.

**یک نکته مهم:** از ساده شروع کن. وقتی درد واقعی داری (مثلاً deploy هفتگی کافی نیست، یا تست نوشتن غیرممکن شده)، اون موقع معماری پیچیده‌تر رو اضافه کن. نه قبلش.

# بخش سوم: زمان اوج قدرت و مقایسه‌ها (فاز ۳)

## چه زمانی هر معماری بهترین است؟

| معماری | بهترین زمانی که... |
|--------|---------------------|
| **Data-Centric** | نیاز به دمو در ۱–۲ هفته، تیم 1–2 نفر، هیچ منطق پیچیده‌ای نیست |
| **Layered** | تیم 3–7 نفر، پروژه ۶ ماه تا ۲ سال، منطق بیزنس متوسط |
| **Hexagonal** | می‌خواهی DB یا UI را عوض کنی، تست واحد مهم است |
| **Onion/Clean** | منطق بیزنس پیچیده، تیم ۵+ نفر، پروژه بلندمدت |
| **Modular Monolith** | می‌خواهی به Microservices برسی ولی هنوز آماده نیستی |
| **CQRS** | read ها ۱۰x بیشتر از write، گزارش‌گیری سنگین، مدل read/write متفاوت |
| **Event-Driven** | سرویس‌های مستقل، async، نیاز به loose coupling |
| **Microservices** | تیم‌های ۱۰+ نفر، deploy مستقل واقعاً لازم است، مقیاس افقی |

---

## مقایسه دوبه‌دو

### Clean vs Hexagonal

| معیار | Clean | Hexagonal |
|-------|-------|-----------|
| تمرکز | نام‌های لایه (Entities، Use Cases) | Port و Adapter |
| منبع | Uncle Bob | Alistair Cockburn |
| در عمل | تقریباً یکسان | تقریباً یکسان |

**نتیجه:** انتخاب سلیقه‌ای. هر دو Domain-Centric و تست‌پذیر.

### Monolith vs Microservices

| معیار | Monolith | Microservices |
|-------|----------|---------------|
| پیچیدگی اولیه | کم | زیاد |
| Deploy | یکپارچه | مستقل |
| مقیاس | کل سیستم | هر سرویس جدا |
| تیم | می‌توان کوچک باشد | معمولاً ۱۰+ نفر |
| Debug | ساده‌تر | سخت‌تر (توزیع‌شده) |
| مناسب برای | شروع، تیم کوچک | scale، تیم بزرگ |

**نتیجه:** با Monolith شروع کن. فقط وقتی درد واقعی داری به Microservices برو.

### Layered vs Clean

| معیار | Layered | Clean |
|-------|---------|-------|
| وابستگی | می‌توان به بیرون هم برود | فقط به داخل |
| Domain | ممکن است Anemic باشد | باید Rich باشد |
| تست | معمولاً با DB | بدون DB |
| Overhead | کم | بیشتر |

## Decision Tree برای انتخاب معماری

```
شروع
  │
  ├─ تیم کمتر از ۳ نفر؟ ──► بله ──► Data-Centric یا Layered ساده
  │
  ├─ منطق بیزنس پیچیده؟ ──► خیر ──► Layered
  │
  ├─ بله ──► نیاز به تست‌پذیری بالا؟ ──► بله ──► Clean / Hexagonal / Onion
  │
  ├─ تیم بیشتر از ۱۰ نفر؟ ──► بله ──► Modular Monolith یا Microservices
  │
  ├─ Read خیلی بیشتر از Write؟ ──► بله ──► CQRS را در نظر بگیر
  │
  └─ سرویس‌های کاملاً مستقل؟ ──► بله ──► Event-Driven + Microservices
```

# بخش چهارم: مثال‌های واقعی (فاز ۴)

خوبه ببینیم شرکت‌های بزرگ چیکار کردن. نه برای کپی کردن، برای اینه که بفهمی هر معماری توی چه شرایطی انتخاب شده.

## کسب‌وکارهای موفق

| شرکت | معماری | دلیل انتخاب |
|------|--------|-------------|
| **Netflix** | Microservices + Event-Driven | scale جهانی، deploy مستقل، resilience با Chaos Engineering |
| **Amazon** | Microservices، هر تیم مالک سرویس خود | Two-Pizza Team، scale، سرعت نوآوری |
| **Uber** | Microservices (بعد از Monolith) | رشد سریع، تیم‌های متعدد، جغرافیای مختلف |
| **Spotify** | Microservices + Squad model | تیم‌های مستقل (Squad)، سرعت release |
| **Stripe** | Monolith (Ruby) → Microservices | شروع ساده، بعداً domain-driven microservices برای scale |
| **Shopify** | Modular Monolith (Rails) | تیم بزرگ روی یک کدبیس، بدون پیچیدگی شبکه |

## استارتاپ‌ها: از کجا شروع و چطور تکامل؟

**مرحله ۱ – MVP (۰–۶ ماه):**
- معمولاً **Layered ساده** یا حتی **تک لایه**
- هدف: سرعت، validation ایده
- تیم: 1–5 نفر

**مرحله ۲ – Product-Market Fit (۶ ماه – ۲ سال):**
- حرکت به **Clean** یا **Modular Monolith** در ماژول‌های اصلی
- refactor تدریجی
- تیم: 5–15 نفر

**مرحله ۳ – Scale (۲ سال به بعد):**
- **Microservices** برای بخش‌های که واقعاً نیاز دارند
- یا **Modular Monolith** اگر یک تیم کافی است (مثل Shopify)

## تغییر معماری: شرکت‌هایی که عوض کردند

| شرکت | قبل | بعد | دلیل |
|------|-----|-----|------|
| **Netflix** | Monolith (جاوا + Oracle) | Microservices | پس از outage ۲۰۰۸ و حرکت به استریمینگ؛ scale، تیم‌های مستقل |
| **Amazon** | Monolith | Microservices | رشد، دو پیتزا تیم، deploy مستقل |
| **Uber** | Monolith | Microservices | رشد سریع، سرویس‌های جغرافیایی |
| **Etsy** | Monolith (LAMP) | API-first، modularization (مثلاً iOS)، cloud | کاهش coupling، پشتیبانی چند پلتفرم |
| **Stack Overflow** | Monolith | Monolith (همان) | با Monolith به scale رسیدند (۹ سرور، میلیاردها pageview)؛ نیاز به Microservices ندیدند |

## نمونهٔ جزئی: هر بخش چه معماری دارد؟

این بخش نشون می‌ده برای هر نوع پروژه، هر قسمت (یا هر microservice) چطور می‌تونه معماری متفاوت داشته باشه. منطق انتخابش رو هم می‌بینی.

### اصل کلی انتخاب برای هر بخش

| سوال | اگه جوابش... | پس معماری... |
|------|--------------|---------------|
| Read خیلی بیشتر از Write؟ | بله | CQRS، Read Replica، مدل read جدا |
| تراکنش و consistency مهمه؟ | بله | Clean یا Layered با Domain مشخص |
| فقط از صف می‌خونه و کار می‌کنه؟ | بله | Worker ساده؛ لایهٔ کم |
| با سرویس بیرونی (درگاه، ERP) کار می‌کنه؟ | بله | Hexagonal (Port/Adapter)، ACL |
| منطق بیزنس پیچیده؟ | بله | Clean، DDD |
| CRUD ساده + ذخیره فایل؟ | بله | Layered ساده یا حتی تک‌لایه |
| تیم مستقل، deploy جدا؟ | بله | Microservice با مرز واضح |

### ۱. فروشگاه آنلاین (E-commerce)

| بخش | معماری | Principle ها | چرا؟ |
|-----|--------|--------------|------|
| **Catalog (محصولات)** | CQRS یا Layered با Read Replica | SRP، separation of read/write | Read خیلی بیشتر از write؛ لیست محصولات، جستجو، فیلتر. مدل read می‌تونه denormalized و بهینه برای نمایش باشه. |
| **Order (سفارش)** | Clean یا Layered با Domain | DIP، تراکنش، consistency | منطق پیچیده (تخفیف، موجودی، وضعیت). consistency مهمه. تست‌پذیری برای قوانین بیزنس ضروریه. |
| **Cart (سبد)** | Layered ساده یا حتی stateless | KISS | معمولاً session-based یا در Redis. منطق کم. سرعت مهمه. |
| **Payment** | Hexagonal | Port/Adapter، ACL | درگاه‌های مختلف (زرین‌پال، ملت، ...). هر درگاه API و مدل متفاوت داره. Adapter برای هر کدوم؛ Domain به جزئیات وابسته نمیشه. |
| **Inventory** | Layered + Event | eventual consistency | با Order و Warehouse sync میشه. Event-driven برای کاهش coupling. |
| **Notification (ایمیل، SMS)** | **Worker** | — | صف رو می‌خونه، می‌فرسته. منطق بیزنس نداره. معماری «نداره» به معنای لایه‌بندی پیچیده؛ یه حلقه + queue consumer کافیه. |
| **ذخیره تصاویر محصول** | Layered ساده | — | آپلود → Object Storage یا CDN. metadata توی DB. پردازش تصویر (thumbnail) معمولاً یه Worker جدا انجام می‌ده. |

### ۲. ERP و سیستم‌های سازمانی

| بخش | معماری | Principle ها | چرا؟ |
|-----|--------|--------------|------|
| **هسته ERP (مالی، انبار، HR)** | Legacy / Monolith | — | تغییرش سخت و گرونه. معمولاً دست نمی‌زنی. |
| **لایهٔ ادغام** | ACL (Anti-Corruption Layer) | DIP، isolation | سیستم جدید نباید مستقیم به schema و API قدیمی وصل بشه. ACL مدل قدیم رو به مدل جدید ترجمه می‌کنه. |
| **گزارش‌گیری و داشبورد** | CQRS، Read Replica | separation of concerns | Read-heavy. Query های سنگین روی DB اصلی نزن. از replica یا مدل denormalized استفاده کن. |
| **ماژول جدید (مثلاً CRM)** | Clean یا Modular | Bounded Context | ماژول جدید با Domain خودش. از طریق ACL با ERP صحبت می‌کنه. |

### ۳. شبکه اجتماعی تصویری (مثل اینستاگرام)

منبع الگو: مهندسی اینستاگرام (صحت‌سنجی: مقالات و tech blog های عمومی).

| بخش | معماری | Principle ها | چرا؟ |
|-----|--------|--------------|------|
| **Upload API** | Layered ساده | — | فایل رو می‌گیره، توی صف می‌ذاره، سریع جواب می‌ده. منطق سنگین اینجا نیست. |
| **Image Processing Worker** | **بدون معماری لایه‌ای** | Single Responsibility | از صف می‌خونه → resize، thumbnail، فیلتر → ذخیره در Object Storage → DB به‌روزرسانی. هیچ UI و Domain پیچیده‌ای نداره. یه pipeline خطی. |
| **Media Storage** | Object Storage + CDN | — | تصویر توی DB ذخیره نمیشه؛ فقط metadata و URL. CDN برای سرو سریع. |
| **Feed (خبرخوان)** | CQRS، Cache (Redis/Memcached) | Read optimization | Read بسیار سنگین. مدل read برای timeline بهینه میشه. Fan-out روی write یا read (مثل توییتر). |
| **User، Follow، Like** | Layered یا Clean | — | بسته به پیچیدگی. social graph خودش مدل جدا می‌خواد. |

### ۴. میکروبلاگ / توییت (مثل توییتر)

منبع الگو: معماری توییتر و fan-out (صحت‌سنجی: مقالات سیستم‌دیزاین و tech blog ها).

| بخش | معماری | Principle ها | چرا؟ |
|-----|--------|--------------|------|
| **Tweet (نوشتن)** | Layered + Event | Event-driven | Write نسبتاً کم. پس از ثبت، event می‌فرسته برای Timeline و Notification. |
| **Timeline (خبرخوان)** | CQRS + Fan-out | Read/Write separation | Read خیلی بیشتر از Write. دو الگو: **Fan-out on write** (وقتی کسی توییت می‌زنه، برای همه follower ها توی cache می‌ذاره) یا **Fan-out on read** (وقتی کاربر timeline می‌خواد، جمع‌آوری می‌کنه). توییتر هر دو رو ترکیب کرده. |
| **Search** | CQRS، Search Engine جدا | separation | Elasticsearch یا مشابه. مدل read برای جستجو با مدل اصلی فرق داره. |
| **User، Follow** | Layered | — | Social graph. برای Fan-out لازمه بدونی هر کاربر دنبال کیاست. |
| **Notification Worker** | **Worker ساده** | — | Event رو می‌گیره، push/email می‌فرسته. |

### ۵. مسنجر (مثل تلگرام)

| بخش | معماری | Principle ها | چرا؟ |
|-----|--------|--------------|------|
| **Message Delivery** | Event-Driven، Real-time | loose coupling | پیام باید سریع برسه. WebSocket یا long polling. Event برای sync بین دستگاه‌ها. |

| **Encryption (پایان به پایان)** | ماژول جدا، حداقل وابستگی | Security by design | منطق رمزنگاری جدا. وابستگی به بقیه سیستم کم. |

### ۶. Worker ها: وقتی «معماری» به معنای لایه‌بندی نیست

بعضی قسمت‌ها اصلاً نیازی به Clean یا Hexagonal ندارن. فقط یه job هستند که کار مشخصی انجام می‌دن.

| نوع Worker | ورودی | خروجی | ساختار |
|------------|-------|-------|--------|
| **Queue Consumer** | پیام از RabbitMQ/Kafka | پردازش + احتمالاً پیام بعدی | حلقه: receive → process → ack. اگه منطق ساده باشه، همین کافیه. |
| **Scheduled Job** | زمان (cron) | کار دوره‌ای (مثلاً گزارش شبانه) | Timer + logic. هیچ لایهٔ Domain پیچیده‌ای لازم نیست. |
| **Image/Video Processor** | فایل در صف | فایل پردازش‌شده در storage | Pipeline: decode → resize/compress → upload → update DB. |
| **Email/SMS Sender** | event یا صف | ارسال | فقط adapter به سرویس ایمیل/SMS. |

**اصل:** اگه منطق بیزنس نداره، وابستگی کم داره، و فقط یک کار خطی انجام می‌ده، معماری سنگین اضافه نکن. ولی تست‌پذیری و error handling رو فراموش نکن.

---

### جمع‌بندی منطق انتخاب

```
هر بخش رو جدا ارزیابی کن:
  ├─ Read >> Write؟ ──► CQRS، Read Replica
  ├─ تراکنش و قوانین پیچیده؟ ──► Clean، Domain
  ├─ فقط صف می‌خونه و کار می‌کنه؟ ──► Worker ساده
  ├─ با سیستم بیرونی/Legacy کار می‌کنه؟ ──► Hexagonal، ACL
  └─ CRUD یا ذخیره ساده؟ ──► Layered ساده
```

یک سیستم می‌تونه هم‌زمان Clean (Order)، CQRS (Catalog)، Hexagonal (Payment)، و Worker ساده (Notification) داشته باشه. هر بخش با نیاز خودش انتخاب میشه.

# بخش پنجم: شکست‌ها و درس‌ها (فاز ۵)

چند تا مورد که به خاطر معماری یا فرآیند اشتباه، خراب شدن. درسشون رو بگیریم.

## شرکت‌ها و پروژه‌هایی که به خاطر معماری دچار مشکل شدند

| مورد | مشکل | دلیل معماری |
|------|------|-------------|
| **Knight Capital (۲۰۱۲)** | از دست رفتن ۴۴۰ میلیون دلار در ~۴۵ دقیقه | deploy اشتباه (کد قدیم حذف نشده)، عدم تست کافی، سیستم سفارش‌دهی بدون محدودیت حجم |
| **Healthcare.gov (۲۰۱۳)** | راه‌اندازی فاجعه‌بار | معماری نامناسب، عدم تست، تیم‌های پراکنده |
| **استارتاپ‌هایی که Microservices زود انتخاب کردند** | تأخیر زیاد، burnout، شکست محصول | Over-engineering، تیم کوچک، پیچیدگی غیرضروری (تجربه رایج در صنعت) |
| **سیستم‌های دولتی قدیمی** | نگهداری بسیار گران | Monolith بدون مرز، coupling شدید، عدم مستندات |

## دلایل رایج شکست

**Over-engineering:** Microservices برای تیم ۳ نفره، یا Clean Architecture برای یه CRUD ساده. درسته که یاد گرفتن خوبه، ولی پروژه رو گروگان نگیر. با ساده شروع کن.

**Under-engineering:** Data-Centric برای سیستمی که منطق پیچیده داره، یا هیچ لایه‌بندی برای پروژه‌ای که قراره دو سال طول بکشه. اگه قراره رشد کنی، زود refactor کن. هر چه دیرتر، سخت‌تر.

**انتخاب اشتباه:** Event-Driven برای جایی که sync کافیه، یا Monolith برای تیم ۵۰ نفره که پراکنده‌ان. با مشکل واقعی هماهنگ کن، نه با چیزی که تو کنفرانس‌ها مد شده.

**عدم انضباط:** معماری درست انتخاب شده ولی کسی رعایتش نمی‌کنه. Controller مستقیم به DB وصل میشه، لایه‌ها رو دور میزنن. معماری فقط با فرهنگ تیم زنده می‌مونه؛ اگه تیم باورش نکنه، نقشه روی کاغذ می‌مونه.

## چطور از اشتباهات درس بگیریم؟

قبل از Microservices، Modular Monolith رو حتماً در نظر بگیر. قبل از هر معماری جدید بپرس: چه دردی رو حل می‌کنه؟ فازبندی کن: MVP ساده، بعد تکامل تدریجی. و تست و deploy رو از همون اول جدی بگیر؛ معماری بدون این‌ها نیمه‌کاره می‌مونه.

# بخش ششم: راهنمای انتخاب برای موفقیت محصول (فاز ۶)

## سوالات کلیدی قبل از انتخاب

| # | سوال | تأثیر روی انتخاب |
|---|------|-------------------|
| ۱ | اندازه تیم چند نفر است؟ | <3: ساده. 3–10: Layered/Clean. 10+: Modular/Microservices |
| ۲ | پروژه چقدر طول می‌کشد؟ | <6 ماه: ساده. >2 سال: Clean، Modular |
| ۳ | منطق بیزنس چقدر پیچیده است؟ | ساده: Data-Centric. پیچیده: Clean، DDD |
| ۴ | Read خیلی بیشتر از Write است؟ | بله: CQRS را در نظر بگیر |
| ۵ | تیم‌ها جغرافیایی یا مستقل هستند؟ | بله: Event-Driven، Microservices |
| ۶ | نیاز به تعویض DB/فریمورک دارید؟ | بله: Domain-Centric |
| ۷ | تست‌پذیری چقدر مهم است؟ | خیلی: Clean، Hexagonal |
| ۸ | سرعت اولیه توسعه مهم‌تر است؟ | بله: Layered ساده |

## Product-Market Fit و معماری

| مرحله محصول | هدف | معماری پیشنهادی |
|-------------|-----|------------------|
| **قبل از PMF** | validation سریع، iterating | Data-Centric، Layered ساده |
| **PMF پیدا شده** | refactor، آمادگی رشد | حرکت به Clean یا Modular Monolith |
| **رشد** | scale، تیم‌های جدید | Modular Monolith، بعد Microservices اگر لازم |
| **بلوغ** | نگهداری، featureهای جدید | Clean، مرزهای واضح |

## تیم Database

**نقش تیم DB:**
- طراحی schema، migration، performance
- در Data-Centric: مرکز تصمیم‌گیری
- در Domain-Centric: زیرمجموعه Infrastructure

**معماری‌های مناسب برای DB-heavy:**
- **Read-heavy (گزارش، داشبورد):** CQRS، Read Replica
- **Write-heavy:** احتمالاً Monolith یا سرویس متمرکز
- **چند دیتابیس:** Microservices (هر سرویس DB خودش) یا Bounded Context

**همکاری با تیم توسعه:**
- در Clean: DB تیم روی Infrastructure و Repository کار می‌کند
- Contract (Interface) را Domain/Application تعریف می‌کند

## استارتاپ‌ها: MVP، Iterating، Scaling

| مرحله | معماری | نکته |
|-------|--------|------|
| **MVP** | تک لایه یا Layered ساده | سریع بساز، سریع تست کن |
| **Iterating** | Layered، شروع به جداسازی ماژول‌ها | refactor تدریجی، نه بازنویسی کامل |
| **Scaling** | Modular Monolith اول | اگر تیم بزرگ شد و درد deploy داشتی → Microservices |

# معماری از نگاه کارفرما و مدیر پروژه

یه چیز که معمولاً یادش می‌ریم: معماری فقط یه موضوع فنی نیست. روی هزینه، زمان، ریسک و حتی نوع آدم‌هایی که می‌تونی استخدام کنی تاثیر مستقیم داره. اگه بتونی از زاویه کارفرما یا PM هم نگاه کنی، هم حرفت رو بهتر می‌زنی هم تصمیمات بهتری می‌گیری.

## کارفرما و مدیر پروژه به چی فکر می‌کنن؟

**هزینه:** چقدر خرج می‌کنیم؟ الان و در آینده. معماری ساده = هزینه اولیه کمتر، ولی ممکنه بعداً refactor گرون دربیاد. معماری پیچیده = هزینه اولیه بیشتر، ولی نگهداری شاید ارزون‌تر بشه.

**زمان:** کی تحویل می‌دیم؟ ددلاین چقدر فشار داره؟ اگه وقت کمه، معماری ساده‌تر منطقیه. اگه وقت داری و محصول قراره سال‌ها بمونه، سرمایه‌گذاری روی ساختار به صرفه‌ست.

**ریسک:** چی می‌شه اگه خراب بشه؟ اگه تیم بره؟ اگه بخوایم vendor عوض کنیم؟ معماری که به یک نفر یا یک تکنولوژی وابسته نباشه، ریسک رو کم می‌کنه.

**مقیاس آینده:** قراره تیم بزرگ بشه؟ چند محصول روی همین زیرساخت میاد؟ اگه جواب آره است، از الان باید به مرزها و ماژول‌ها فکر کنی.

**استخدام:** چه کسی می‌تونه این پروژه رو نگه داره؟ Monolith ساده = احتمالاً Junior هم می‌تونه. Microservices = به Senior و DevOps نیاز داری. این روی هزینه نیروی انسانی تاثیر داره.

## منابع موجود و تاثیرش روی انتخاب

| منبع | کم هست | تاثیر روی معماری |
|------|--------|-------------------|
| **بودجه** | محدود | از ساده شروع کن. Microservices گرون‌تره (infra، DevOps، monitoring). |
| **تیم** | 1–3 نفر | Layered ساده یا Data-Centric. Clean اگه تجربه دارن. Microservices ممنوع. |
| **زمان** | ددلاین فشرده | ساده‌ترین چیزی که جواب بده. refactor بعداً. |
| **زیرساخت موجود** | Monolith قدیمی | Strangler Fig. جدا کردن تدریجی. بازنویسی کامل معمولاً غیرواقعیه. |
| **نیروی فنی** | Junior زیاد | معماری باید قابل فهم باشه. مستندات و استانداردها مهم‌تر میشن. |
| **نیاز به scale** | هنوز مشخص نیست | Modular Monolith. آمادگی بدون هزینه Microservices. |

## تاثیر هر تصمیم روی کسب‌وکار

| تصمیم | هزینه اولیه | هزینه نگهداری | ریسک | زمان تا تحویل |
|-------|-------------|----------------|------|----------------|
| Data-Centric | کم | بالا (refactor) | زیاد | کم |
| Layered ساده | کم | متوسط | متوسط | کم |
| Clean/Onion | متوسط | کم | کم | متوسط |
| Modular Monolith | متوسط | کم–متوسط | کم | متوسط |
| Microservices | بالا | بستگی به تیم داره | متوسط–زیاد | زیاد |

**نکته:** هزینه نگهداری Data-Centric وقتی پروژه بزرگ میشه بالا میره؛ ولی برای MVP یا دمو اصلاً مهم نیست.

## چطور با کارفرما یا PM حرف بزنی؟

**از درد شروع کن، نه از راه‌حل.** نگو «می‌خوام Clean Architecture بزنیم». بگو «الان اضافه کردن هر feature دو هفته طول می‌کشه و باگ‌ها دارن زیاد میشن. یه refactor ساختاری می‌تونه این رو حل کنه.»

**عدد بده.** «الان ۴۰٪ وقت تیم صرف باگ‌گیری میشه. با ساختار بهتر می‌تونیم به ۲۰٪ برسونیم.» یا «refactor این ماژول ۳ هفته طول می‌کشه، ولی اضافه کردن feature بعدی از دو هفته به یک هفته می‌رسه.»

**گزینه بدی.** «می‌تونیم همون ساختار فعلی رو نگه داریم، ولی ریسکش اینه که...» یا «می‌تونیم refactor کنیم، هزینه اش اینه، نفعش اینه.»

**زبانشون رو حرف بزن.** برایشون مهمه هزینه، زمان، ریسک. کمتر براشون مهمه که Clean باشه یا Hexagonal. تاثیر رو تو اینها نشون بده.

## سناریوهای واقعی

**بودجه کم، تیم ۲ نفره، ددلاین ۲ ماهه:**
ساده‌ترین چیزی که کار کنه. Data-Centric یا تک لایه. هدف اینه زنده بیرون بیاد. بعد از launch می‌شه refactor کرد. اگه از اول Clean بزنی، یا ددلاین رو از دست میدی یا کیفیت رو.

**تیم ۵ نفره، محصول قراره ۳ سال نگه داریم:**
از الان Clean یا Modular Monolith. هزینه اولیه بیشتره، ولی روی سه سال به صرفه‌ست. مستند کن، استاندارد بذار، تا هر کس جدیدی که میاد راحت‌تر onboard بشه.

**Monolith قدیمی، هیچکس نمی‌خواد دست بزنه:**
از یه ماژول که بیشتر باگ داره یا بیشتر تغییر می‌کنه شروع کن. جدااش کن، تست بنویس، نشون بده نتیجه چیه. بعد بقیه رو. یک‌دفعه «بذار از اول بنویسیم» معمولاً رد میشه؛ تدریجی قابل قبول‌تره.

**کارفرما می‌گه همه جا Microservices باشه:**
بپرس چرا. چه دردی رو حل می‌کنه؟ اگه جواب مشخص نبود، با عدد و مثال نشون بده هزینه و پیچیدگی چقدره. پیشنهاد بده اول Modular Monolith، بعد اگه واقعاً لازم شد جدا کنیم.

## جمع‌بندی نگاه کسب‌وکاری

معماری یه سرمایه‌گذاریه. مثل هر سرمایه‌گذاری، باید با وضعیت و منابع هماهنگ باشه. اگه منابع کمه، کم سرمایه‌گذاری کن. اگه محصول بلندمدته و رشد داره، بیشتر سرمایه‌گذاری کن. و همیشه با کسی که پول یا زمان رو مدیریت می‌کنه، با زبان خودش حرف بزن.

# نگاه‌های تکمیلی: استقرار، تیم‌ها، و روش‌های مدیریتی

## استقرار (Deployment) و الزاماتش

معماری روی نحوه deploy و زیرساخت تاثیر مستقیم داره.

**Monolith:**
- یک واحد deploy می‌شه. هر تغییر = ری‌استارت کل سیستم
- زیرساخت ساده: یک سرور یا چند تا instance پشت load balancer
- فرکانس deploy معمولاً هفتگی یا کمتر
- برای rollback کافیه نسخه قبلی رو برگردونی

**Microservices:**
- هر سرویس جدا deploy میشه. تغییر یک سرویس بقیه رو تحت تاثیر نمی‌ذاره
- ولی نیاز به orchestration (مثلاً Kubernetes)، service discovery، و monitoring متمرکز داره
- فرکانس deploy می‌تونه روزانه یا بیشتر باشه
- هزینه infra و ابزارها بیشتره. بدون DevOps یا CI/CD درست، دردسرش زیاد میشه

**نکته:** اگه تیم DevOps نداری یا تجربه‌ات کمه، Microservices می‌تونه مانع deploy باشه به جای تسهیلش.

---

## نگاه تیم دیتابیس

تیم DB معمولاً روی schema، migration، performance و consistency کار می‌کنه. معماری تعیین می‌کنه چطور با این تیم هماهنگ بشی.

**Data-Centric:** تیم DB در مرکز تصمیم‌گیریه. schema طراحی می‌کنن، گاهی منطق هم توی stored procedure میره. توسعه‌دهنده‌ها مستقیماً با schema کار می‌کنن. ریسکش اینه که تغییر schema روی همه تاثیر میذاره.

**Clean / Domain-Centric:** تیم توسعه Domain و مدل رو تعریف می‌کنه. تیم DB روی Infrastructure و mapping (مثلاً EF) کار می‌کنه. Contract بین Domain و DB روشن هست. migration ها باید با تغییرات Domain هماهنگ باشن.

**Microservices:** هر سرویس دیتابیس خودش رو داره. تیم DB دیگه مالک متمرکز schema نیست؛ هر تیم سرویس روی بخش خودش تصمیم می‌گیره. چالش: consistency بین سرویس‌ها، migration توزیع‌شده.

**CQRS و Read Replica:** تیم DB روی write و read جدا کار می‌کنه. replication و eventual consistency باید درست مدیریت بشه.

## معماری و Agile / Scrum

**Emergent Design (طراحی emergent):** توی Agile، معماری می‌تونه کم‌کم و با iterating شکل بگیره، نه یک‌دفعه در ابتدا. هر sprint یه قدم، refactor مداوم. این برای پروژه‌های کوچک و متوسط جواب می‌ده.

**محدودیت:** اگه scale بالاست یا تیم‌ها زیادن، emergent design به تنهایی کافی نیست. عدم استاندارد و هماهنگی بین تیم‌ها مشکل می‌شه. برای همین مدل‌هایی مثل SAFe «Architectural Runway» دارن: یه لایه قبلی برنامه‌ریزی که اجازه autonomous بودن تیم‌ها رو بده ولی coherence رو حفظ کنه.

**Incremental Delivery:** تحویل مکرر و در بسته‌های کوچک. معماری باید طوری باشه که بشه featureها رو به صورت end-to-end تحویل داد بدون اینکه کل سیستم رو بشکنی. ماژولار بودن این رو ممکن می‌کنه.

**نکته:** Agile به معنای «بدون معماری» نیست. به معنای تکامل تدریجی معماری با feedback واقعی است.

---

## ساختار تیم و معماری

**Feature Team:** تیم عمودی کار می‌کنه؛ از UI تا DB یه feature رو کامل تحویل می‌ده. معمولاً با Agile و تحویل مکرر سازگاره. ریسکش: ناسازگاری بین تیم‌ها، تکرار کد.

**Component Team:** تیم روی یک component یا لایه خاص متمرکزه (مثلاً فقط backend یا فقط یک سرویس). سازگاری معماری بهتره، ولی وابستگی بین تیم‌ها زیاد میشه و تحویل کندتر. برای Microservices یا سیستم‌های خیلی بزرگ استفاده میشه.

**تطابق با معماری:** Feature team با Modular Monolith یا ماژول‌های واضح خوب کار می‌کنه. Component team با Microservices (هر تیم مالک یک یا چند سرویس) منطقیه. فریمورک LeSS و SAFe معمولاً feature team رو ترجیح می‌دن؛ component team به عنوان راه‌حل موقت.

## اصل‌های مهم، فرهنگ سازمان و تاثیر روی معماری

### قانون کانوی (Conway's Law)

ملوین کانوی (۱۹۶۸) گفت: *«هر سازمانی که سیستمی طراحی می‌کنه، محصولش ساختاری شبیه ساختار ارتباطی خود سازمان پیدا می‌کنه.»* یعنی نرم‌افزار تمایل داره آینهٔ نحوهٔ ارتباط تیم‌ها باشه. مارتین فاولر می‌گه این قانون روی هر سیستمی تاثیر داره و مبارزه بااش شکست میاره.

**چرا این‌طوریه؟** کدهایی که نویسنده‌شون راحت باهم حرف می‌زنن، تمایل دارن به هم وصل بشن (coupling). هم صریح (function call) هم تلویحی (فرض‌های مشترک). پس مرزهای ارتباط تیم‌ها به مرزهای ماژول‌های نرم‌افزار تبدیل میشن.

**مثال:** تیم بر اساس لایه (Frontend، Backend، DB) چیده شده → معماری layered غالب میشه. هر feature نیاز به همکاری سه تیم داره؛ hand-off زیاد، کندی. یا: شش تیم در شش شهر → شش subsystem جدا، چون ارتباط بین شهرها سخت‌تره. معماری باید با این واقعیت هماهنگ باشه.

**Inverse Conway Maneuver:** می‌تونی برعکس عمل کنی؛ ساختار تیم رو طوری عوض کنی که معماری دلخواه رو تولید کنه. مثلاً تیم‌های کوچک cross-functional بر اساس قابلیت کسب‌وکار (نه لایه) → سرویس‌های مستقل و قابل deploy جدا. این همون منطق پشت Microservices و مدل Spotify هست.

**محدودیت:** برای سیستم legacy با معماری خشک، فقط عوض کردن ساختار تیم کافی نیست؛ هر دو (سازمان و کد) باید با هم تکامل پیدا کنن.

---

### سازمان چاق (سلسله‌مراتبی) در مقابل فلت (مسطح)

| ویژگی | چاق / سلسله‌مراتبی | فلت / مسطح |
|-------|---------------------|------------|
| **سطوح تصمیم‌گیری** | زیاد؛ تأیید چندلایه | کم؛ تصمیم نزدیک به تیم |
| **سرعت تصمیم** | کندتر؛ بوروکراسی | سریع‌تر؛ خودمختاری بیشتر |
| **هماهنگی** | از بالا به پایین؛ استاندارد متمرکز | از طریق alignment و توافق؛ احتمال ناسازگاری |
| **مسئولیت‌پذیری** | روشن‌تر (مدیر مشخص) | گاهی مبهم؛ کی مسئوله؟ |
| **معمولاً به چه معماری می‌رسه** | Monolith یا سیستم متمرکز؛ تغییرات از مرکز کنترل میشن | Microservices یا ماژول‌های مستقل اگه تیم‌ها خودمختار باشن؛ ولی ریسک هرجومرج |

**نکته:** هیچ‌کدوم «درست مطلق» نیست. سازمان‌های بزرگ غالباً ترکیبی دارن: تصمیم‌های حیاتی متمرکز (مثلاً امنیت، استانداردها)، و autonomy برای چگونگی اجرا در تیم. مدل Spotify همین‌طوره: Squads خودمختار، ولی با alignment از طریق Chapters، Guilds و guardrail های مهندسی.

---

### Principle های در حال استفاده

| اصل | کاربرد |
|-----|--------|
| **Conway's Law** | ساختار تیم و معماری رو با هم طراحی کن؛ یکی رو بدون دیگری عوض نکن. |
| **Inverse Conway** | برای معماری دلخواه، اول مرزهای تیم رو طراحی کن. |
| **Bounded Context (DDD)** | مرزهای domain رو مشخص کن؛ هر Context می‌تونه با یک تیم منطبق باشه. |
| **Autonomy + Alignment** | تیم‌ها خودمختار باشن برای سرعت؛ ولی هدف‌ها، استانداردها و guardrail ها مشترک باشن. |
| **SOLID، DIP، SRP** | در سطح کد و ماژول؛ برای تست‌پذیری و نگهداری. |

**جمع‌بندی:** معماری فقط انتخاب تکنیکی نیست. ساختار سازمان، نحوهٔ ارتباط تیم‌ها و فرهنگ تصمیم‌گیری مستقیم روی محصول نرم‌افزار تاثیر میذاره. اگه معماری رو عوض می‌کنی، به ساختار تیم و ارتباطات هم فکر کن؛ و برعکس.

## زبان برنامه‌نویسی و تاثیر روی معماری

انتخاب زبان روی معماری، سرعت توسعه و عملیات تأثیر می‌ذاره. نه تعیین‌کنندهٔ قطعی، ولی بخشی از معادله است.

### Monolith: یک زبان معمولاً

توی Monolith یک زبان غالباً انتخاب میشه. مزیت: اکوسیستم واحد، کتابخانه‌های مشترک، تست و refactor ساده‌تر، استخدام نیرو با یک مهارت اصلی. زبان تعیین می‌کنه کدوم فریمورک‌ها (مثلاً Spring، ASP.NET، Django) و کدوم الگوها راحت‌تر پیاده میشن.

### Microservices: امکان Polyglot

توی Microservices هر سرویس می‌تونه زبان متفاوت داشته باشه (Polyglot). مثلاً API Gateway با Go، سرویس پیشنهاد با Python (به خاطر ML)، پرداخت با Java یا C#. مزیت: انتخاب ابزار مناسب برای هر مسئله. چالش: pipeline های متعدد، tracing و لاگ یکپارچه، استخدام و نگهداری چند مهارت.

### ویژگی‌های زبان و تاثیر عملی

| ویژگی | تاثیر روی معماری |
|-------|-------------------|
| **زمان راه‌اندازی (startup)** | Java/JVM و Python کندتر از Go یا Rust. برای scale افقی و serverless مهمه؛ instance های زیاد = هزینه startup. Go و .NET AOT برای سرویس‌های سبک مناسب‌ترن. |
| **فریمورک و اکوسیستم** | Spring، ASP.NET، Laravel هرکدوم ساختار و لایه‌های پیش‌فرض دارن. معماری تا حدی با انتخاب فریمورک گره می‌خوره. |
| **نوع‌دهی (static vs dynamic)** | زبان‌های static برای پروژهٔ بزرگ و refactor امن‌ترن. زبان‌های dynamic برای prototype و سرعت اولیه. |
| **مدل اجرا (sync vs async)** | Node.js و Go به‌طور native async/concurrent هستن؛ برای I/O-heavy و real-time مناسب‌ترن. Java و C# هم پشتیبانی دارن ولی مدل متفاوته. |

### چه زمانی زبان مهم‌تر میشه؟

- **Monolith:** زبان روی سرعت توسعه، نگهداری و hiring تاثیر داره. روی شکل معماری کمتر (همه چیز یک کدبیس است).
- **Microservices:** انتخاب زبان برای هر سرویس آزادتره؛ ولی polyglot یعنی governance، CI/CD و observability پیچیده‌تر.
- **Worker و Batch:** زبان‌های سبک (Go، Python برای script) یا همون زبان اصلی پروژه برای consistency.

**نکته:** زبان به‌تنهایی معماری رو تعیین نمی‌کنه. تیم، مقیاس و نیاز کسب‌وکار مهم‌ترن. ولی وقتی معماری رو انتخاب می‌کنی، به مهارت تیم، اکوسیستم و محدودیت‌های runtime فکر کن.

## نگاه تیم DevOps

DevOps روی CI/CD، monitoring، و عملیات روزانه تمرکز داره. معماری روی حجم کارشون تاثیر داره.

**Monolith:** pipeline ساده، یک build، یک deploy. monitoring هم ساده‌تره.

**Microservices:** چند pipeline، چند deploy، service mesh، distributed tracing. نیاز به ابزار و تجربه بیشتر.

**قبل از انتخاب معماری:** بپرس آیا ظرفیت DevOps برای پشتیبانی وجود داره. اگه نه، Monolith یا Modular Monolith منطقی‌تره.

---

## نگاه تیم پشتیبانی

تیم Support/SRE باید باگ‌ها رو پیدا کنه، incident رو handle کنه و گاهی root cause رو تشخیص بده. معماری روی کارشون تاثیر مستقیم داره.

**Monolith:** یک لاگ، یک flow. پیدا کردن مشکل نسبتاً ساده‌تره؛ ولی اگه سرویس fall کنه، کل سیستم down میشه. پاسخ «چرا down شد؟» معمولاً واضح‌تره.

**Microservices:** لاگ‌ها پراکنده، تراکنش‌ها چند سرویس رو رد می‌کنن. بدون distributed tracing و correlation ID، دنبال کردن یک request سخت میشه. از طرفی، خرابی یک سرویس کل سیستم رو نمی‌ندازه. Support باید ابزار و آموزش ببینه.

**نکته:** قبل از انتخاب معماری، بپرس تیم Support چه ابزاری داره و چقدر با سیستم‌های توزیع‌شده آشناست. اگه نه، مستندات و runbook ساده‌تر برای Monolith منطقی‌تره.

## سخت‌افزار و هزینه‌های محتمل

| مورد | Monolith | Microservices |
|------|----------|---------------|
| **سرور** | یک یا چند instance مشابه؛ scaling عمودی ساده | چندین سرویس، هرکدوم ممکنه نیاز متفاوت داشته باشه؛ scaling افقی |
| **شبکه** | ترافیک داخلی کم | ترافیک بین سرویس‌ها زیاد؛ latency و bandwidth مهم میشه |
| **ذخیره‌سازی** | یک یا چند DB؛ backup ساده‌تر | چند DB یا schema؛ backup و restore پیچیده‌تر |
| **ابزار** | CI/CD و monitoring ساده | orchestration، service mesh، tracing؛ هزینه لایسنس و نگهداری |
| **نیروی انسانی** | تیم کوچک‌تر کافیه | به Senior، DevOps و احتمالاً SRE نیاز داری |

هزینه فقط خرید سرور نیست؛ نگهداری، آموزش و زمان troubleshoot هم در محاسبه باید باشه.

## تجربه تیم و تاثیرش روی پروژه

معماری باید با سطح بلوغ تیم همخوان باشه.

**تیم Junior-heavy:** معماری ساده‌تر (Layered، Data-Centric) منطقیه. Clean و Microservices بدون راهنما و استاندارد مشخص، احتمال فروریختن ساختار رو زیاد می‌کنه. مستندات و code review منظم مهم‌تر میشه.

**تیم با تجربه:** می‌تونه Clean، DDD یا Microservices رو درست اجرا کنه. refactor و emergent design بهتر جواب می‌ده.

**ترکیب:** اگه یک یا دو Senior دارن و بقیه Junior، معماری باید طوری باشه که مرزها روشن باشه و Junior ها بتونن داخل یک ماژول کار کنن بدون اینکه کل سیستم رو بشکنن. Modular Monolith یا ماژول‌های واضح در Clean کمک می‌کنه.

**نکته:** انتخاب معماری «درست» بدون تیمی که بتونه نگه‌ش داره، به شکست منجر میشه. اول تیم، بعد معماری.

## زیرساخت شبکه و حساسیت دیتا

بعضی شرکت‌ها (بانک، بهداشت، دولت، صنایع حساس) به خاطر امنیت، شبکهٔ داخلی و خارجی رو از هم جدا می‌کنن. معماری باید با این محدودیت‌ها سازگار باشه.

**شبکهٔ داخلی (Internal):** دیتای اصلی، DB ها و سرویس‌های هسته اینجان. دسترسی فقط از داخل یا از طریق واسط‌های امن.

**شبکهٔ خارجی (DMZ / External):** API های عمومی، وب، موبایل. کاربر نهایی اینجارو می‌بینه. با فایروال و proxy به شبکهٔ داخلی متصله.

**جریان داده:** درخواست از خارج → فایروال → API Gateway یا BFF → واسط امن (مثلاً message queue یا sync API با احراز هویت) → سرویس داخلی → DB داخلی. دیتای حساس از شبکهٔ داخلی خارج نمیشه؛ فقط نتیجهٔ پردازش‌شده برگرده.

**تاثیر روی معماری:**
- **Monolith:** می‌تونه پشت یک فایروال باشه؛ یه لایه جدا برای API عمومی. ساده‌تره.
- **Microservices:** اگه بعضی سرویس‌ها توی DMZ و بعضی توی internal باشن، ارتباط بین zone ها باید از طریق واسطِ تعریف‌شده (API، queue) باشه. طراحی شبکه و امنیت پیچیده‌تر میشه.
- **Event-Driven:** event bus می‌تونه مرز zone ها رو رد کنه؛ باید encryption، authentication و authorization درست تعریف بشه.

**نکته:** قبل از طراحی، محدودیت‌های شبکه و سیاست امنیتی شرکت رو بگیر. بعضی جاها ارتباط مستقیم بین سرویس‌ها ممنوعه؛ فقط از طریق gateway یا queue مجاز است.

## برونسپاری و پروژه‌های جانبی

وقتی بخشی از کار به تیم بیرونی (شرکت دیگر یا فریلنسر) سپرده میشه، معماری باید طوری باشه که هماهنگی و کنترل ممکن باشه.

**چالش‌ها:**
- **Contract و مرزها:** تیم برونسپار باید بدونه دقیقاً چه چیزی تحویل می‌ده و چطور با بقیه سیستم وصل میشه. Interface ها، API‌ها و مدل داده باید از قبل تعریف و مستند بشن. اگه مرزها مبهم باشه، انتظار merge conflict و integration دردسرساز برو.
- **پیچیدگی معماری:** Microservices با چند تیم مستقل منطقیه؛ ولی اگه تیم برونسپار تجربه‌اش کمه یا دسترسی به infra نداره، معماری ساده‌تر (ماژول واضح داخل Monolith) عملی‌تره.
- **تحویل و تست:** تحویل مکرر و تحویل ماژول به ماژول بهتر از تحویل یک‌بارهٔ کل پروژه است. هر ماژول باید Contract خودش رو رعایت کنه تا integration ساده‌تر بشه.

**توصیه:** از اول مرزهای ماژول، Interface ها و نحوهٔ ارتباط رو مشخص کن. ماژول برونسپارشده رو طوری طراحی کن که بتونی با Mock تست کنی و بدون وابستگی به تیم بیرونی integration رو بسنجی.

## ادغام با ERP و سیستم‌های ثابت (Legacy)

خیلی شرکت‌ها ERP، سیستم مالی، منابع انسانی یا نرم‌افزارهای هسته‌ای دارن که تغییرشون گرون، ریسک‌دار یا عملاً غیرممکنه. پروژهٔ جدید باید با این‌ها کار کنه.

**ویژگی‌های معمول سیستم‌های ثابت:**
- API تمیز و مدرن ندارن؛ گاهی فقط batch export یا DB مستقیم
- schema و مدل داده قدیمیه؛ naming و ساختار با سیستم جدید فرق داره
- واقع‌زمان (real-time) پشتیبانی نمی‌کنن؛ sync شبانه یا دوره‌ای

**الگوی Anti-Corruption Layer (ACL):** یه لایهٔ میانی که سیستم جدید رو از Legacy جدا می‌کنه. این لایه مدل قدیمی رو به مدل جدید ترجمه می‌کنه و برعکس. منطق بیزنسِ سیستم جدید به مدل Legacy وابسته نمیشه؛ فقط از طریق ACL با اون صحبت می‌کنه. این الگو از DDD میاد و برای ادغام با ERP و سیستم‌های قدیمی رایجه.

**راه‌های ارتباط:** API wrapping (اگه Legacy یه endpoint داره)، batch sync (اگه فقط export/import ممکنه)، یا message queue برای جداسازی و کاهش وابستگی مستقیم.

**نکته:** ادغام با Legacy معمولاً bottleneck میشه. طراحی رو طوری انجام بده که اگه بعداً ERP عوض شد یا API بهتری اومد، فقط لایهٔ ACL رو عوض کنی، نه کل سیستم.

## بستر ایران و شرکت‌های داخلی

شرکت‌های بزرگ ایرانی (مثل دیجی‌کالا، اسنپ، کافه‌بازار، تپسی و ...) با مقیاس بالا و ترافیک زیاد کار می‌کنن و طبیعتاً با چالش‌های معماری مشابه (scale، deploy، تیم‌های متعدد) مواجه‌اند. جزئیات فنی معماری آن‌ها به‌ندرت به صورت رسمی منتشر میشه؛ ولی اصول کلی این سند (شروع از ساده، رشد تدریجی، Modular Monolith قبل از Microservices) برای بستر ایران هم صادقه. محدودیت‌های تحریم روی زیرساخت ابری و ابزارها هم گاهی انتخاب‌ها رو محدود می‌کنه؛ این رو در طراحی infra در نظر بگیر.

# بخش هفتم: مسیر Mid → Senior/Architect (فاز ۷)

## چه چیزهایی باید بلد باشیم (از کد به معماری)

| سطح | مهارت |
|-----|--------|
| **Mid** | کد تمیز، SOLID، الگوهای طراحی، تست واحد |
| **Senior** | معماری لایه‌ها، trade-off ها، refactoring در سطح ماژول |
| **Architect** | انتخاب معماری، هماهنگی تیم‌ها، طراحی سیستم توزیع‌شده |

**تفاوت چیه عملاً؟** میدل می‌تونه یه feature رو درست پیاده کنه و کد تمیز بنویسه. سنیور می‌فهمه این feature کجا باید بره، چطور با بقیه سیستم کار کنه، و اگه بعداً عوض شد چه تاثیری داره. معمار تصمیم می‌گیره اصلاً چه معماری داشته باشیم و چرا.

**چیکار کنم عملی؟**
یه پروژه واقعی با Clean یا Hexagonal بساز، حتی کوچیک. یا اگه توی پروژه‌ای هستی که Monolith داره، سعی کن یه ماژولش رو به صورت Modular جدا کنی. اگه بتونی توی یه پروژه Microservices (یا حداقل چند سرویس) کار کنی، خیلی چیز یاد می‌گیری.

## تفکر معماری: Trade-off ها و عدم قطعیت

هیچ تصمیم معماری «درست مطلق» نیست. همیشه trade-off داره. باید بپرسی: چی به دست می‌اریم، چی از دست می‌دیم؟ اگه شش ماه دیگه نیاز عوض شد چی؟ هزینه refactor چقدره؟

تصمیم‌هایی بگیر که بشه برگشتشون رو خورد. از ساده شروع کن، بعد تکامل بده. و حتماً جایی بنویس چرا این انتخاب رو کردی؛ چند ماه بعد یادت میره.

## مهارت‌های نرم

| طرف | چه کاری |
|-----|---------|
| **Product** | نیاز واقعی را بفهم، over-engineering نکن |
| **DB Team** | مرزها را روشن کن، Contract ها را با هم تعریف کن |
| **DevOps** | deploy و monitoring را در طراحی لحاظ کن |
| **Support** | runbook و logging/tracing را برای عیب‌یابی در نظر بگیر |
| **تیم** | معماری را توضیح بده، فرهنگ رعایت مرزها را بساز |

## سوالات مصاحبه Architect و نمونه پاسخ

**چرا Microservices انتخاب کردی یا نکردی؟**
جواب درست اینه که با Monolith شروع کردیم، و وقتی تیم به حدود ۱۵ نفر رسید و deploy هفتگی کافی نبود، ماژول‌های مشخص رو جدا کردیم. اگه بگی «همه پروژه‌ها باید Microservices باشن» یا برعکس «Microservices هیچوقت لازم نیست»، معمولاً یعنی trade-off رو درک نکردی.

**Clean Architecture چه زمانی overkill است؟**
برای CRUD ساده و تیم کوچک. overhead لایه‌ها به نتیجه نمی‌ارزه. ولی اگه پروژه قراره رشد کنه یا منطق پیچیده داره، از اول سرمایه‌گذاری روی ساختار به صرفه‌ست.

**چطور بین سرعت و کیفیت تعادل برقرار می‌کنی؟**
با Modular Monolith: مرزها رو از اول مشخص می‌کنیم ولی بدون پیچیدگی شبکه. بعداً اگه لازم شد می‌تونیم ماژول رو جدا کنیم. یا مثلاً برای MVP ساده می‌زنیم، بعد refactor تدریجی.

# بخش هشتم: خلاصه و مرجع (فاز ۸)

## جدول مقایسه نهایی

| معماری | مناسب برای | قوت اصلی | ضعف اصلی |
|--------|-------------|----------|----------|
| Data-Centric | MVP، دمو | سرعت | تست‌ناپذیر |
| Layered | تیم متوسط، پروژه متوسط | سادگی | احتمال Big Ball of Mud |
| Hexagonal | تست‌پذیری، تعویض DB/UI | وابستگی به داخل | overhead |
| Clean | منطق پیچیده، بلندمدت | نگهداری | پیچیدگی اولیه |
| Modular Monolith | رشد تدریجی | تعادل | نیاز به انضباط |
| CQRS | read-heavy | scale جدا | دو مدل |
| Event-Driven | async، loose coupling | decoupling | debug سخت |
| Microservices | تیم بزرگ، scale | deploy مستقل | پیچیدگی ops |

## چک‌لیست انتخاب معماری

- [ ] اندازه تیم را مشخص کردم
- [ ] مدت پروژه را تخمین زدم
- [ ] پیچیدگی منطق بیزنس را ارزیابی کردم
- [ ] نیاز به تست‌پذیری را در نظر گرفتم
- [ ] از ساده شروع می‌کنم (مگر دلیل قوی داشته باشم)
- [ ] مرزهای ماژول را تعریف کردم (حتی در Monolith)
- [ ] refactor و تکامل را در طرح لحاظ کردم
- [ ] اگه برونسپاری دارم: Contract ها و مرزهای ماژول را تعریف کردم
- [ ] اگه ERP یا Legacy دارم: لایهٔ ادغام (مثلاً ACL) را در نظر گرفتم

## یک نکته درباره منابع

ادعاهای مربوط به شرکت‌ها (Knight Capital، Netflix، Amazon، Shopify، Stack Overflow، Healthcare.gov) از منابع عمومی و گزارش‌های رسمی گرفته شده. اعداد تیم و سناریوها تخمین‌های کلی هستن بر اساس تجربه رایج توی صنعت، نه استاندارد قطعی. الگوهای فروشگاه، توییتر و اینستاگرام از مقالات سیستم‌دیزاین و tech blog های عمومی هستن. قانون کانوی و Inverse Conway از Melvin Conway (۱۹۶۸)، Martin Fowler و Cutter IT Journal؛ مقایسه سازمان چاق/فلت از پژوهش‌های سازمانی (از جمله Springer) و تجربهٔ عملی صنعت نرم‌افزار.
