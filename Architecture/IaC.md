## IaC چیه؟

در اصل **IaC** مخفف **Infrastructure as Code** یا همون **زیرساخت به‌عنوان کد**. یعنی زیرساخت‌های فناوری اطلاعات (شبکه، سرورها، پایگاه داده، لود بالانسر و ...) رو با کد مدیریت می‌کنی، نه با کلیک و دستکاری دستی.

### تعریف فنی‌تر

اینجا IaC یعنی توصیف وضعیت مطلوب زیرساخت در قالب فایل‌های متنی (معمولاً YAML، JSON، HCL) که قابل ذخیره در سیستم کنترل نسخه (مثل Git) هستند. سپس یه ابزار (مثل Terraform، CloudFormation) این فایل‌ها را می‌خواند و منابع رو در ارائه‌دهنده ابر (یا on‑premise) ایجاد یا به‌روز می‌کند.

**دو رویکرد اصلی:**

-اول **Declarative (اعلامی):** شما وضعیت نهایی را مشخص می‌کنید، ابزار تصمیم می‌گیرد چطور به آن برسد. مثل Terraform یا CloudFormation.
    
-دوم **Imperative (امری):** شما دقیقاً دستوراتی که باید اجرا شوند را می‌نویسید. مثل Ansible (اگرچه Ansible هم می‌تواند اعلامی باشد) یا اسکریپت‌های شل.


**مثال قدیمی (دستی):**  
۱. وارد کنسول AWS می‌شدی.  
۲. یه EC2 instance می‌ساختی با کلیک.  
۳. SSH می‌زدی تو instance.  
۴. nginx نصب می‌کردی با apt-get.  
۵. فایل کانفیگ nginx رو دستی درست می‌کردی.  
۶. firewall رو تنظیم می‌کردی.  
اگه instance می‌سوخت، باید از اول تکرار می‌کردی.

**با IaC (Terraform):**  
فایل `main.tf` به این شکل:

hcl

resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"
  user_data     = file("setup.sh")
}
resource "aws_security_group" "web_sg" {
  name = "web-sg"
  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

بعد `terraform apply` اجرا می‌کنی. همه چیز ساخته می‌شه. اگه instance خراب شد، یا دوباره apply کنی (بازسازی می‌کند) یا کل infrastructure رو با `terraform destroy` نابود می‌کنی.

### چرا IaC یه ضرورته (حتی بیشتر از چیزی که فکر می‌کنی)

۱. **قابلیت تکرار (Repeatability):** هر بار که اجرا کنی، نتیجه یکسان است. دیگه "روی ماشین من کار می‌کنه" نداریم.

۲. **نسخه‌بندی و تاریخچه:** کد زیرساخت توی Git هست. هر تغییری ثبت می‌شه. می‌تونی برگردی به نسخه قبلی اگه خراب کردی.

۳. **مستندسازی زنده:** خود کد سند است. نیازی به ویکی و نمودارهای از‌مدت‌افتاده نیست.

۴. **خودکارسازی و CI/CD:** می‌تونی توی pipeline اتوماسیون، تست کنی و بعد deploy کنی. مثلاً Terraform plan رو توی Pull Request اجرا کنی تا تأثیر تغییرات رو ببینی.

۵. **کاهش خطای انسانی:** ماشین‌ها دقیق‌تر از انسان‌ها execute می‌کنند.

۶. **مدیریت محیط‌های مختلف:** یک کد برای توسعه، استیجینگ، پروداکشن با مقادیر متغیر (مثلاً تعداد instances).

### مفاهیم عمیق‌تری که باید بلد باشی

#### ۱. **Idempotency (هم‌توانی)**

یعنی هر چند بار که یک کد IaC اجرا بشه، نتیجه نهایی همان وضعیت مطلوب است. مثلاً Terraform همیشه منابع را به وضعیت تعریف‌شده تطبیق می‌دهد. اگر منبع وجود نداشته باشد، می‌سازد. اگر وجود داشته باشد و تنظیماتش متفاوت باشد، تغییر می‌دهد. اگر با تعریف هماهنگ باشد، هیچ کاری نمی‌کند.

#### ۲. **State Management (مدیریت حالت)**

ابزارهای declarative مثل Terraform یک فایل state دارند (terraform.tfstate) که نگاشت منابع واقعی با کد را ذخیره می‌کند. این state خیلی مهم است؛ باید در جای امن (مثل remote backend S3، با locking) نگهداری شود تا چند نفر هم‌زمان conflict ایجاد نکنند.

#### ۳. **Immutable Infrastructure (زیرساخت تغییرناپذیر)**

به جای آپدیت کردن یک سرور (مثلاً با ansible-pull)، یک نسخه جدید از image (مثلاً AMI) می‌سازیم و instance جدید با image جدید جایگزین می‌شود. این رویکرد با IaC ساده می‌شود (مثلاً با Auto Scaling Group و launch template جدید).

#### ۴. **GitOps**

یعنی Git به عنوان منبع حقیقت. هر تغییری در کد زیرساخت از طریق Pull Request انجام می‌شود. بعد از merge، یک operator (مثل ArgoCD) تغییرات را به صورت خودکار در کلاستر اعمال می‌کند.

#### ۵. **ماژولار بودن**

ابزارهایی مثل Terraform اجازه می‌دهند ماژول‌های قابل استفاده مجدد بنویسیم. مثلاً یک ماژول برای وب‌سرور، یک ماژول برای دیتابیس. این باعث می‌شود کد تمیزتر و قابل اشتراک بین تیم‌ها باشد.

### ابزارهای معروف و مقایسه سریع

|ابزار|رویکرد|پلتفرم‌ها|ویژگی خاص|
|---|---|---|---|
|**Terraform**|declarative|چند ابری (AWS، Azure، GCP، ...)|محبوب‌ترین، HCL، state خارجی، community بزرگ|
|**AWS CloudFormation**|declarative|فقط AWS|بومی AWS، YAML/JSON، stack drift detection|
|**Azure Resource Manager (ARM)**|declarative|فقط Azure|JSON، ماژول‌ها|
|**Pulumi**|imperative/declarative|چند ابری|با زبان‌های عمومی (TypeScript، Python، C#)|
|**Ansible**|imperative/declarative|چند ابری + on‑premise|بدون agent، مناسب برای configuration management|
|**AWS CDK**|imperative|فقط AWS|ساخت CloudFormation با زبان‌های برنامه‌نویسی|
|**Crossplane**|declarative|کلاسترهای Kubernetes|کنترلر داخل K8s که منابع ابری را مدیریت می‌کند|

### چالش‌ها و محدودیت‌ها

- **مدیریت state حساس:** فایل state می‌تواند شامل اطلاعات محرمانه (مانند IP‌ها، آرن‌ها) باشد. باید با دقت ذخیره و access کنترل شود.
    
- **پیچیدگی وابستگی‌ها:** وقتی زیرساخت بزرگ می‌شود، گراف وابستگی‌ها پیچیده می‌شود و ممکن است تغییرات غیرمنتظره ایجاد کند.
    
- **منحنی یادگیری:** هر ابزار syntax و مفاهیم خاص خود را دارد.
    
- **اشتباهات انسانی در کد:** با اینکه خطای دستی کم می‌شود، ممکن است باگ در کد باعث تخریب منابع شود. بنابراین تست و plan ضروری است.
    

---

### ارتباط با میکروسرویس‌ها

در معماری میکروسرویس، شما ده‌ها یا صدها سرویس دارید که هر کدام ممکن است به زیرساخت جداگانه نیاز داشته باشند (مثلاً دیتابیس‌های متفاوت، صف‌ها، تنظیمات شبکه). IaC تنها راه مدیریت این پیچیدگی است. می‌توان هر سرویس را به عنوان یک مجموعه منابع تعریف کرد و با یک pipeline مستقل deploy کرد. همچنین با GitOps می‌توان استقرار خودکار و مداوم داشت.

---

**خلاصه:** IaC دیگر یک انتخاب نیست، برای تیم‌های حرفه‌ای و پروژه‌های مقیاس‌پذیر یک ضرورت است. مثل این می‌ماند که چرا از کنترل نسخه برای کد استفاده می‌کنیم. IaC همان کنترل نسخه را برای زیرساخت به ارمغان می‌آورد. اگه می‌خوای در معماری‌های مدرن (مخصوصاً میکروسرویس و کلاود) حرفی برای گفتن داشته باشی، IaC رو باید مثل کف دستت بلد باشی.
