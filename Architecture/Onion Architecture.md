# معماری پیازی (Onion Architecture)

**معماری پیازی (Onion Architecture)** توسط **Jeffrey Palermo** در سال ۲۰۰۸ معرفی شد تا بر مشکلات معماری‌های لایه‌ای سنتی (N-Layer) غلبه کند. این معماری مانند یک پیاز، از لایه‌های متحدالمرکزی تشکیل شده که هستهٔ مرکزی (Domain) را احاطه کرده‌اند و وابستگی‌ها همیشه از بیرون به سمت داخل (به سمت هسته) هستند. هدف اصلی، ایجاد سیستمی **مستقل از زیرساخت، پایگاه داده و فناوری‌های خارجی** با تمرکز بر **منطق کسب‌وکار (Domain)** است.

**اهمیت در مصاحبه:** Onion در مصاحبه‌های معماری همراه با Hexagonal و Clean مطرح می‌شود. انتظار می‌رود تفاوت با لایه‌ای، قانون وابستگی به سمت داخل، و شباهت/تفاوت با Hexagonal و Clean را بتوانید توضیح دهید.

---

## ۱. فلسفه و چرایی

### مشکل معماری لایه‌ای سنتی
در معماری لایه‌ای (N-Layer)، لایه‌ها به صورت افقی چیده می‌شوند (Presentation → Business → Data Access) و وابستگی‌ها از بالا به پایین است. این مدل مشکلاتی دارد:
- **لایه Business (منطق کسب‌وکار)** به لایه Data Access (زیرساخت) وابسته می‌شود و تغییر در دیتابیس می‌تواند منطق کسب‌وکار را تحت تأثیر قرار دهد.
- **تست‌پذیری** کاهش می‌یابد، زیرا برای تست لایه Business نیاز به دیتابیس واقعی دارید.
- **جزئیات فنی** (مانند نحوه ذخیره‌سازی) به لایه‌های داخلی نشت می‌کند.

### ایده معماری پیازی
معماری پیازی بر اصل **وارونگی وابستگی (Dependency Inversion)** استوار است. به‌جای اینکه لایه‌های بالایی به لایه‌های پایینی وابسته باشند، همهٔ لایه‌ها به **انتزاع‌ها (Abstractions/Interfaces)** که در لایه‌های داخلی تعریف شده‌اند وابسته می‌شوند. این کار باعث می‌شود:
- **هسته (Domain)** هیچ وابستگی به زیرساخت، پایگاه داده یا کتابخانهٔ خارجی نداشته باشد.
- **تست‌پذیری** به شدت افزایش یابد، زیرا هسته را می‌توان بدون هیچ وابستگی خارجی تست کرد.
- **تغییر زیرساخت** (مثلاً عوض کردن دیتابیس از SQL Server به MongoDB) فقط نیازمند نوشتن یک لایه جدید Infrastructure است و هسته دست‌نخورده باقی می‌ماند.

## ۲. لایه‌ها (از درون به بیرون)

قانون طلایی معماری پیازی این است: **"هیچ‌چیز در یک دایرهٔ داخلی نمی‌تواند از چیزی در یک دایرهٔ بیرونی باخبر باشد"**. این قانون با استفاده از **تزریق وابستگی (Dependency Injection)** پیاده‌سازی می‌شود.

```text
         ┌─────────────────────────────────────┐
         │        UI / Infrastructure          │ (بیرونی‌ترین لایه)
         │  ┌─────────────────────────────────┐ │
         │  │       Application Services      │ │
         │  │  ┌─────────────────────────────┐ │ │
         │  │  │      Domain Services        │ │ │
         │  │  │  ┌─────────────────────────┐ │ │ │
         │  │  │  │    Domain Model         │ │ │ │ (هسته)
         │  │  │  └─────────────────────────┘ │ │ │
         │  │  └─────────────────────────────┘ │ │
         │  └─────────────────────────────────┘ │
         └─────────────────────────────────────┘
```

### ۲.۱. لایهٔ Domain Model (هسته)

- **مسئولیت:** نمایش **مفاهیم و قوانین کسب‌وکار**. این لایه شامل موجودیت‌ها (Entities)، اشیای مقدار (Value Objects)، و منطق اصلی دامنه است.
- **ویژگی:** این لایه **هیچ وابستگی به هیچ لایهٔ دیگری ندارد**. اینجا محل **زبان فراگیر (Ubiquitous Language)** و مدل‌سازی دامنه است. اگر از ORM استفاده می‌کنید، موجودیت‌های این لایه باید **POCO** (Plain Old CLR Objects) و مستقل از ORM باشند.

### ۲.۲. لایهٔ Domain Services

- **مسئولیت:** شامل **منطق کسب‌وکاری است که در یک Entity خاص جا نمی‌گیرد** و به هماهنگی بین چند Entity نیاز دارد. همچنین **اینترفیس‌هایی (Ports) که برای ارتباط با دنیای خارج نیاز داریم**، مانند اینترفیس‌های Repository، در این لایه تعریف می‌شوند.
- **ویژگی:** این لایه فقط به لایهٔ Domain Model وابسته است. اینترفیس‌های تعریف شده در اینجا، قراردادهایی هستند که لایه‌های بیرونی موظف به پیاده‌سازی آن‌ها هستند.

### ۲.۳. لایهٔ Application Services

- **مسئولیت:** هماهنگ‌سازی (Orchestration) بین سرویس‌های دامنه و اینترفیس‌ها برای انجام یک **Use Case** خاص. این لایه شامل:
    - **Command/Query Handlerها** (اگر از CQRS استفاده شود)
    - **DTOها** (Data Transfer Objects) برای انتقال داده بین لایه‌ها
    - **ایجاد تراکنش** و مدیریت جریان کاری
- **ویژگی:** این لایه **هیچ منطق کسب‌وکاری ندارد** و فقط وظیفهٔ هماهنگ‌سازی را بر عهده دارد. به لایه‌های Domain Model و Domain Services وابسته است.

### ۲.۴. لایهٔ Infrastructure / UI (بیرونی‌ترین لایه)

- **مسئولیت:** شامل تمام **جزئیات فنی و زیرساختی** است که در لایه‌های داخلی فقط به صورت اینترفیس دیده می‌شوند.
- **محتویات:**
    - **پیاده‌سازی اینترفیس‌ها:** مانند `SqlOrderRepository` که اینترفیس `IOrderRepository` را پیاده‌سازی می‌کند.
    - **کدهای مربوط به پایگاه داده:** DbContextها، کانفیگ‌های EF Core، مهاجرت‌ها (Migrations).
    - **سرویس‌های خارجی:** ارسال ایمیل، فراخوانی APIهای دیگر، ثبت لاگ.
    - **ارائه (Presentation):** کنترلرهای Web API، Viewهای MVC، و هر چیزی که با کاربر در ارتباط است.
- **ویژگی:** این لایه به همهٔ لایه‌های داخلی وابسته است و در واقع **وصل‌کنندهٔ همهٔ قطعات** می‌باشد. تنظیمات **تزریق وابستگی (DI)** معمولاً در همین لایه (یا نقطه ورود برنامه) انجام می‌شود تا اینترفیس‌ها به پیاده‌سازی‌های مناسب متصل شوند.

## ۳. مقایسه با معماری‌های مشابه (هگزاگونال و تمیز)

معماری پیازی، هگزاگونال و تمیز (Clean) همگی بر اساس اصول مشترکی بنا شده‌اند :

- **قانون وابستگی (Dependency Rule):** وابستگی‌ها فقط به سمت داخل هستند.
- **تمرکز بر دامنه (Domain-Centric):** منطق کسب‌وکار در مرکز و مستقل از زیرساخت است.
- **استفاده از انتزاع و وارونگی وابستگی**.

اما تفاوت‌های ظریفی نیز دارند :

| ویژگی | معماری پیازی (Onion) | معماری هگزاگونال (Hexagonal) | معماری تمیز (Clean) |
| :--- | :--- | :--- | :--- |
| **تأکید اصلی** | لایه‌بندی دایره‌ای و جداسازی با اینترفیس | پورت‌ها (Ports) و Adapterها (Adapters) | لایه‌های مشخص با نام‌های Entities، Use Cases، Interface Adapters |
| **تعریف هسته** | Domain Model و Domain Services | Application Core (معمولاً مبهم‌تر) | Entities و Use Cases |
| **دسترسی به لایه‌ها** | لایه‌های بیرونی می‌توانند مستقیماً به هسته دسترسی داشته باشند و نیازی به عبور از همهٔ لایه‌ها نیست | ارتباط از طریق پورت‌ها و Adapterهای مشخص | مشابه پیازی، لایه‌ها می‌توانند از چند لایه عبور کنند |
| **منطق پیاده‌سازی** | تمرکز بر اشیای دامنه و وارونگی وابستگی | تمرکز بر جداسازی هسته از دنیای خارج با پورت و Adapter | تمرکز بر قانون وابستگی و استقلال از فریم‌ورک |

**نتیجه‌گیری:** هر سه معماری، انواعی از یک ایده هستند و انتخاب بین آن‌ها بیشتر به **سلیقه و زبانی که تیم با آن راحت‌تر است** بستگی دارد تا تفاوت‌های فنی بنیادین.

## ۴. مزایا

- **تست‌پذیری بسیار بالا:** هسته کاملاً مستقل است و می‌توان آن را با Unit Test به سادگی تست کرد. وابستگی‌ها به راحتی با Mock جایگزین می‌شوند.
- **جداسازی دغدغه‌ها (Separation of Concerns):** هر لایه یک مسئولیت مشخص دارد و کد بسیار تمیز و قابل نگهداری می‌شود.
- **استقلال از زیرساخت:** تغییر پایگاه داده، فریم‌ورک یا سرویس خارجی، فقط نیازمند تغییر در لایه Infrastructure است و هسته دست‌نخورده باقی می‌ماند.
- **قابلیت نگهداری بالا:** با تعریف قراردادهای واضح (اینترفیس‌ها) بین لایه‌ها، تغییرات محدود به یک بخش می‌شود و به بقیه سیستم نشت نمی‌کند.
- **تمرکز بر دامنه:** تیم مجبور است ابتدا به مدل‌سازی دقیق کسب‌وکار فکر کند و سپس به سراغ پیاده‌سازی‌های فنی برود.

---

## ۵. معایب و چالش‌ها

- **پیچیدگی اولیه بالا:** تعداد لایه‌ها و اینترفیس‌ها برای پروژه‌های کوچک می‌تواند بیش از حد باشد و به اصطلاح Over-engineering رخ دهد.
- **منحنی یادگیری:** اعضای تیم باید با مفاهیم وارونگی وابستگی، تزریق وابستگی و معماری لایه‌ای آشنا باشند.
- **نگاشت (Mapping):** برای انتقال داده بین لایه‌ها (مثلاً Entity به DTO و برعکس)، نیاز به Mapper (دستی یا خودکار مانند AutoMapper) دارید که خود باعث افزایش حجم کد و کاهش اندک کارایی می‌شود.
- **برای CRUD ساده توصیه نمی‌شود:** اگر منطق کسب‌وکار پیچیده‌ای ندارید و فقط یک CRUD ساده است، معماری پیازی بیش از حد پیچیده خواهد بود و ارزش سرمایه‌گذاری ندارد.

---

## ۶. چه زمانی استفاده کنیم؟ چه زمانی نه؟

### ✅ موارد مناسب

- **پروژه‌های بلندمدت و بزرگ** با منطق کسب‌وکار پیچیده که نیاز به نگهداری و توسعه مداوم دارند.
- **سیستم‌هایی که احتمال تغییر تکنولوژی زیرساخت (دیتابیس، سرویس‌های خارجی) در آینده وجود دارد.**
- **تیم‌های با تجربه** که با اصول SOLID و DDD آشنا هستند و می‌توانند انضباط معماری را رعایت کنند.
- **هنگامی که تست‌پذیری و استقلال از فریم‌ورک برای شما حیاتی است.**

### ❌ موارد نامناسب

- **پروژه‌های کوچک و CRUD ساده** که منطق کسب‌وکار پیچیده‌ای ندارند.
- **تیم‌های تازه‌کار** که هنوز با وارونگی وابستگی و DI آشنا نیستند.
- **زمانی که سرعت تحویل اولیه از همه‌چیز مهم‌تر است** و نمی‌توان زمان طراحی لایه‌ها را صرف کرد.

## ۷. نکات مصاحبه (برای سینیورها)

- **تفاوت Onion با Layered:** در Onion وابستگی به سمت داخل است؛ در Layered به سمت پایین. هسته در Onion از زیرساخت بی‌خبر است.
- **تفاوت Onion با Hexagonal و Clean:** هر سه قانون وابستگی یکسان دارند. Onion تأکید روی لایه‌های دایره‌ای، Hexagonal روی پورت و Adapter، Clean روی نام‌گذاری لایه‌ها (Entities، Use Cases، Interface Adapters).
- **جایگاه اینترفیس‌ها:** در لایهٔ Domain Services (یا معادل آن) تعریف می‌شوند؛ پیاده‌سازی در لایهٔ Infrastructure.

### اشتباهات رایج

- تعریف اینترفیس‌ها در لایهٔ Infrastructure به‌جای لایهٔ داخلی.
- نشت موجودیت‌های ORM یا DbContext به هسته.
- استفاده از Onion برای پروژه‌های خیلی کوچک (Over-engineering).

---

## ۸. خلاصه

معماری پیازی (Onion Architecture) یک رویکرد قدرتمند برای ساخت برنامه‌هایی با **هستهٔ غنی کسب‌وکار** است. با چیدمان دایره‌ای لایه‌ها و پیروی از **قانون وابستگی به سمت داخل**، سیستمی می‌سازیم که:
- مستقل از جزئیات فنی است.
- به سادگی قابل تست و نگهداری است.
- برای تغییرات آینده آماده است.

درست مانند دیگر معماری‌های دامنه‌محور (هگزاگونال و تمیز)، معماری پیازی نیز باید با آگاهی از **هزینه‌ها و مزایای آن** انتخاب شود و برای پروژه‌های ساده، یک معماری لایه‌ای ساده می‌تواند انتخاب بهتری باشد.
