# Clean Code — کد تمیز

بر اساس کتاب *Clean Code: A Handbook of Agile Software Craftsmanship* اثر **Robert C. Martin (Uncle Bob)**.

---

## مقدمه: کد تمیز چیست و چرا مهم است؟

**کد تمیز** (Clean Code) به کدی می‌گن که:
- **خوانا باشه** (Readable) — مثل یه کتاب داستان، هر کی می‌خونه بفهمه چی به چیه.
- **قابل نگهداری باشه** (Maintainable) — اگه خواستی یه ویژگی جدید اضافه کنی، راحت باشی و نترسی که همه چیز خراب بشه.
- **قابل توسعه باشه** (Extensible) — بشه راحت روش ساخت.

کد کثیف (Dirty Code) مثل یه اتاق به‌هم‌ریخته‌ست. اولش فکر می‌کنی "بابا فعلاً کار می‌کنه، بعداً درستش می‌کنم". ولی کمکم این اتاق انقدر شلوغ می‌شه که دیگه نمی‌تونی توش راه بری. توی پروژه‌های نرم‌افزاری، کد کثیف یه **بدهی فنی** (Technical Debt) ایجاد می‌کنه. یعنی هر روز باید سودش رو بدی: باگ بیشتر، زمان توسعه طولانی‌تر، اعصاب خوردی تیم.

بعضی وقتا این بدهی انقدر زیاد می‌شه که تنها راه چاره **بازنویسی کامل پروژه** (Rewrite) میشه. ولی اگه از اول به تمیزی کد فکر کنی، کلی وقت و پول و اعصاب تیم رو نجات میدی.

**قانون مهم:** هر بار که داری یه ویژگی جدید اضافه می‌کنی یا یه باگ رو رفع می‌کنی، سعی کن کدی که باهاش کار می‌کنی رو **کمی تمیزتر** از قبل تحویل بدی. این مثل قانون «پارک ملی» می‌مونه: «همیشه کمپ رو تمیزتر از وقتی که اومدی ترک کن.»

## فصل ۲: نام‌گذاری معنادار (Meaningful Names)

اسم‌ها توی برنامه‌نویسی خیلی مهمن. یه اسم خوب می‌تونه جای کلی کامنت رو پر کنه.

#### ۱. از اسم‌های مبهم و بی‌اطلاع دوری کن

❌ بد:
```csharp
int d; // elapsed time in days
```

✅ خوب:
```csharp
int elapsedTimeInDays;
```

#### ۲. پیشوند و پسوند بی‌خود نذار

توی زبان‌های مدرن، لازم نیست بگی `strName` یا `intAge`. تایپ متغیر رو کامپایلر می‌دونه. همچنین اگه کلاس `Person` داری، فیلد `personName` توش اضافیه. کافیه بگی `Name`.

❌ بد:
```csharp
public class Person
{
    private string personName;
    private int personAge;
}
```

✅ خوب:
```csharp
public class Person
{
    private string name;
    private int age;
}
```

#### ۳. از اسم‌هایی که فقط تو ذهن خودت معنی دارن (Mental Mapping) بپرهیز

مثال: توی یه حلقه، استفاده از `i` و `j` برای شمارنده قابل قبوله (چون خیلی رایجه)، ولی اگه یه متغیر بذاری `r` به جای `userRepository`، یکی دیگه که کد رو می‌خونه باید بره بالای صفحه ببینه `r` چیه.

❌ بد:
```csharp
var r = userRepository.GetById(id);
```

✅ خوب:
```csharp
var user = userRepository.GetById(id);
```

#### ۴. اسم کلاس باید اسم باشه، نه فعل

کلاس‌ها معمولاً اسم‌ان: `Customer`، `OrderProcessor`، `PaymentService`. از اسم‌های فعلی مثل `Process` یا `Calculate` برای کلاس استفاده نکن.

#### ۵. پسوندهای تکراری (Manager, Processor, Provider, Handler, Factory) رو بی‌خود استفاده نکن

اگه کل سیستم پر بشه از `XYZManager`، `ABCProcessor`، تمایز بینشون سخت میشه. سعی کن اسم‌ها معنی‌دار باشن و نشون بدن کلاس دقیقاً چیکار می‌کنه. مثلاً به جای `OrderManager`، می‌تونی `OrderService` یا `OrderProcessor` بذاری، ولی اگه همه جا از `Manager` استفاده کنی، دیگه هیچی معلوم نیست.

#### ۶. کلاس‌ها: عبارت‌های اسمی، متدها: عبارت‌های فعلی

متدها باید کار رو برسونن: `GetUser()`، `CalculateTotal()`، `SendEmail()`. کلاس‌ها باید چیزها رو توصیف کنن: `User`، `ShoppingCart`، `EmailSender`.

#### ۷. برای ساخت آبجکت‌های مختلف با کانستراکتورهای متفاوت، از متدهای استاتیک با اسم‌های واضح استفاده کن

فرض کن کلاس `User` داری که دو جور ساخته میشه: یکی با ایمیل و پسورد، یکی با شماره موبایل. به جای اینکه کانستراکتورهای مختلف بذاری که تشخیصشون سخت باشه، می‌تونی از **Factory Method**های استاتیک استفاده کنی:

```csharp
public class User
{
    private User(string email, string password) { ... }
    private User(string phoneNumber) { ... }
    
    public static User CreateWithEmail(string email, string password) => new User(email, password);
    public static User CreateWithPhone(string phoneNumber) => new User(phoneNumber);
}
```

حالا موقع استفاده:
```csharp
var user1 = User.CreateWithEmail("a@b.com", "123");
var user2 = User.CreateWithPhone("09123456789");
```

#### ۸. برای هر مفهوم، یه کلمه ثابت استفاده کن

مثلاً توی کل سیستم، یه جا نگو `FetchUser`، یه جا نگو `GetUser`، یه جا `RetrieveUser`. یکیش رو انتخاب کن و همیشه استفاده کن.

#### ۹. اسم‌های مرتبط با دامنه کسب‌وکار رو انتخاب کن

تیم بیزنس می‌گه "مشتری"، تو کد نذار `Client`، بذار `Customer`. اینطوری همه راحت‌تر ارتباط برقرار می‌کنن.

#### ۱۰. اسم‌های کوتاه بهتر از بلندن، به شرطی که شفاف باشن

`user` از `currentUserLoggedInToTheSystem` بهتره. اما `u` از `user` بدتره.

## فصل ۳: توابع (Functions)

#### ۱. تابع باید کوتاه باشه

قانون سرانگشتی: اگه یه تابع از ۲۰-۳۰ خط بیشتر شد، بو می‌ده. احتمالاً چند کار رو باهم داره انجام می‌ده.

#### ۲. تابع فقط یه کار انجام بده (Do One Thing)

این اصل شاید ساده به نظر بیاد، ولی توی عمل سخته. یه راه برای تشخیص این که تابع یه کار انجام میده اینه: **آیا می‌تونی یه اسم دیگه براش بذاری که دقیقاً کاری رو که می‌کنه توصیف کنه؟** اگه مجبور بشی از کلمات "و" (and) توی اسم استفاده کنی، یعنی چند کار داره.

❌ بد:
```csharp
void ProcessOrderAndSendEmail(Order order)
{
    // پردازش سفارش
    // ارسال ایمیل
}
```

✅ خوب:
```csharp
void ProcessOrder(Order order)
{
    // پردازش سفارش
}
void SendEmailConfirmation(Order order)
{
    // ارسال ایمیل
}
```

#### ۳. هر بلاک شرطی باید کوتاه باشه

توی `if`، `else`، `while` و ... سعی کن فقط یه خط کد باشه (معمولاً فراخوانی یه تابع دیگه). این باعث می‌شه تابع اصلی خونده بشه و جزئیات بره توی توابع دیگه.

❌ بد:
```csharp
if (user.IsActive)
{
    // 10 خط کد برای ارسال ایمیل
}
```

✅ خوب:
```csharp
if (user.IsActive)
    SendWelcomeEmail(user);
```

#### ۴. قانون Step-down: توابع رو به ترتیب سلسله‌مراتب بنویس

یعنی اول تابع اصلی که کارهای سطح بالا رو می‌گه، بعد توابع کمکی که جزئیات رو پیاده می‌کنن. اینجوری وقتی کد رو می‌خونی، مثل این می‌مونه که از بالا به پایین داری یه داستان رو می‌خونی.

#### ۵. Switch statement رو مخفی کن

سوییچ‌ها معمولاً نشونه‌ی انجام چند کار هستن. می‌تونی با استفاده از **Abstract Factory** یا **پلی‌مورفیسم**، سوییچ رو به یه جا محدود کنی.

مثلاً به جای این که توی چند جا سوییچ روی نوع کاربر داشته باشی:

```csharp
double CalculateDiscount(User user)
{
    switch (user.Type)
    {
        case "Gold": return 0.2;
        case "Silver": return 0.1;
        default: return 0;
    }
}
```

می‌تونی از پلی‌مورفیسم استفاده کنی:

```csharp
interface IDiscountStrategy
{
    double GetDiscount();
}
class GoldDiscount : IDiscountStrategy { public double GetDiscount() => 0.2; }
class SilverDiscount : IDiscountStrategy { public double GetDiscount() => 0.1; }
// و بعد توی کلاس User، یک خاصیت از نوع IDiscountStrategy داشته باشی.
```

حالا سوییچ فقط یه جا (موقع ساختن کاربر) اجرا می‌شه.

#### ۶. همیشه در حال ريفکتور باش

وقتی داری کد می‌نویسی، مدام به این فکر کن که "آیا می‌شه اینو بهتر کرد؟" اگه جواب مثبت بود، همین الان انجام بده. "بعداً درست می‌کنم" یعنی "هیچ‌وقت".

### آرگومان‌های توابع (بخشی از فصل ۳)

#### ۱. تعداد آرگومان‌ها رو کم کن

حالت ایده‌آل: **بدون آرگومان**. بعدی: یه آرگومان، دو آرگومان، سه آرگومان. بیشتر از سه تا دیگه خیلی بده.

چرا؟ چون هر چی آرگومان بیشتر باشه، تست کردن سخت‌تر می‌شه، فهمیدنش سخت‌تر می‌شه، و احتمال خطا بالا می‌ره.

#### ۲. از آرگومان‌های بولین بپرهیز

وقتی تابعی یه پارامتر `bool` می‌گیره، یعنی احتمالاً داری دو کار مختلف رو با یه تابع انجام میدی. بهتره دو تابع جدا بسازی.

❌ بد:
```csharp
void UpdateUser(int id, bool sendEmail) { ... }
UpdateUser(123, true); // یعنی آپدیت کن و ایمیل بفرست
UpdateUser(456, false); // یعنی فقط آپدیت کن، ایمیل نده
```

✅ خوب:
```csharp
void UpdateUser(int id) { ... }
void UpdateUserAndSendEmail(int id) { ... }
```

#### ۳. آرگومان‌های تکراری رو گروه‌بندی کن

اگه چند تا پارامتر داریم که همیشه با هم میان (مثل مختصات `x` و `y`)، می‌تونیم اون‌ها رو توی یه کلاس بسته‌بندی کنیم.

❌ بد:
```csharp
void DrawRectangle(int x, int y, int width, int height) { ... }
```

✅ خوب:
```csharp
class Point { public int X; public int Y; }
class Size { public int Width; public int Height; }
void DrawRectangle(Point position, Size size) { ... }
```

#### ۴. از اشیا به عنوان پارامتر استفاده کن تا تعداد کم بشه

مثلاً به جای ۵ تا پارامتر، یه شیء بدیش که اون ۵ تا رو توش داره.

### ساید افکت (Side Effects) — بخشی از فصل ۳

**ساید افکت** یعنی تابع قول داده یه کار رو بکنه، ولی تو دلش کار دیگه‌ای هم انجام بده. این یه دروغ بزرگ به خواننده‌ست.

مثال:
```csharp
bool CheckPassword(string userName, string password)
{
    var user = userRepository.GetByUserName(userName);
    if (user == null) return false;
    if (user.Password != password) return false;
    user.LastLogin = DateTime.Now; // <-- ساید افکت! قرار بود فقط چک کنه، ولی تاریخ رو هم عوض کرد
    return true;
}
```

کسی که این تابع رو می‌خونه، فکر می‌کنه فقط بررسی می‌کنه رمز درسته یا نه. ولی غافل از اینکه تاریخ آخرین ورود رو هم آپدیت می‌کنه. این می‌تونه باعث باگ‌های عجیب بشه.

**راه حل:** یا اسم تابع رو عوض کن (مثلاً `CheckPasswordAndUpdateLastLogin`)، یا عملیات آپدیت رو جدا کن.

## فصل ۴: کامنت‌ها (Comments)

#### ۱. کامنت خوب جایگزین کد بد نیست

اگه کدت انقدر بد شده که مجبوری براش کامنت بنویسی، برو کد رو تمیز کن، نه اینکه کامنت بذاری.

#### ۲. کامنت‌های توضیح‌دهنده‌ی "چرا" مفیدن

کامنت‌ها باید دلیل تصمیمات رو توضیح بدن، نه این که "چی" داره اتفاق می‌افته. "چی" رو خود کد باید بگه.

❌ بد:
```csharp
// i رو یکی زیاد کن
i++;
```

✅ خوب:
```csharp
// چون کاربر می‌تونه از ۱ شماره‌گذاری کنه، ما ۰ ایندکس رو به ۱ تبدیل می‌کنیم
i++;
```

#### ۳. از کامنت‌های TODO با احتیاط استفاده کن

بعضی از IDEها `// TODO` رو هایلایت می‌کنن. خوبه برای یادآوری کارهایی که باید انجام بشن، ولی اگه زیاد بشه، یعنی بی‌نظمی.

#### ۴. کامنت‌های اجباری مثل مجوز و کپی‌رایت مشکلی ندارن.

**قانون طلایی عمو باب:**  
> کامنت‌ها همیشه یه شکست هستن. چون اگه کد به‌اندازه‌ی کافی گویا بود، نیازی به کامنت نداشتیم.

**کامنت خوب نیست، کد خوبه.** کامنت‌ها دروغ می‌گن؛ نه عمداً، بلکه چون کد evolve می‌شه ولی کامنت‌ها آپدیت نمی‌شن. چند ماه بعد، کامنت و کد دیگه با هم جور درنمیان.

**چه کامنت‌هایی خوبن؟**  
۱. قانونی (کپی‌رایت، لایسنس).  
۲. اخطار (هشدار به برنامه‌نویس دیگر، مثلاً «این متد ترد-سیف نیست»).  
۳. TODO فقط اگر واقعاً قرار باشه بعداً انجام بشه.  
۴. توضیح «چرا»، نه «چی».

**چه کامنت‌هایی بدترینن؟**  
کامنت اضافی و بدیهی (`i++; // i رو یکی زیاد کن`)، تکرار کد، کد کامنت‌شده (همیشه پاک کن؛ Git هست)، ژورنالی (تاریخچه در Git باشد).

## فصل ۵: قالب‌بندی (Formatting)

#### قالب‌بندی عمودی

- **استعاره روزنامه:** فایل رو مثل روزنامه در نظر بگیر. تیتر و چکیده بالا، جزئیات پایین. هر چی مهم‌تره، بالاتر.
- **فاصله‌های عمودی:** بین مفاهیم مختلف، خط خالی بذار. بین خطوط مرتبط، خط خالی نذار.
- **وابستگی‌ها:** توابعی که همدیگه رو صدا می‌زنن، باید نزدیک هم باشن. معمولاً تابع caller بالای callee قرار می‌گیره .
- **متغیرها:** متغیرهای محلی باید تا حد امکان نزدیک به محلی که استفاده می‌شن تعریف بشن. متغیرهای عضو (instance variables) رو همه می‌ذارن بالای کلاس.

#### قالب‌بندی افقی

- **طول خط:** عمو باب می‌گه سعی کن خطوط بیشتر از ۱۲۰ کاراکتر نشن.
- **فاصله‌های افقی:** بین عملگرها فاصله بذار. برای گروه‌بندی مفاهیم از فاصله استفاده کن.
  ```csharp
  var total = price * quantity + tax;  // ✅ خوب
  var total=price*quantity+tax;        // ❌ بد
  ```
- **تورفتگی (Indentation):** قاتل اصلی خوندایی کد. حتماً رعایت کن.

#### قانون تیمی

> یه تیم باید روی یه استایل واحد توافق کنه. هر کی هر جور دوست داره کد بزنه، هرج و مرج ایجاد می‌کنه. از ابزارهای خودکار مثل EditorConfig یا Prettier استفاده کن.

## فصل ۶: اشیا و ساختارهای داده (Objects and Data Structures)

این فصل یکی از عمیق‌ترین بخش‌های کتاب است. عمو باب اینجا یه تمایز مهم ایجاد می‌کنه.

### ۱. آبسترکشن، نه پیاده‌سازی

**اصل:** نباید به بیرون بگی که "من یه فیلد دارم". باید به بیرون بگی "من می‌تونم یه کاری بکنم".

❌ بد (همه چی رو لو دادی):
```csharp
public class Point
{
    public double x;
    public double y;
}
```

✅ خوب (فقط قرارداد رو گفتی):
```csharp
public interface Point
{
    double GetX();
    double GetY();
    void SetCartesian(double x, double y);
    void SetPolar(double rho, double theta);
}
```
دقت کن اینجا کسی نمی‌دونه که داده به چه شکلی ذخیره شده. فقط می‌دونه چه عملیاتی می‌تونه انجام بده.

### ۲. تمایز Objects vs. Data Structures

| | **Object** | **Data Structure** |
|---|---|---|
| **تعریف** | داده رو پشت آبسترکشن قایم می‌کنه و فقط متد (رفتار) رو نشون می‌ده | داده رو مستقیماً expose می‌کنه و رفتار معنی‌داری نداره |
| **مثال** | کلاس‌های Domain، Service | DTOها، POCOهای ساده |
| **افزودن قابلیت** | کلاس جدید می‌سازی (محافظت در برابر تغییر نوع داده) | تابع جدید می‌نویسی (محافظت در برابر تغییر رفتار) |

عمو باب می‌گه: "شیء داده رو پشت آبسترکشن قایم می‌کنه و توابعی روی اون داده expose می‌کنه. ساختار داده داده‌هاش رو expose می‌کنه و تابع معنی‌داری نداره." 

**نتیجه عملی:** هیچ‌وقت توی یه کلاس، هم داده expose بشه هم تابع بیزنس نداشته باشه. این گیج‌کننده‌ست.

### ۳. قانون دیمیتر (Law of Demeter) 

قانون می‌گه: "حرف نزن با غریبه‌ها!" یعنی متدهای یه شیء فقط باید با اینا کار کنن:
- خود شیء
- آبجکت‌هایی که به عنوان آرگومان گرفتن
- آبجکت‌هایی که خودشون ساختن
- آبجکت‌های عضو (member) خودش

**علائم نقض (Train Wreck):**
```csharp
var outputDir = ctxt.GetOptions().GetScratchDir().GetAbsolutePath();  // ❌ قطار!
```
این زنجیره یعنی کد ما زیادی به ساختار داخلی ctxt وابسته‌ست. اگه یه تیکه از این زنجیره عوض بشه، کل کد می‌شکنه.

**راه‌حل:** از شیء بخواه کاری برات بکنه، نه این که بری توی دلش و داده‌هاش رو بکشی بیرون.

### ۴. Data Transfer Objects (DTO) 

DTOها ساختار داده‌ی خالصن. فقط فیلد دارن، رفتار ندارن. عالی هستن برای:
- فرستادن داده به دیتابیس
- سریالایز کردن به JSON برای API
- عبور از مرزهای معماری (مثل لایه‌ها)

---

## فصل ۷: مدیریت خطا (Error Handling)

### ۱. از Exception استفاده کن، نه کد خطا

❌ بد (قدیمی، مثل C):
```csharp
int result = divide(a, b);
if (result == -1) { /* خطا */ }
```

✅ خوب:
```csharp
try
{
    var result = Divide(a, b);
}
catch (DivideByZeroException ex)
{
    // مدیریت خطا
}
```

### ۲. try-catch-finally رو اول بنویس

وقتی داری تابعی می‌نویسی که ممکنه خطا بده، اول try-catch رو بنویس، بعد logic رو. این باعث می‌شه مرز بین logic و error handling واضح باشه .

### ۳. به Exceptionها Context بده

وقتی exception پرتاب می‌کنی، یه پیغام خوب بهش بده که بگه کجا و چرا:
```csharp
throw new InvalidOperationException("User not found with ID: " + userId);
```

### ۴. Exception کلاس‌ها رو بر اساس نیاز caller تعریف کن 

❌ بد (سه تا exception جدا):
```csharp
try { ... }
catch (DeviceNotFoundException) { ... }
catch (ATM216Exception) { ... }
catch (NetworkUnavailableException) { ... }
```

✅ خوب (یک exception با wrapper):
```csharp
try { ... }
catch (Exception ex)
{
    throw new LocalPortException("Port failed: " + port, ex);
}
```

### ۵. از Null استفاده نکن! 

عمو باب خیلی روی این تأکید داره: **هیچ‌وقت از توابع null برنگردون. هیچ‌وقت null رو به تابع پاس نده.**

❌ بد:
```csharp
public User GetUser(int id)
{
    if (notFound) return null;
}
```

✅ خوب (از Null Object Pattern یا Exception استفاده کن):
```csharp
public User GetUser(int id)
{
    if (notFound) throw new UserNotFoundException();
    // یا
    return NullUser.Instance;  // Null Object Pattern
}
```

اگه null رو قبول کنی، همه جا باید چک کنی `if (user == null)` و این کد رو کثیف می‌کنه.

---

## فصل ۸: مرزها (Boundaries)

مرزها جایی است که کد ما با کد شخص ثالث (Third-party) یا کدی که هنوز نوشته نشده ملاقات می‌کند.

### ۱. کد شخص ثالث

وقتی از کتابخونه‌ای مثل log4j استفاده می‌کنی، مستقیم به API اون وابسته نشو. یه لایه (Wrapper) بذار بین کد خودت و اون کتابخونه.

**مزیت:**
- اگه کتابخونه عوض شد، فقط یه جا باید تغییر بدی.
- API کتابخونه رو به چیزی که خودت می‌خوای، محدود می‌کنی.

### ۲. Learning Tests 

قبل از استفاده از یه کتابخونه، تست بنویس که باهاش آشنا شی. این تست‌ها:
- بهت یاد می‌دن کتابخونه چطور کار می‌کنه.
- بعداً می‌تونن بفهمن کتابخونه آپدیت شده و رفتارش عوض شده یا نه.

### ۳. کدی که هنوز وجود نداره

بعضی وقتا وابسته به کدی هستی که یکی دیگه باید بنویسه. اینجا می‌تونی یه اینترفیس (Facade) تعریف کنی که خودت می‌خوای. بعداً وقتی کد واقعی اومد، یه Adapter می‌نویسی که اینترفیس تو رو به اون وصل کنه .

---

## فصل ۹: تست‌های واحد (Unit Tests)

کد تمیز بدون تست قابل اعتماد نیست. تست‌ها هم باید تمیز باشن: یک چیز را ثابت کنند، اسم واضح داشته باشند (مثلاً `Should_ThrowException_When_DivideByZero`)، و از الگوی **Arrange-Act-Assert** استفاده کنند.

### قوانین سه‌گانه TDD (Test-Driven Development) 

1. تا وقتی تست واحد failing ننوشتی، اجازه نداری کد تولیدی (production code) بنویسی.
2. بیشتر از حد لازم برای fail کردن تست، تست ننویس.
3. بیشتر از حد لازم برای pass کردن تست، کد تولیدی ننویس.

### تست‌ها هم باید تمیز باشن

تست‌ها مثل کد تولیدی اهمیت دارن. تست کثیف:
- اعتماد به سیستم رو کم می‌کنه.
- نگهداریش سخته.
- بعد از مدتی همه ازش فرار می‌کنن و دیگه اجراش نمی‌کنن.

### اصول FIRST برای تست‌ها 

- **F**ast: تست باید سریع اجرا بشه.
- **I**ndependent: تست‌ها به هم وابسته نباشن.
- **R**epeatable: توی هر محیطی جواب بده.
- **S**elf-validating: خروجی boolean داشته باشه (pass/fail).
- **T**imely: در زمان مناسب نوشته بشه (همون TDD).

### یک Assert در هر تست 

عمو باب می‌گه بهتره هر تست فقط یه چیز رو ثابت کنه. این باعث می‌شه اسم تست معنی‌دار باشه و وقتی تست fail می‌شه، دقیقاً بدونی کجا خراب شده.

---

## فصل ۱۰: کلاس‌ها (Classes)

### کلاس‌ها باید کوچک باشند، ولی معیار کوچیکی متفاوته

برای توابع، معیار "خط کد" بود. برای کلاس‌ها، معیار "مسئولیت" هست.

### اصل تک مسئولیتی (SRP) 

> یک کلاس باید فقط یک دلیل برای تغییر داشته باشه.

❌ بد: کلاسی که هم کاربر رو validate می‌کنه، هم توی دیتابیس ذخیره می‌کنه، هم ایمیل می‌فرسته.

✅ خوب: هر کدوم از اینا بره توی یه کلاس جدا.

### انسجام (Cohesion) بالا

وقتی متغیرهای عضو کلاس توسط اکثر متدها استفاده می‌شن، انسجام بالاست. وقتی می‌بینی چندتا متد از یه متغیر اصلاً استفاده نمی‌کنن، بو می‌ده. احتمالاً وقت تقسیم کلاس رسیده.

### سازماندهی برای تغییر 

کلاس‌ها باید طوری طراحی بشن که در برابر تغییرات جدید باز باشن (OCP). یعنی بتونی قابلیت جدید اضافه کنی بدون اینکه مجبور باشی کلاس موجود رو تغییر بدی.

---

## فصل ۱۱: سیستم‌ها (Systems)

این فصل در سطح بالاتری صحبت می‌کند: معماری سیستم.

### جداسازی ساختن از استفاده کردن (Separation of Construction from Use)

هر برنامه دو مرحله داره:
1. ساختن اشیا و وابستگی‌ها (startup)
2. اجرای منطق

این دو تا رو قاطی نکن. از Dependency Injection استفاده کن.

### مقیاس‌پذیری (Scaling Up)

سیستم‌ها یک‌شاخه بزرگ نمی‌شن. باید incremental رشد کنن. با معماری تمیز و تست‌های خوب، می‌تونی به تدریج سیستم رو scale کنی.

### زبان‌های خاص دامنه (DSL)

DSLها بهت اجازه می‌دن منطق بیزنس رو به زبونی نزدیک به دامنه بنویسی. این کار ارتباط با stakeholders رو راحت‌تر می‌کنه و کد رو گویاتر.

---

## فصل ۱۲: طراحی نوظهور (Emergent Design)

عمو باب چهار قانون برای «طراحی ساده» دارد که کنت بک مطرح کرده است:

### قوانین طراحی ساده (Simple Design Rules)

1. **همه تست‌ها رو پاس کن:** سیستمی که تست نداره، غیرقابل اعتماده و تغییرش ترسناکه.
2. **تکرار نداشته باش:** DRY (Don't Repeat Yourself). هر جا تکراری دیدی، باید یه انتزاع باهاش درست کنی.
3. **قصد برنامه‌نویس رو برسون:** کد باید گویا باشه و بگه چی می‌خواد بکنه.
4. **کلاس‌ها و متدها رو کم کن:** فقط به اندازه نیاز کلاس و متد بساز. نه بیشتر.

---

## فصل ۱۳: هم‌روندی (Concurrency)

این فصل سنگین است. عمو باب می‌گوید concurrency از بقیهٔ مسائل جداست و باید جداگانه به آن فکر کرد.

### اصول دفاعی در concurrency

- **SRP:** کدهای concurrent رو از بقیه کدها جدا کن.
- **محدود کردن دسترسی:** بخش‌هایی که synchronized می‌کنی رو تا حد ممکن کوچیک کن.
- **کپی کردن داده:** گاهی بهتره یه کپی از داده به هر ترد بدی تا اینکه مجبور باشی data رو share کنی.
- **تردها باید مستقل باشن:** هر ترد باید تا حد ممکن به تردهای دیگه وابسته نباشه.

### کتابخونه‌ها رو بشناس

از کلاس‌های thread-safe استفاده کن. مثل ConcurrentHashMap توی جاوا. خودت پیاده‌سازی نکن مگر مجبور باشی.

### تست هم‌روندی سخته

اگه یه تست گاهی pass می‌شه گاهی fail، یعنی مشکل concurrency داری. ابزارهای مثل FindBugs یا ترد تسترها می‌تونن کمک کنن.

---

## فصل ۱۷: بوها و اکتشافات (Smells and Heuristics)

آخرین فصل کتاب یک لیست از ۶۶ «بو» (bad smell) و راهنمایی برای تمیز کردن کد است. چند مورد مهم:

### بوهای مربوط به کامنت

- کامنت‌های نامناسب
- کامنت‌های قدیمی
- کامنت‌های اضافی
- کد کامنت‌شده

### بوهای مربوط به محیط

- build چند مرحله‌ای
- تست چند مرحله‌ای

### بوهای مربوط به توابع

- آرگومان زیاد
- آرگومان خروجی
- پرچم به عنوان آرگومان

### بوهای عمومی

- کد مرده (Dead Code)
- تکرار (Duplication)
- جادو (Magic Numbers)
- قضیه دیمیتر نقض شده
- switch/if طولانی
- تابعی که چند کار می‌کنه
