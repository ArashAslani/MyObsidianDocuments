## HTTP چیه؟ (از صفر تا صد)

### یه نگاه کلی

اصطلاح HTTP مخفف **Hypertext Transfer Protocol** یا همون **پروتکل انتقال ابرمتن** هستش. بیایم ساده بگیم: این قانونی‌ست که مرورگر و سرور با هم حرف می‌زنن. هر بار که یه سایت رو باز می‌کنی، مرورگرت یه درخواست HTTP می‌فرسته، سرور جواب میده.

خود HTTP یه پروتکل **لایهٔ کاربرد** (Application Layer) هست که روی TCP/IP سوار می‌شه. یعنی اگه TCP/IP رو بگیم جاده‌ست، HTTP ماشینه که توش داده جابه‌جا می‌کنه.

**تعریف رسمی‌ش** (مطابق RFC):

> HTTP is a stateless application-level protocol for distributed, collaborative, hypertext information systems.

---

### معماری HTTP چطور کار می‌کنه؟

ساختارش خیلی ساده‌ست: **کلاینت (Client)** می‌گه، **سرور (Server)** می‌شنوه و جواب می‌ده.

**سه تا جزء اصلی داریم:**

1. **کلاینت (User-Agent):** معمولاً مرورگر (مثل Chrome یا Firefox). گاهی وقتا ابزارهایی مثل `curl` یا یه اپلیکیشن موبایل هم می‌تونن کلاینت باشن.

2. **سرور (Web Server):** همونجایی که درخواست می‌ره و پردازش می‌شه. Apache، Nginx، IIS از معروف‌ترینان.

3. **پروکسی (Proxy):** یه چیزایی میان‌تایم هستن که کارهای مختلفی می‌کنن: کش می‌گیرن، فیلتر می‌کنن، لود بالانس می‌کنن، یا احراز هویت انجام می‌دن.

---

### نسخه‌های مختلف HTTP (چجوری تکامل پیدا کرد)

خب HTTP از روز اولش تا حالا کلی تغییر کرده:

| نسخه | سال | ویژگی‌های مهم |
|------|-----|---------------|
| HTTP/0.9 | 1991 | فقط GET داشت، خیلی ساده |
| HTTP/1.0 | 1996 | هدر اضافه شد، انواع محتوا اومد |
| HTTP/1.1 | 1999 | **اتصال پایدار** (Keep-Alive)، هاست اجباری، pipeline |
| HTTP/2 | 2015 | **مالتی‌پلکسینگ**، فشرده‌سازی هدر، باینری شدن |
| HTTP/3 | 2022 (RFC 9114) | به‌جای TCP روی **QUIC** (استاندارد IETF، RFC 9000؛ روی UDP)، اتصال سریع‌تر و مقاوم‌تر در برابر از دست دادن بسته |

**نتیجه عملی:** در سناریوهای با تعداد زیاد درخواست هم‌زمان (مثلاً بارگذاری چند منبع یک صفحه)، HTTP/2 به‌خاطر مالتی‌پلکسینگ و فشرده‌سازی هدر معمولاً کارایی بهتری نسبت به HTTP/1.1 داره. عدد دقیق به نوع ترافیک و شبکه بستگی داره.

---

### ساختار پیام‌های HTTP

هر چی توی HTTP رد و بدل می‌شه، دو تا شکل داره: **درخواست (Request)** و **پاسخ (Response)**. هر دو تا از سه تا قسمت تشکیل شدن:

1. **خط شروع (Start Line)** - یا همون request line توی درخواست، status line توی پاسخ
2. **هدرها (Headers)** - یه سری کلید-مقدار هستن
3. **بدنه (Body)** - اختیاری، داده اصلی اینجاست

#### درخواست (Request) چجوریه؟

```http
POST /api/users HTTP/1.1
Host: example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOiJ...
Content-Length: 42

{
  "name": "Ali",
  "age": 30
}
```

اینجا:
- خط اول: متد (`POST`) + مسیر (`/api/users`) + نسخه (`HTTP/1.1`)
- بعدش هدرها (تا قبل از یه خط خالی)
- بعد از خط خالی، بدنه (اگه باشه)

#### پاسخ (Response) چجوریه؟

```http
HTTP/1.1 201 Created
Content-Type: application/json
Cache-Control: max-age=3600

{
  "id": 12345,
  "name": "Ali",
  "createdAt": "2024-01-15T10:30:00Z"
}
```

اینجا:
- خط اول: نسخه + کد وضعیت (`201`) + پیام (`Created`)
- بعد هدرها
- بعد بدنه

---

### متدهای HTTP (چیکار می‌خوای بکنی؟)

متدها به سرور می‌گن که چه عملیاتی می‌خوایم انجام بدیم:

| متد         | توضیح                  | ایمن (Safe) | یک‌سان‌تأثیر (Idempotent)             |
| ----------- | ---------------------- | ----------- | ------------------------------------- |
| **GET**     | گرفتن اطلاعات          | ✅ آره       | ✅ آره                                 |
| **HEAD**    | مثل GET، فقط بدون بدنه | ✅ آره       | ✅ آره                                 |
| **POST**    | ایجاد منبع جدید        | ❌ نه        | ❌ نه                                  |
| **PUT**     | جایگزینی کامل منبع     | ❌ نه        | ✅ آره                                 |
| **PATCH**   | تغییر جزئی منبع        | ❌ نه        | بستگی به پیاده‌سازی داره (معمولاً نه) |
| **DELETE**  | حذف منبع               | ❌ نه        | ✅ آره                                 |
| **OPTIONS** | متدهای مجاز رو می‌گه   | ✅ آره       | ✅ آره                                 |

**ایمن (Safe):** یعنی سمت سرور چیزی رو تغییر نمی‌ده؛ پس میشه بدون نگرانی کش کرد یا پیش‌بارگذاری کرد.  
**یک‌سان‌تأثیر (Idempotent):** یعنی اجرای چندبارهٔ همان درخواست نتیجهٔ معادل یک بار اجرا رو میده. برای retry و بازیابی از خطای شبکه مهمه: GET، PUT، DELETE رو میشه در صورت قطع یا timeout دوباره فرستاد؛ POST و PATCH رو نباید بدون مکانیزم (مثلاً idempotency key) خودکار retry کرد.

---

### کدهای وضعیت (Status Codes) - سرور چی می‌گه؟

کد وضعیت ۳ رقمی‌ هست که توی خط اول پاسخ میاد. دسته‌بندیش بر اساس رقم اول:

**1xx (اطلاعاتی):** یعنی "دارم کار می‌کنم، صبور باش"
- `100 Continue`: ادامه بده، تا حالا اوکی بوده

**2xx (موفقیت):** یعنی "انجام شد"
- `200 OK`: همه چی اوکی، نتیجه رو ببین
- `201 Created`: منبع جدید ساخته شد (معمولاً بعد POST)
- `204 No Content`: موفق بود ولی چیزی برای نمایش ندارم

**3xx (ردایرکت):** یعنی "اینو یه جای دیگه بگرد"
- `301 Moved Permanently`: آدرس عوض شده، دفعه بعد برو اینجا
- `304 Not Modified`: از آخرین باری که اومدی، چیزی عوض نشده (کش)

**4xx (خطای کلاینت):** یعنی "تقصیر توئه"
- `400 Bad Request`: درخواستت خرابه، دوباره بفرست
- `401 Unauthorized`: اول باید خودتو معرفی کنی
- `403 Forbidden`: معرفی کردی ولی اجازه نداری
- `404 Not Found`: همچین چیزی اینجا نیست
- `408 Request Timeout`: سرور منتظر موند، درخواست کامل نشد
- `409 Conflict`: وضعیت منبع با درخواستت تضاد داره (مثلاً تداخل نسخه)
- `429 Too Many Requests`: داری زیاد درخواست می‌دی، یه کم صبر کن (نرخ محدود / rate limit)
- `422 Unprocessable Entity`: درخواست درست فرمت شده ولی از نظر منطق بیزنس قابل قبول نیست (معمولاً validation)

**5xx (خطای سرور):** یعنی "ببخشید، مشکل از منه"
- `500 Internal Server Error`: یه چیزی خراب شد، نمی‌دونم چی
- `502 Bad Gateway`: یکی از پشت‌صحنه‌ها جواب نمی‌ده
- `503 Service Unavailable`: سرم شلوغه، بعداً بیا

---

### هدرهای HTTP (جزئیات بیشتر)

هدرها کلید-مقدارهایی هستن که اطلاعات بیشتری می‌دن:

**هدرهای عمومی (General Headers):**
- `Cache-Control: max-age=3600`: تا یه ساعت کشش کن
- `Connection: keep-alive`: تا می‌تونی همین اتصال رو نگه دار

**هدرهای درخواست (Request Headers):**
- `Host: example.com`: به کدوم سرور داری می‌گی (اجباری توی HTTP/1.1)
- `User-Agent: Mozilla/5.0...`: مرورگر من اینه
- `Accept: application/json`: فرمت جواب رو JSON می‌خوام
- `Authorization: Bearer <token>`: من اینم
- `Cookie: sessionId=abc123`: من قبلاً اومده بودم، یادت هست؟

**هدرهای پاسخ (Response Headers):**
- `Content-Type: application/json`: داده‌ای که می‌فرستم این شکلیه
- `Content-Length: 123`: اندازه داده‌ها ۱۲۳ بایته
- `Set-Cookie: sessionId=abc123`: این کوکی رو ذخیره کن برای دفعه بعد
- `Location: /new-url`: برو اینجا (برای ردایرکت‌ها)

## مفاهیم کلیدی HTTP (عمیق‌تر و برای تصمیم‌گیری مهندسی)

بیا بریم لایه‌های زیرین رو واکاوی کنیم. اینجا قراره دیگه سطحی نگاه نکنیم. می‌خوام بعد از خوندن این بخش، نه‌تنها بفهمی چطور کار می‌کنه، بلکه بتونی توی پروژه واقعی تصمیم بگیری که از کدوم ویژگی کی استفاده کنی و چرا.

---

### ۱. بی‌حالتی (Statelessness)؛ چرا HTTP اینجوریه؟

**چیستی:** HTTP ذاتاً **بی‌حالته** یعنی سرور هیچ خاطره‌ای از درخواست قبلی تو نداره. هر درخواست مثل این می‌مونه که اولین باره داری با سرور حرف می‌زنی .

**چرا این تصمیم رو گرفتن؟** دو تا دلیل اصلی داره:

1. **مقیاس‌پذیری افقی (Horizontal Scaling):** اگه سرور مجبور باشه وضعیت (state) کاربر رو حفظ کنه، اون درخواست باید به همون سرور قبلی برسه. این یعنی لود بالانسرت باید sticky session داشته باشه که خودش یه دنیا دردسر و محدودیت ایجاد می‌کنه. با stateless بودن، هر درخواست می‌تونه بره به هر سروری که خالی‌ست. این یعنی مقیاس‌پذیری بی‌نهایت .
   
2. **کاهش مصرف حافظه:** تصور کن یه سایت میلیونی بخواد state همه کاربراش رو توی حافظه سرور نگه داره. خیلی زود تموم می‌شیم.

**ولی چطور سایت‌ها state دارن؟** اینجا باید دو نوع state رو از هم جدا کنیم :

| نوع State | کجا نگه داشته می‌شه؟ | مثال | ویژگی |
|-----------|---------------------|------|--------|
| **Application State** | سمت کلاینت (مرورگر) | اینکه توی صفحه ۲۳ گالری هستی | با هر درخواست باید بفرستی سمت سرور |
| **Resource State** | سمت سرور | عکسی که آپلود کردی، توییتی که زدی | بین sessionها موندگاره |

**چطور application state رو می‌فرستیم؟** از طریق کوکی‌ها (Cookies)، URL parameters، یا هدرهای خاص مثل Authorization. اینا توی هر درخواست فرستاده می‌شن تا سرور بفهمه "کی هستی و کجایی".

**تصمیم‌گیری عملی:**
- **کی باید stateless بمونیم؟** همیشه. حتی اگه state داری، بذارش سمت کلاینت یا توی دیتابیس مرکزی (مثل Redis).
- **کی sticky session لازمه؟** در طراحی جدید معمولاً نیاز نیست؛ state رو با Redis یا JWT جابه‌جا کن. فقط در سیستم‌های legacy با session در حافظهٔ سرور ممکنه موقتاً لازم باشه.

### ۲. اتصال (Connection)؛ از keep-alive تا multiplexing

**چیستی:** نحوه مدیریت اتصال TCP بین کلاینت و سرور، تأثیر مستقیم روی تأخیر داره.

#### تکامل اتصال در نسخه‌های HTTP:

| نسخه         | رفتار اتصال                                              | مشکل                                                        | راه‌حل                                                  |
| ------------ | -------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------- |
| **HTTP/1.0** | هر درخواست یه اتصال جدید                                 | سربار بالای اتصال (سه‌مرحله دست دادن – Handshake)          | اضافه شدن `Connection: keep-alive` به‌صورت غیراستاندارد |
| **HTTP/1.1** | **اتصال پایدار (Persistent Connection)** به‌صورت پیش‌فرض | هنوز یه زمان یه درخواست می‌تونه بره (Head-of-Line Blocking) | باز کردن چندین اتصال موازی (معمولاً ۶ تا)               |
| **HTTP/2**   | **Multiplexing**: چندین درخواست هم‌زمان روی یه اتصال     | پیچیدگی پیاده‌سازی                                          | یه اتصال کافیه                                          |
| **HTTP/3**   | روی QUIC (روی UDP)                                       | عبور از محدودیت‌های TCP                                     | کاهش تأخیر، مقاومت در برابر از دست دادن بسته            |

**تنظیمات keep-alive توی سرور (مثلاً Nginx):**
```nginx
# سمت کلاینت (مرورگر به Nginx)
keepalive_timeout 65s;    # بعد از آخرین درخواست، ۶۵ ثانیه صبر کن
keepalive_requests 100;    # هر اتصال حداکثر ۱۰۰ تا درخواست بده

# سمت upstream (Nginx به backend)
upstream backend {
    server 127.0.0.1:8080;
    keepalive 32;          # ۳۲ تا اتصال idle رو باز نگه دار
}
```

**تصمیم‌گیری عملی:**
- **HTTP/1.1:** برای هر host تا ۶ اتصال موازی باز کن. این محدودیت رو مرورگر اعمال می‌کنه .
- **HTTP/2:** تعداد اتصال رو کم کن (حتی یه دونه کافیه). این باعث کاهش مصرف منابع سرور می‌شه.
- **کی Connection: close بفرستیم؟** وقتی می‌خوایم سرور رو از بار سنگین خلاص کنیم (مثلاً بعد از redirect). ولی در کل توصیه نمی‌شه.

### ۳. کش (Caching)؛ علم معامله بین تازگی و سرعت

کش (Cache) یعنی نگه داشتن یه کپی از پاسخ قبلی برای استفاده مجدد. این کار سرعت رو می‌بره بالا و بار سرور رو کم می‌کنه. ولی اگه درست استفاده نشه، کاربر می‌تونه محتوای قدیمی ببینه.

**دو نوع کش داریم:**

| نوع کش | کجا قرار داره | مخاطب |
|--------|---------------|-------|
| **Private Cache** | مرورگر خود کاربر | فقط همون کاربر |
| **Shared Cache** | پراکسی، CDN | همه کاربرا |

#### هدرهای اصلی کش :

**۱. Cache-Control (مهمترین)**

```http
# اصلاً کش نکن (برای اطلاعات حساس)
Cache-Control: no-store

# کش کن ولی قبل از استفاده، با سرور چک کن (validation)
Cache-Control: no-cache

# فقط برای همین کاربر (مثل داشبورد شخصی)
Cache-Control: private, max-age=3600

# برای همه قابل اشتراکه (مثل عکس‌ها، CSS)
Cache-Control: public, max-age=31536000

# برای CDN یه مدت طولانی‌تر بذار، برای مرورگر کوتاه‌تر
Cache-Control: public, max-age=600, s-maxage=3600
```

**۲. Expires (قدیمی‌تر)** - یه تاریخ مشخص می‌ده :
```http
Expires: Mon, 25 Jun 2026 21:31:12 GMT
```
اگه `max-age` هم باشه، `max-age` مقدمه.

**۳. ETag (Entity Tag)** - validation مبتنی بر محتوا :
```http
# پاسخ سرور
ETag: "33a64df551425fcc55e4d42a148795d9f25f89d4"

# درخواست بعدی (If-None-Match)
If-None-Match: "33a64df551425fcc55e4d42a148795d9f25f89d4"

# اگه تغییر نکرده باشه، سرور 304 برمی‌گردونه
```

**۴. Last-Modified** - validation مبتنی بر زمان :
```http
# پاسخ سرور
Last-Modified: Mon, 03 Jan 2011 17:45:57 GMT

# درخواست بعدی (If-Modified-Since)
If-Modified-Since: Mon, 03 Jan 2011 17:45:57 GMT
```

#### استراتژی‌های پیشرفته :

**۱. Stale-While-Revalidate**  
محتوای قدیمی رو نشون بده، در همین حین توی پس‌زمینه نسخه جدید رو بگیر:
```http
Cache-Control: max-age=3600, stale-while-revalidate=3600
```
یعنی تا ۱ ساعت محتوای تازه، بین ۱ تا ۲ ساعت محتوای قدیمی با بازآوری پس‌زمینه.

**۲. Immutable**  
برای فایل‌هایی که هیچ‌وقت عوض نمی‌شن (مثل فایل‌های با hash توی اسم) :
```http
Cache-Control: public, max-age=31536000, immutable
```

**۳. Max-Age=0**  
هر بار validation کن:
```http
Cache-Control: max-age=0
```
این شبیه `no-cache` هستش.

**تصمیم‌گیری عملی:**

| نوع محتوا | استراتژی کش | دلیل |
|-----------|-------------|------|
| **HTML صفحات پویا** | `no-cache` یا `max-age=0` | همیشه تازه باشه |
| **APIهای عمومی** | `max-age=60, stale-while-revalidate=300` | یه دقیقه تازه، ۵ دقیقه قدیمی با بازآوری |
| **عکس‌ها، CSS، JS (بدون hash)** | `max-age=86400` (۱ روز) | روزانه عوض می‌شن |
| **فایل‌های با hash (versioned)** | `public, max-age=31536000, immutable` | تا ۱ سال، با نام جدید عوض می‌شن |
| **داده‌های خصوصی کاربر** | `private, no-cache` | فقط برای اون کاربر، همیشه validation |
| **داده‌های حساس (بانکی)** | `no-store` | اصلاً ذخیره نکن |

### ۴. محدوده (Range Requests)؛ دانلود جزئی

**چیستی:** کلاینت می‌تونه فقط یه تیکه از یه فایل رو بخواد. این برای resume دانلود، ویدیوهای آنلاین، یا PDF خوان‌ها عالیه.

**چطور کار می‌کنه؟** 

کلاینت می‌گه:
```http
GET /bigfile.zip HTTP/1.1
Range: bytes=5000-9999
```

سرور اگه پشتیبانی کنه، جواب می‌ده:
```http
HTTP/1.1 206 Partial Content
Content-Range: bytes 5000-9999/1024000
Content-Length: 5000
...
```

**کدهای وضعیت مرتبط:**
- `206 Partial Content`: تیکه مورد نظر رو می‌فرستم
- `416 Range Not Satisfiable`: همچین رنجی وجود نداره

**تصمیم‌گیری عملی:**
- برای فایل‌های بزرگ (ویدیو، PDF، فایل‌های دانلودی) حتماً پشتیبانی کن.
- توی CDNها معمولاً خودش پشتیبانی می‌کنن.
- اگه Range درخواست رو نمی‌تونی پاسخ بدی، `Accept-Ranges: none` بفرست.

### ۵. امنیت؛ دیوار دفاعی اول

یه سری هدر هستن که باید برای هر برنامه وب بشناسی :

**۱. HSTS (Strict-Transport-Security)**  
همیشه با HTTPS حرف بزن:
```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

**۲. CSP (Content-Security-Policy)**  
کنترل دقیق روی اینکه چه اسکریپتی اجرا بشه :
```http
# روش nonce-based (برای هر درخواست یه nonce جدید)
Content-Security-Policy: script-src 'nonce-{RANDOM1}' 'strict-dynamic'; object-src 'none'

# روش hash-based (برای static HTML)
Content-Security-Policy: script-src 'sha256-{HASH1}' 'sha256-{HASH2}'
```

**۳. X-Content-Type-Options**  
جلوگیری از MIME sniffing :
```http
X-Content-Type-Options: nosniff
```

**۴. X-Frame-Options**  
جلوگیری از clickjacking:
```http
X-Frame-Options: DENY  # یا SAMEORIGIN
```

**۵. CORS (Cross-Origin Resource Sharing)**  
کنترل دسترسی از دامنه‌های دیگه :
```http
Access-Control-Allow-Origin: https://trusted-site.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, Authorization
```

**تصمیم‌گیری عملی:**
- از ابزار **Helmet** (برای Node.js) یا معادلش توی فریم‌ورکت استفاده کن تا این هدرها رو راحت ست کنی .
- هر شش ماه یه بار سایتت رو با [securityheaders.com](https://securityheaders.com) چک کن.
- برای APIهای عمومی، CORS رو خیلی محدود بذار. هیچ‌وقت از `*` استفاده نکن مگر اینکه واقعاً public API باشه.

---

### خلاصه

| مفهوم | نکته کلیدی برای تصمیم‌گیری |
|-------|---------------------------|
| **Statelessness** | همیشه. اگه state نیاز داری، برو سمت Redis یا JWT |
| **Connections** | HTTP/2 رو فعال کن. تعداد اتصال رو کم کن، کارایی رو ببر بالا |
| **Caching** | محتوای ایستا: `immutable` و طولانی. محتوای پویا: `no-cache` یا `stale-while-revalidate` |
| **Range Requests** | برای فایل‌های بزرگ حتماً پشتیبانی کن |
| **Security Headers** | HSTS، CSP، X-Content-Type-Options رو همیشه بذار. CORS رو محدود کن |

### HTTP/3 چی داره که قبلاً نبود؟

HTTP/3 دیگه روی TCP سوار نمی‌شه، رفته روی **QUIC** (پروتکل لایهٔ انتقال، RFC 9000) که خودش روی UDP سواره. چرا؟

- **وصل شدن سریع‌تر:** ۰-RTT (صفر رفت و برگشت) برای وصل شدن مجدد
- **بدون بلاک شدن:** اگه یه بسته گم شد، بقیه بسته‌ها راهشون رو ادامه می‌دن
- **تغییر شبکه:** اگه از وای‌فای بری به موبایل، قطع نمی‌شی

در سناریوهایی که کاربر زیاد بین شبکه‌ها جابه‌جا میشه (مثلاً وای‌فای به موبایل) یا تأخیر اولیه اتصال مهمه، HTTP/3 (به‌خاطر QUIC و ۰-RTT) می‌تونه قطعی کمتر و latency بهتری در عمل نشون بده؛ اعداد دقیق به محیط و اندازه‌گیری بستگی داره.

## چرا این موضوع در مصاحبه مهمه؟

خب HTTP پایهٔ هر REST API و وب‌سرویسه. مصاحبه‌گر انتظار داره بتونی بگی متدها چی هستن، چرا GET باید Safe و Idempotent باشه، چرا برای POST retry بی‌دقت خطرناکه، و چطور کدهای وضعیت و هدرها رو در طراحی API انتخاب می‌کنی. بدون اینها بحث middleware، CORS، یا امنیت API ناقص میمونه.

---

## نکات کلیدی برای مصاحبه

- **HTTP چیه:** پروتکل لایهٔ کاربرد، stateless، روی TCP (یا QUIC در HTTP/3). درخواست = متد + URI + هدرها + اختیاری بدنه؛ پاسخ = کد وضعیت + هدرها + اختیاری بدنه.
- **Safe vs Idempotent:** Safe = فقط خواندن، بدون تغییر state. Idempotent = اجرای چندباره = نتیجه معادل یک بار. GET هر دو؛ POST هیچ‌کدوم؛ PUT/DELETE Idempotent. اهمیت: retry امن، کش، و طراحی API.
- **کدهای وضعیت:** ۲xx موفقیت، ۴xx خطای کلاینت (۴۰۰ بد درخواست، ۴۰۱ نیاز به احراز هویت، ۴۰۳ ممنوع، ۴۰۴ پیدا نشد، ۴۰۹ تداخل، ۴۲۲ validation، ۴۲۹ rate limit)، ۵xx خطای سرور. انتخاب درست در API = حرفه‌ای بودن.
- **هدرهای مهم برای API:** `Authorization`، `Content-Type`، `Accept`، `Cache-Control`. برای امنیت و مرورگر: CORS، `Content-Security-Policy`، HSTS.
- **HTTP/2 و HTTP/3:** HTTP/2 مالتی‌پلکسینگ و هدر فشرده؛ HTTP/3 روی QUIC (RFC 9000، روی UDP)، اتصال سریع‌تر و مقاوم‌تر در برابر تغییر شبکه. در مصاحبه معمولاً کافیه بدونی چه مشکلی رو حل می‌کنن.

---

## اشتباهات رایج و پرچم قرمز

- **POST برای همه‌چیز:** استفاده از POST به‌جای GET برای خواندن (کش نشدن، عدم استفاده از Idempotent). یا برعکس GET برای عملیاتی که state عوض می‌کنه.
- **retry بدون فکر:** فرستادن دوبارهٔ خودکار POST بدون idempotency key و در نتیجه ایجاد دوبارهٔ منبع.
- **کد وضعیت اشتباه:** برگردوندن ۲۰۰ برای خطا، یا ۴۰۴ برای validation. ۴۰۰ برای ورودی اشتباه، ۴۲۲ برای validation بیزنس، ۴۰۹ برای تداخل.
- **ادعای عددی بدون منبع:** گفتن «HTTP/2 همیشه X درصد سریع‌تره» بدون زمینه. بهتره بگی چه مزیتی داره و در چه شرایطی به کار میاد.
- **نادیده گرفتن CORS:** نمی‌دونم چرا فرانت از دامنهٔ دیگه درخواست نمیزنه یا preflight چیه.

## چه زمانی از چی استفاده کنی

| موضوع | استفاده کن | استفاده نکن |
|--------|-------------|-------------|
| **متد** | GET برای خواندن؛ PUT برای جایگزینی کامل؛ PATCH برای تغییر جزئی؛ DELETE برای حذف؛ POST برای ایجاد یا عملیات غیر idempotent | POST برای خواندن؛ GET با side effect |
| **کد وضعیت** | ۲۰۰/۲۰۱/۲۰۴ برای موفقیت؛ ۴۰۰ برای درخواست بد؛ ۴۰۱/۴۰۳ برای احراز/مجوز؛ ۴۰۴ برای پیدا نشدن؛ ۴۰۹ برای تداخل؛ ۴۲۲ برای validation؛ ۵۰۰/۵۰۳ برای خطای سرور | ۲۰۰ برای خطا؛ ۴۰۴ برای «ورودی اشتباه» |
| **Retry** | برای GET، PUT، DELETE (با رعایت احتیاط برای DELETE) | برای POST/PATCH بدون idempotency key یا مکانیزم یکتا |
| **HTTP/2 و HTTP/3** | وقتی ترافیک زیاد هم‌زمان یا تأخیر اولیه و پایداری اتصال مهمه | ادعای درصد بهبود بدون اندازه‌گیری در همان محیط |
