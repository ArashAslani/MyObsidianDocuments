### 1. مقدمه ای بر DNS (Domain Name System)

اینترنت یک شبکهٔ جهانی از روترها، سوئیچ ها و میزبان‌ها (Host) است.  
هر دستگاهی که بخواد با دستگاه دیگه‌ای صحبت کنه، باید آدرس ‎IP‎ اون میزبان رو بلد باشه.  
آدرس‌های ‎IP‎ بلند، عددی و پویا هستن یعنی حفظ کردنشون برای آدما سخته و ازونطرف ممکنه آدرس IP یه برنامه تغییر بکنه یعنی روی یک سرور دیگه مستقر بشه و IP متفاوتی بگیره پس ردیابی یک برنامه صرفا از روی IP برای ما کار سختیه.

تو یک برداشت ساده DNS یا سیستم نام دامنه (Domain Name System) یه دفترچه تلفن اینترنته که نام های دامنه که خیلی خوانا و مناسب ذهن انسان هاست (مثلاً www.google.com) رو به آدرس‌های ‎IP‎ ‌ترجمه می‌کنه.  
درک ساختار، جریان و مکانیزم‌های کش DNS برای هر مهندس شبکه، مدیر سیستم و توسعه‌دهندهٔ نرم‌افزاری که با اینترنت سروکار داره، ضروریه پس بریم سراغش.

---
### 2. از برنامه تا DNS – جعبهٔ سیاه

وقتی توی مرورگر یک دامنه مثل google.com رو سرچ میکنیم مرورگر به عنوان کلایت DNS عمل میکنه:

1. یک پرس و جو (query) یا درخواست برای دامنه مورد نظر می‌سازه.
2. اون query رو به صورت UDP دیتاگرام به سرور DNS محلی (که معمولاً سرور ISP یا DHCP هست) می‌فرسته.
3. منتظر جواب می‌مونه (معمولاً چند میلی‌ثانیه، ولی ممکنه چند ثانیه هم طول بکشه).
4. حالا IP ای که به دست اورده (یا خطای رخ داده شده) رو به برنامه برمی‌گردونه.

از دید برنامه، DNS یک جعبهٔ سیاهه – فقط آدرس دامنه رو می‌گیره و IP برمیگردونه. ولی پشت صحنه، یک پایگاه دادهٔ توزیع‌شده و پیچیده هست که باید به میلیاردها query جواب بده.

### 3. سوال اینه چرا پایگاه های توزیع شده و مرکزی نه؟

فرض کنیم به صورت ساده تمام نگاشت‌های Domain→IP رو بر روی یک سرور قرار بدیم. این روش چند مشکل اساسی داره:

| مشکل              | تاثیر                                                                                                                                   |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| نقطهٔ شکست واحد   | اگر سرور DNS واحدمون از کار بیوفته، کل اینترنت غیر قابل دسترس میشه.                                                                     |
| گلوگاه ترافیک     | یک سرور باید تمام کوئری های همه سرورها رو جواب بده.                                                                                     |
| تاخیر             | مثلا اگر سرور توی تهران باشه کاربر های استرالیایی باید 15ms منتظر هر IP بمونن.                                                          |
| اضافه‌بار نگهداری | هر سرور جدید، هر تغییر، هر به‌روزرسانی، روی یک پایگاه داده کار میکنن و اینکار عملا سرور رو سنگین می‌کنه و تاخیر توی پاسخ دهی زیاد میشه. |

بنابراین DNS به‌صورت توزیع‌شده و سلسله‌مراتبی (Hierarchical) طراحی شده.

---

### 4. بریم سراغ The DNS Hierarchy

سلسله‌مراتب از سه طبقه اصلی از سرور تشکیل شده که هر کدوم نقش خاصی داره:

| نوع سرور               | مسئولیت                                                            | مقیاس معمولی که دارن                                                                                 |
| ---------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| Root DNS               | آدرس سرورهای TLD رو می‌ده.                                         | حدود ۴۰۰ سرور در سراسر جهان، توسط ۱۳ سازمان اداره میشه.                                              |
| TLD (Top‑Level Domain) | آدرس سرورهای مجاز دامنهٔ خاص (مثلاً .com، .edu، .uk) رو می‌ده.     | یک کلاستر برای هر TLD؛ مثلا برای .com، یک شرکت (Verisign) مسئوله. برای .net یک شرکته دیگه و...       |
| Authoritative          | رکوردهای واقعی دامنه (A، AAAA، MX، CNAME و ...) رو نگهداری می‌کنه. | یک یا چند سرور برای هر سازمان؛ می‌تونن خودمونو میزبان کنن یا به سرویس‌دهنده مثل ابرآروان واگذار بشن. |

دیاگرام سلسله‌مراتب

```
Host → Local DNS (ISP) → Root → TLD → Authoritative → Host
```

یک سرور دیگه هم وجود داره به نام Local DNS Server که متعلق به این سلسله مراتب نیست با این حال تو مرکز ساختار DNS قرار داره. وقتی از سیستم خانگی به یک ارائه دهنده اینترنت ISP وصل میشیم اون به عنوان پروکسی بین ما و ساختار DNS قرار میگیره و کوئری های مارو ارسال میکنه.
به Local DNS Server معمولا DNS resolver یا recursive DNS resolver هم میگن.

### 5. جریان پرس و جو DNS

بریم سراغ یک مثال برای پیدا کردن ‎www.amazon.com‎ از یک کلاینت در خانه که به ISP متصل هست:

1. Client → Local DNS  
    کلاینت یک کوئری بازگشتی (recursive) به DNS محلی می‌فرسته (مثلاً `dns.nyu.edu`).  
    
2. Local DNS → Root Server  
    چون DNS محلی کشی نداره، کوئری از نوع تکراری (iterative) رو به سرور ریشه (مثلاً `a.root-servers.net`) می‌فرسته.  
    سرور ریشه IP سرورهای TLD .com را برمی‌گردونه.
    
3. Local DNS → TLD Server  
    اینجا DNS محلی به یکی از سرورهای TLD .com (مثلاً `a.gtld-servers.net`) ارتباط میگیره و به اون یک کوئری iterative ارسال میکنه.  
    سرور TLD آدرس IP سرور authoritative DNS برای amazon.com را برمی‌گردونه.
    
4. Local DNS → Authoritative Server  
    در نهایت DNS محلی سرور authoritative (مثلاً `ns-123.awsdns.com`) را پرس و جو می‌کنه یعنی دوباره یک کوئری از نوع iterative میفرسته.  
    سرور authoritative رکوردهای A برای ‎www.amazon.com‎ را برمی‌گردونه.
    
5. پخش پاسخ  
    اینجا DNS محلی هر پاسخ را (با توجه به TTL) کش می‌کنه و آدرس نهایی را به کلاینت برمی‌گردونه.
    

در این حالت ساده ۴ پرس و جو و ۴ پاسخ داریم؛ در عمل تعداد بسته‌ها ممکنه ۸ یا ۱۰ هم بشه وقتی سرورهای واسطه‌ای وجود داشته باشن.

### رکورد های DNS

| رکورد | هدف                                 | مثال                                                    |
| ----- | ----------------------------------- | ------------------------------------------------------- |
| A     | آدرس IPv4                           | `google.com A 172.217.3.110`                            |
| AAAA  | آدرس IPv6                           | `google.com AAAA 2607:f8b0:4007:80e::200e`              |
| MX    | سرور پست الکترونیک (Mail exchanger) | `example.com MX 10 mail.example.com.`                   |
| CNAME | نام مستعار (Canonical name)         | `www.example.com CNAME example.com.`                    |
| TXT   | متن دلخواه (برای SPF، DKIM و…)      | `example.com TXT "v=spf1 include:_spf.google.com ~all"` |
| NS    | رکوردهای Nameserver                 | `example.com NS ns1.example.net.`                       |

### 7. کش کردن DNS – موتور عملکرد

بدون کش، به ازای هر درخواست آدرس IP از طریق دامنه باید کل زنجیره پرس و جو اجرا بشه، که حجم عظیمی ترافیک و تاخیر ایجاد می‌کنه.  
سرورهای DNS هر رکوردی را که دریافت می‌کنن، بر اساس TTL (زمان بقاء) کش می‌کنن:

- کش محلی – پاسخ‌های سریع برای درخواست‌های بعدی از طرف همان یا دیگر کلاینت‌ها.
- کش TLD – به سرورهای محلی اجازه میده ریشه رو برای کوئری های تکراری رد کنن.
- کش ریشه – خیلی کم مورد استفاده هست؛ سرورهای ریشه فقط آدرس TLD را برای مدت کوتاهی کش می‌کنن.

کش کردن، ترافیک رو به طرز چشمگیری کاهش میده. مثلاً اگر دو سرور مختلف تو همون شبکه درخواست ‎youtube.com‎ رو در عرض چند دقیقه بدن، سرور محلی از کش خودش پاسخ میده بدون اینکه تماسی با سرورهای ایجاد کنه.
